# M9: Dashboard and docs design overhaul

Status: **draft for review**. No code is written until this is approved. Ships in **1.4.0**.

M9 rebuilds three things on one design system:

- the public site, `seasonsmc.petepeterepeat.com`
- the public docs on that site
- the Seasons Web dashboard every server runs

It also adds rich link previews, finding a server's dashboard from its game address, and rules that keep the docs in step with the code.

## Goals

1. A public site that sells Seasons in under a minute, and takes an owner from "what is this" to a working first season without leaving it.
2. Full, searchable docs for server owners, admins and players: setup, guides, every command, every permission, every config key, and troubleshooting.
3. One visual identity across the site, the docs, the dashboard and the listings (Modrinth, Hangar, GitHub). It should be pixel-art and fun, but professional and easy to read.
4. A dashboard that is responsive from phone to second monitor, that players can lay out themselves (drag, resize, their own dashboards), and that links to the docs.
5. Rich previews when any page is shared, generated per page: every docs page, the server's dashboard, and each player's profile.
6. Finding a dashboard from the game address. A player types the address they join with (`play.example.com`) and is taken to that server's dashboard, or told why not.
7. Docs that can't drift: generated references, CI checks, and an agent rule that every change to commands or usage updates the docs in the same PR.

## Non-goals

- No GitHub Wiki and no separate docs repo (see "Why in this repo").
- No change to a spec decision. Where M9 adds behaviour the spec doesn't cover, the reading goes in `docs/questions.md`, as usual.
- No versioned docs yet. The docs track the latest release, with "since 1.x" badges.
- No server-side saving of dashboard layouts. The API stays read-only, as the spec decides for v1.

## Why in this repo

- The repo is small on GitHub (about 2.5 MB, 805 tracked files). The 1.8 GB on disk is local only: `testkit/bots/node_modules`, the dev server in `adapters/paper/run` and build output.
- Commands, permissions, config and messages change in the same PRs as the code. Docs in the same repo let one PR change both, and let CI fail when they disagree.
- Seasons Web is a Paper plugin built on `core`/`api`, released in the same tag and tested by the same scenarios. Independent work on it is already possible with branches and path-filtered CI.

## Design system

### Look and feel

- **Dark first.** A deep night navy base, panels a step lighter, and 2 px borders.
- **Hard pixel shadows.** `8px 8px 0` on cards and `4px 4px 0` on buttons, in near-black. **Square corners** everywhere.
- **Pixel art as crisp SVG** (`shape-rendering: crispEdges`): the hourglass and laurel logo, the trophy mark, player figures in armour colours, chests, grass and dirt strips, the Hall's brick arches with gold plaques, and the red carpet strip.
- **Type, all three self-hosted** (SIL OFL), with nothing loaded from Google:
  - **Pixelify Sans** for headings and the brand
  - **Inter** for body text
  - **JetBrains Mono** for commands, codes and coordinates
- **Gold is the accent.** The armour colours (diamond teal, gold, iron, netherite) mark seasons.
- **Small touches:** segmented, blocky progress bars; Minecraft-style item tooltips; copy buttons on every command.
- **Motion:** short and steppy, with none under `prefers-reduced-motion`.

### Theme behaviour (site, docs and dashboard)

1. **First visit:** the theme follows the system (`prefers-color-scheme`). With no system preference, it is dark.
2. **The toggle** (sun or moon, with a pixel icon) switches between dark and parchment light. The choice is kept per device.
3. **When the system theme changes** (a `matchMedia('(prefers-color-scheme: dark)')` change event, such as an iPad going dark at sunset), the page switches instantly to match and clears the toggle's override. The system always wins on a change; the toggle only lasts until the next one.
4. **No flash of the wrong theme.** A tiny script, hashed into the CSP, sets `data-theme` before first paint.
5. **Second-screen mode** stays dark, as the spec says.

Starlight's own three-way "auto, dark, light" select is replaced by this two-state toggle, so all three surfaces behave the same. This is recorded in `docs/questions.md`.

### Generated references, so the docs can't drift

- **`:core:commandReference`**, and the same in `web` for `/web`, walks the command tree that Paper registers from: literals, arguments and their types, permission nodes, and help text from `messages.yml`. It writes `site/src/data/commands.json`.

- **CI** (`build.yml`, on every PR):

  - builds the site and checks links
  - checks that every command has a docs page linking to it and a `since` entry
  - checks that the spec's command table and the generated list agree
  - runs the TheRanch grep

## Connect: from game address to dashboard

### What the player does

They type the address they join the game with, such as `play.example.com`, `play.example.com:25566` or `mc.example.com`, and press **Find dashboard**. A blocky progress bar steps through the checks below. Then one of these happens:

- **Found:** "Taking you to Example SMP's dashboard…", then a redirect. A "Remember this server" option, on by default, stores the address and dashboard URL in `localStorage`, so the next visit offers a one-tap "Go to Example SMP".
- **Found, but not answering:** "Example SMP has a dashboard at seasons.example.com, but it isn't answering. The server may be offline or restarting." It offers a retry.
- **No Seasons:** "play.example.com is online, but it doesn't publish a Seasons dashboard. It may not run Seasons Web, or its owner hasn't added the discovery record." It links to the owner guide.
- **Server offline:** "We couldn't reach play.example.com. Check the address, or the server may be offline."
- **Not a valid address:** "That doesn't look like a server address" (as now, with the reason).

Typing a dashboard URL directly still works, as it does today.

### How discovery works

A browser can't talk to a Minecraft server, so the dashboard has to be found through records the owner publishes, then confirmed with the dashboard itself.

1. **Normalise.** Strip the scheme and port and lower-case the host. A raw IP is allowed, but it can only be found by a reverse lookup (step 3).
2. **SRV.** Resolve `_minecraft._tcp.<host>` and note its target, so a player who types the SRV name and one who types the target both work.
3. **TXT record (the main way).** Look up `_seasons.<host>`, and `_seasons.<srv-target>` if different, for `v=seasons1; url=https://seasons.example.com`.
   - Lookups use DNS-over-HTTPS JSON: Cloudflare (`cloudflare-dns.com/dns-query`), with Google (`dns.google/resolve`) as fallback.
   - For an IP, a PTR lookup first gives the host name.
4. **Conventions (fallback).** Try `/.well-known/seasons.json` at `https://seasons.<registrable domain>`, `https://<host>` and `https://<registrable domain>`, each with a short timeout and in parallel.
5. **Confirm.** The well-known reply must list the typed address in a new `gameAddresses` field before the site redirects, so a convention guess can never send a player to someone else's dashboard.
   - Without that field (servers on 1.3 or older), a dashboard found by TXT is trusted, and one found by convention asks "Is this your server?" first.
   - The existing checks remain: https only, a Seasons instance, and a supported API version.
6. **Online or offline.** Only when no dashboard is found does the page ask a public Minecraft status service (`api.mcsrvstat.us`) whether the game server is up. That separates "online, but no Seasons" from "offline". The page says this lookup is made.
7. **Privacy.** Only the typed host name goes to the two DNS resolvers and, when needed, the status service. The page lists them. Nothing is stored except the "Remember this server" entry. CSP `connect-src` names exactly those origins plus `https:` for the dashboard check.

**Deep links.** `seasonsmc.petepeterepeat.com/connect/?server=play.example.com` runs discovery straight away, so owners can post a single link in Discord.

### Seasons Web side

- **`web.yml`** gets `game-addresses: [play.example.com]`. They are served in `.well-known/seasons.json` as `gameAddresses`. This is an additive field, so the API stays at v1.
- **`/web discovery`** prints the exact TXT record to add, for the configured `public-url` and game addresses.
- **`/web discovery check`** looks the record up with the JDK's DNS provider (off the server thread). It reports whether the record is there, matches and points at a reachable dashboard, and the same checks show on the dashboard's admin health widget.
- The `publish-dashboard` guide walks through the Cloudflare DNS steps.

## Rich previews

Every shared link unfurls with a title, a description and a generated 1200 × 630 image in the pixel style. This covers Discord, iMessage, Slack, WhatsApp, X, Bluesky and Facebook.

### What each page sends

Each page sends `og:title`, `og:description`, `og:image` (with width, height and alt), `og:url`, `og:site_name`, `og:type`, `twitter:card=summary_large_image` and `theme-color` (`#1d2333`). Each page also gets a canonical URL and a favicon set (SVG, PNG and apple-touch) from the hourglass.

### The public site

- **Build-time images,** one per page: the page title in Pixelify Sans over a night panel, the section's pixel art (zones show a locked circle, museum a plinth, commands a command block), and a breadcrumb such as "Docs · Running a server".
- The images come from the tokens and art files in `design/`, rendered at build time with a Satori-based renderer, which needs an ADR.
- **Command reference entries** have their own anchors and preview text ("`/hof link go <id>`: take a link you stand at").
- **`/connect/?server=…` links** get a generic "Find your server's dashboard" card. The site is static and can't know the server.

### The dashboard (per server, rendered by Seasons Web)

Social crawlers don't run JavaScript, so Seasons Web puts the tags into the HTML of each page it serves, and renders the images itself.

| Page | Title and description | Image |
| --- | --- | --- |
| `/` (the server) | "Example SMP · Season 3, Frontier" and "Day 12 · 4 online · Homecoming when the group votes" | Server name and icon, season and phase chip, day counter, online count, the next countdown, a grass and dirt strip |
| `/player/<uuid>`, and a new `/p/<name>` that redirects to it | "Alex on Example SMP" and "3 seasons · 2 awards · first into the Nether, Season 3" | The player's pixel head and body from their skin, seasons played, award badges, their latest cell plaque |
| `/hall/<n>` | "Season 2 Hall of Fame · Example SMP" | A row of figures under arches, in each player's armour colours |
| `/museum` | "The Museum · Example SMP" | Egg plinths with the slayers' names |
| `/screen`, `/history` | Generic server card | As `/` |

**Visibility is enforced.**

- A preview shows only what an anonymous visitor may see under `web.yml`'s visibility settings.
- With `profiles: players` (the default), a player preview reads "A player on Example SMP · Log in to see their profile", with no stats.
- Players hidden with `/web privacy` never get a personal card.
- With `public: false`, every preview is the generic server card.
- Admin data never appears.

**How Seasons Web renders the images:**

- Images are drawn with Java2D (`BufferedImage`, `ImageIO`), which is in the JDK, so there is no new dependency. They use the bundled fonts and the same tokens, and run on Seasons Web's own executor, never the server thread.
- Images are cached by a hash of what they show (season, phase, counts, the player's summary). They're served with `Cache-Control` and an `ETag`, and sizes are fixed.
- Requests are rate-limited per IP, and rendering for `/p/<name>` is skipped when no such player exists, so a crawler or attacker can't make the server draw images endlessly.

**Skins.**

- Player heads come from the skin texture already in the player's profile on the server.
- When the texture isn't cached, Seasons Web fetches it once from `textures.minecraft.net`, the only URL the profile points to, and keeps it with the player's web data.
- `web.yml` has `previews.skins: true|false`. With `false`, a plain pixel figure in the player's armour colours is used instead.

**`web.yml`** gets:

```yaml
previews:
  enabled: true
  skins: true
  server-icon: icon.png    # optional, in plugins/SeasonsWeb/
```

## The dashboard (Seasons Web)

### Visual refresh and responsiveness

- **Shared design.** The dashboard uses `design/` tokens, fonts and icons, copied into the jar. It stays a no-build, vanilla ES module app with no inline styles.
- **The login page is rebuilt to match the design's "Link your Minecraft account" page closely:**
  - the server header and "Wrong server?" (which goes to the public connect page)
  - the pixel player figure
  - the big code in separate gold-on-deep cells
  - `/web link CODE` with a copy button
  - the segmented expiry bar
  - "Waiting for you in-game…" as a live status
  - the 30-day and `/web logout` note
  - It works one-handed on a phone and is roomy on an iPad.
- **Breakpoints:**
  - 1 column under 640 px, where widgets stack in priority order
  - 2 columns at 640–1024 px
  - a 12-column grid at 1024 px and up
  - second screen landscape at any size
- **Touch and layout details:** 44 px touch targets, `env(safe-area-inset-*)`, and container queries so a widget adapts to its own width.
- **Profile page** from the design's Profile artboard: season cards, awards, the cell, and archived gear in Minecraft-style tooltips. Each page has a **Share** button that uses the Web Share API, or copies the link.

### Docs inside each instance

- A **Help** item in the dashboard's navigation, and a **Help widget** that can be placed like any other. It contains:
  - The player guides (visiting the Hall, your vault, the dashboard, links) bundled into the jar at build time from the site's `players/` pages, so they match the server's version and work without the public site.
  - The server's own links and rules from `web.yml`. This is where an instance like TheRanch puts its own references.
  - "Full docs" links to `seasonsmc.petepeterepeat.com/docs/` (version-matched path where possible).
- `web.yml` gets `help: { links: [...], rules: <markdown file> }`. Instance-specific text lives only in the instance's config, never in the jar or on the public site.

### Customisable dashboards

- **Edit mode.** "Edit layout" turns the page into a 12-column grid editor:
  - drag a widget by its handle
  - resize it from its corner, snapping to the grid
  - add a widget from a tray of everything the viewer may see, or remove one
  - reset to the server's default
- **Keyboard.** Focus a widget, then arrow keys move it and shift plus arrows resize it. Changes are announced in a live region.
- **Several dashboards** ("Second screen", "Build night", "Admin"), switched from a tab strip. One can be marked as what `/screen` opens on this device.
- **Where layouts are kept:** in `localStorage`, per server address.
  - **Copy layout** gives a short share code another device can paste.
  - **Copy as web.yml**, for admins, gives the `screens:` block, so an owner can design the server default in the browser.
- **The server still decides visibility.** A layout only arranges widgets the API returns to that viewer. A hidden one shows "not available to you".
- **Widget sizes.** Each widget declares its minimum and preferred sizes, and has compact, regular and large renderings.
- **Implementation.** An in-house grid built on pointer events and CSS grid, with positions set through the CSSOM, which the CSP allows. `gridstack.js` is only a fallback, with an ADR.

## Rules for future agents

These go in `AGENTS.md`, mirrored in `CONTRIBUTING.md` and the PR template:

- **Docs in the same PR.** Any change to a command, argument, permission, config key, `web.yml` key, player-facing message or visible behaviour updates the public docs in `site/` **in the same PR**:
  - the guide page that explains it
  - the regenerated references (`./gradlew commandReference permissionReference configReference`)
  - a `since.yml` entry for anything new
  - a CHANGELOG line
- **Bundled guides.** A change to a page under `docs/players/` also changes the guide bundled in the dashboard, and the build regenerates it.
- **CI fails** on a stale reference, a command with no docs page or `since` entry, a broken link, or `TheRanch` on the public site or in the README.
- **Spec first.** The public docs explain *how to use* what `docs/spec.md` *decides*. When they disagree, the docs are fixed, never the spec.
- **Style.** Second person, task first, one idea per paragraph, real commands that can be copied, and generic examples only.
- **PR template checkbox:** "Docs updated (site/), or not needed because …".

## Readings to record in `docs/questions.md`

- Theme: the system preference wins on every change, and the toggle lasts until the next change.
- Connect: discovery by the `_seasons` TXT record and conventions; `gameAddresses` confirms a match; the status service is asked only after discovery fails; DNS-over-HTTPS and status lookups are listed on the page. The spec's connect flow (type an address, fetch the well-known) is kept and extended.
- Previews: public share pages render meta tags and images from data visible to anonymous visitors only. `/p/<name>` is an alias. Skin textures are fetched from `textures.minecraft.net` only when needed, and can be turned off.
- The Help widget and bundled guides are read-only pages served by Seasons Web, so the API stays read-only.

## Risks

- **Starlight under a strict CSP.** Spiked first. The fallback is a post-build hash step.
- **DNS-over-HTTPS or the status service being down or blocked.** The page falls back to the other resolver, then to conventions, and finally says it couldn't check, rather than "no Seasons".
- **Crawlers caching old previews.** Image URLs carry the content hash, so a changed season or profile gives a new URL.
- **Drag and resize on iPad Safari.** Pointer events with `touch-action: none` on handles only. Tested in Playwright's WebKit.
- **Doc volume.** Phase 3 is the largest. It is written section by section from the spec and checked against the generated references.
