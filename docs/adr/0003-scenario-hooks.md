# 3. Scenario hooks, only on scenario servers

Date: 2026-11-18 · Status: accepted

## Context

The M1 acceptance scenarios need three things no Seasons command offers:

- A7 stops the server dead at each step of archiving, to show every item ends up exactly once after the restart.
- Several scenarios check what an archive holds (stacks, items, the vault page, the advancement count) and whether a player's operations wait for recovery.
- A8 clicks through the archive view, which players reach through archive anchors in the Hall. The Hall arrives in M1 part 3.

## Decision

`com.petepeterepeat.seasons.core.scenario.ScenarioHooks` does exactly three things:

1. Arm a crash point for one player: archiving them calls `Runtime.getRuntime().halt(0)` right after that step's fsync (the archive file written, `ARCHIVE_STARTED`, `VAULT_SEALED`, the reset, `ARCHIVE_DONE`).
2. Read an archive summary and the player's record (`archivedThrough`, operations pending).
3. Open an archive view for a viewer.

Seasons creates the hooks only when the JVM starts with `-Dseasons.scenario=true`, read once in `SeasonsPlugin#onEnable`. Without the flag no `ScenarioHooks` object exists, no service is registered, nothing listens for crash points (the archiver gets `CrashPoints.NONE`) and no command reaches them. Nothing can turn them on at run time: there is no command, config key or API call for it. Only the scenario servers set the flag, in `testkit/build.gradle.kts`, and Seasons logs a warning when it is on.

The test plugin (`testkit`, never shipped) finds the hooks through the services manager and offers `/scenario crash-at`, `/scenario archive` and `/scenario open-archive` to the admin bot. When the server halts on purpose, the test plugin writes `halted.json`; Gradle then accepts the session if the bot runner's own `results.json` says every check passed.

## Consequences

- A production server is unaffected: the hooks are inert unless an operator adds the JVM flag by hand.
- The test plugin also has `/scenario place`, which fires a `BlockPlaceEvent` for a bot and sets the block if nothing cancels it. It is not one of the hooks and touches nothing in Seasons: through ViaBackwards the server drops a Mineflayer bot's own block placement, so A15 can't place blocks otherwise (see ADR 0001).
- Opening the archive view through the hooks is temporary. M1 part 3 switches A8 to clicking an archive anchor (the TODO in `a08-archive-view.mjs`).
- M1 part 3 amendment (2026-11-18): crash points also cover `/hof import` (`IMPORT_STARTED`: the record written and journalled, nothing in the cell changed; `IMPORT_CLEARED`: the cell emptied, `IMPORT_DONE` not written), armed for the cell's owner. The archive summary also reports how many pages the archive view has. Like `/scenario place`, the test plugin gains `/scenario break` (fires `BlockBreakEvent`) and `/scenario use` (fires `PlayerInteractEvent` for a right-click on a block), because the translation drops a bot's own clicks on blocks; a spike showed its clicks on entities get through, so figures are clicked by the bot itself. With archive anchors in place, A8 opens the view by clicking one, and `/scenario open-archive` stays only for debugging.
- M1 part 4 amendment (2026-11-18): reading what Seasons holds also covers a player's season card, as plain lines (`/scenario card <player> <season>`), since bots can't read a book's pages through the protocol translation. A14 checks the book itself opens from the plaque anchor by waiting for the `open_book` packet.
- Alternatives rejected: a config key could be switched on by mistake or by `/season reload`; reflection into Seasons from the test plugin breaks the public-API rule and hides what the tests depend on; killing the server process from outside can't stop it at an exact journal step.
- M2 part 1 amendment (2026-11-18): like `/scenario place`, the test plugin gains stand-ins for what bots can't do through the translation, none of them hooks into Seasons: `/scenario use … sneak`, `move`, `pearl`, `use-item`, `consume`, `drop`, `sit` and `glide`. Each fires the real Paper event (or calls the Paper API that fires it) so Seasons decides as it would for a real client.
- Review of #11 amendment (2026-11-18): `/scenario move` puts the player where the move went with a teleport the test plugin cancels at `LOWEST` and lets through at `HIGHEST`, so no other plugin, Seasons included, sees a teleport event, as with a real client's movement. Before this, Seasons also saw the teleport, which by itself returned a visitor, so A27 would have passed without `PlayerMoveEvent` reaching Seasons. A last word `back` makes a second move return the player in the same tick, which only the move event can notice (the Hall's sweep runs every 500 ms); A27 uses it to show the move event is wired.
- M2 part 2 amendment (2026-11-18): three more stand-ins, again none of them hooks into Seasons. `/scenario open` right-clicks a block and, if the click goes through, opens a container's inventory as the game would (`InventoryOpenEvent`), then reports a few ticks later whether the player has the block's own inventory open, something else (Seasons' view-only copy) or nothing. `place-entity` fires `EntityPlaceEvent` for an entity such as a cushion and adds it if allowed. `hit` makes the player attack an entity with `Player#attack`, a real hit with all its events. `/scenario place` now sets the block before `BlockPlaceEvent` runs and puts the old one back if refused, as the game does, so listeners see the placed block. Bots still right-click and hit item frames and armour stands themselves, since entity clicks get through the translation.
- Review of #12 amendment (2026-11-18): `/scenario place` takes a block with its state, such as `minecraft:chest[facing=north,type=right]`, so a scenario can place half of a double chest; `/scenario break … drops` breaks as survival does, dropping what the block drops unless a listener turns drops off, so a scenario can see that Seasons did. Neither hooks into Seasons.
- M3 part 1 amendment (2026-11-19): more stand-ins, none of them hooks into Seasons. `/scenario move … fly` moves a player gliding with an elytra; `place … consume` takes the block from what the player carries, as the game does; `ride` seats the player in a new boat and moves the boat with them in it (`VehicleMoveEvent`, then the teleport); `chorus` teleports with the cause chorus fruit gives, since where the fruit lands is random; `portal` fires `PlayerPortalEvent` and then teleports with the portal cause; `portal-pair` fires `PortalCreateEvent` for the frame the game would build at the other end of a trip; `bucket` fires the bucket events; `ignite` fires `TNTPrimeEvent` for TNT and `BlockIgniteEvent` otherwise; `permit` attaches a permission, such as `seasons.zone.bypass`, which no permissions plugin on the scenario server can grant. The bots also read Paper's action bar packet, which this Mineflayer ignores, as a chat line at the action bar's position, so scenarios can wait for action bar text as for chat.
- Faster scenario suite amendment (2026-11-19): the suite runs many scenarios on one server per shard instead of booting a server for each, and skips waits instead of sitting them out. Seasons gains three hooks, under the same rule as the others (they exist only with `-Dseasons.scenario=true`, read once in `SeasonsPlugin#onEnable`; nothing turns them on at run time):
  1. **Reset.** `ScenarioHooks#reset` disarms every crash point, stops Seasons, runs the test plugin's own reset of the world (loading a chunk to put it back can still reach Seasons' listeners, such as the tripwire's), deletes Seasons' config folder and its data folder in the world, and starts a new Seasons as on a fresh install. Paper commands now run whatever command tree is registered under their path when they run, so the new Seasons answers the commands Brigadier already knows; on a real server the tree is registered once and nothing changes.
  2. **Clock.** On a scenario server Seasons runs on a `ScenarioClock` (real time plus an offset that only grows) and a `ScenarioScheduler` (the platform's scheduler, plus a note of every delayed and repeating global task). `ScenarioHooks#advance` moves the clock forward and, on the server thread, runs every delayed task that came due and every repeating task whose period passed, once each, so reminders, countdowns, decorating windows, rate limits, cooldowns and Seasons' own sweeps come due at once (`docs/questions.md` 114). A reset puts the clock back to real time.
  3. **Task count.** `ScenarioHooks#scheduledTasks` counts Seasons' delayed and repeating tasks, for the leak check.

  The test plugin gains `/scenario reset`, `/scenario clock [+<duration>]` and `/scenario sync <id> [ticks] [player...]`, which answers once the current tick (or that many more) has finished, to the sender and each player named, so scenarios end "no message" windows and wait for the game's own ticks without fixed sleeps. The reset itself is the test plugin's, none of it a hook into Seasons beyond the three above: it kicks everyone, deletes their player files, clears ops, the whitelist, scoreboards, command boss bars, forced chunks and its own chunk tickets, puts back game rules, time, weather, difficulty, world border and spawn, puts back every block of every chunk loaded since the last reset from a copy taken the first time the chunk loaded, untouched until then (in every dimension, kept on disk so it survives restarts and halts), and removes every entity but players. It loads those chunks first, holds them with a ticket and waits for their entities, which Paper loads after the chunk itself, so an entity left in a chunk that had unloaded is removed too (`m0-reset-leaks` checks this through `ctx.reset()`). It then compares the server with the fingerprint of the shard's fresh boot and reports any difference as a leak, which fails the scenario before it. The bot runner asks for the reset over its standard output and reads the answer from its standard input. Scenarios with sessions or crash points still get real restarts; a scenario the reset can't serve would carry `// @isolated <reason>` and get a fresh server of its own (none does). `-PscenarioIsolation=fresh` keeps one fresh server per scenario, run nightly.
- M3 part 2 amendment (2026-11-19): one more hook, under the same rule as the others: `ScenarioHooks#returnToVault` (`/scenario vault-return <player> <item> <count>`) hands a stack back to a player on their vault's Returned page, as a curator's return or an undelivered dragon egg will once M4 brings them; and three crash points for a vault withdrawal (`VAULT_WITHDRAW_STARTED`, `VAULT_WITHDRAW_PERSISTED`, `VAULT_WITHDRAW_GIVEN`). The test plugin gains stand-ins that don't hook into Seasons: `tame` (sets an animal's owner through the API), `chest` (puts a chest on a donkey, mule or llama or takes it off), `leash`, and `forget-pet`, which takes the `seasons:pet` mark off an animal so that its removal goes unnoticed, standing in for a pet removed while Seasons wasn't watching, such as when its chunks are regenerated.
- M3 part 3 amendment (2026-11-19): `/scenario bluemap` prints what BlueMap holds in Seasons' marker sets, read through BlueMap's API on the one scenario server that has BlueMap (ADR 0004). It reads BlueMap, not Seasons, and is no hook.
- M4 part 1 amendment (2026-11-20): `/scenario dragon info|respawn|hurt|crystal` plays the End's dragon fight as players would: bots can't aim, so a hit is made with the player as its damage source's causing entity (and an arrow they shot as the direct one), and a crystal is one the player really breaks beside the dragon, whose real explosion hurts it. It reads and changes the game, not Seasons, and is no hook. `respawn <player>` has the player place four end crystals from their inventory, each firing `EntityPlaceEvent` as the game's own placement does, and after each calls `DragonBattle#initiateRespawn()`, the game's own check that the end crystal item makes; the previously-killed flag is never touched. Five more crash points, armed for the slayer or the op: `EGG_JOURNALLED` (`EGG_DELIVERED` on disk, the egg still on the portal), `EGG_CLEARED` (the egg journalled and off the portal), `EGG_RETURNED` (on the Returned page, not given), `MUSEUM_STORED` (a `/museum add` in the store, the item still held) and `MUSEUM_TAKEN` (taken and the op's file saved, `MUSEUM_DONE` not written). The record line of `/scenario archive` gains `returned=`, what waits on the player's Returned page. The dragon scenarios are the first `@isolated` ones: the reset puts back blocks, entities and the flag, but not the fight's own state (its gateways and exit portal), which the game keeps outside the chunks.
- M4 part 1 review amendment (2026-11-20): one more hook, under the same rule: `ScenarioHooks#armSave` (`/scenario save-at <POINT> <player>`) saves every world to disk when the player reaches that crash point, without stopping, through a saver the test plugin sets (`save-all flush`). A halt at a later crash point then finds the world as it was at the save, not at the last autosave, so the egg crash scenarios start from an egg on disk on the portal, as a real crash before the next save would.
- M4 part 2 amendment (2026-11-20): `/scenario stat <player> <statistic> <value>` sets a vanilla statistic of an online player with `Player#setStatistic`, a General-tab one by the game's id (`minecraft:deaths`, `minecraft:play_time`) or a block mined or used (`minecraft:mined:minecraft:diamond_ore`), so the award scenarios can give players numbers bots can't earn in time. Like `/scenario place`, it is a stand-in, not a hook: it touches nothing in Seasons, which reads the statistic through the game as usual.
- M4 part 3 amendment (2026-11-21): three crash points for a curation (`CURATE_JOURNALLED`, `CURATE_REMOVED`, `CURATE_DELIVERED`), armed by the curator, under the same rule as the others. A sneak-click on a figure is the bot's own `use_entity` packet with its sneaking flag set, since Mineflayer's `activateEntity` always clears it; it needs no stand-in. The bots' webhook receiver serves several paths on the shard's port, one per webhook (the public channel and the admin webhook), and can answer a request with 500 or 429 to check retries.
- M5 amendment (2026-11-21): `/scenario use` takes `left` for a left click and `face=<side>` for the side of the block clicked (default `up`), beside `sneak`, so scenarios click blocks with the wand as a builder does; it still only fires `PlayerInteractEvent` and is no hook. Two crash points for `/hof stamp`, armed by the admin who stamps, under the same rule as the others: `STAMP_STARTED` (the plan saved and `STAMP_STARTED` on disk, nothing placed) and `STAMP_PLACED` (every copy placed, its markers air and the world saved; the gallery file and `STAMP_DONE` not written). Templates are saved in scenarios with a real structure block in SAVE mode powered by a redstone block, as a builder could, so capture needs no stand-in.
- Setting up the Hall amendment (2026-11-22): four more stand-ins, none of them a hook into Seasons. `/scenario console <command...>` runs a command as a sender that isn't a player (`Server#createCommandSender`), passing what it is told back prefixed "Console: ", so scenarios check console replies (A62, A64). `/scenario swap-hands <player>` fires `PlayerSwapHandItemsEvent` and swaps unless it is cancelled (A67); `/scenario scroll <player> <slot> [sneak]` fires `PlayerItemHeldEvent`, sneaking if asked, and holds that slot unless it is cancelled (A71), since bots' sneaking and looking are movement the translation drops. `/scenario place-entity` now spawns a creature, such as an armour stand, with the `DEFAULT` spawn reason the game's own placing gives it, rather than adding it as a plugin would, so the Hall's spawn guard sees what it would for a real player (A75).
- M6 amendment (2026-11-22): one more hook, under the same rule as the others: `ScenarioHooks#meter`, a `TickMeter` for the performance scenario A43. On a scenario server the `ScenarioScheduler` times every task Seasons runs on the server thread and `MeteredDisplays` times every call to the displays port, both in the server thread's CPU time, so the bots sharing the machine don't count. It measures nothing until started. The test plugin gains `/scenario perf warm|start|stop`: `start` marks each tick from Paper's `ServerTickStartEvent` and `ServerTickEndEvent` and, the first time, rebuilds every handler list Seasons is in with each of Seasons' listeners wrapped in a timer, in the order they ran, through the public `HandlerList` API, so no listener's place moves; the wrappers stay for the server's life, which is why A43 is `@isolated`. `stop` reports the ticks watched, Seasons' average and worst tick, the worst tick of drawing displays and the slowest work by name. `warm` spawns and removes, through the Paper API, a figure, a text display and an item display dressed as Seasons dresses them, paying the game's one-off cost of the first of each before measuring (questions 289); it touches nothing in Seasons. Scenario servers also take 40 players, and a scenario may export `timeoutMs` for a session longer than two minutes.
- M7 part 1 amendment (2026-11-23): Seasons Web has hooks of its own under the same rule: `WebScenarioHooks`, registered only when the JVM starts with `-Dseasons.scenario=true`, with `reload` (read `web.yml` again and listen as it says), `reset` (stop listening and delete `web.yml`, `messages.yml` and `<world>/seasons-web`, as a fresh install) and `advance` (Seasons Web's own `OffsetClock`, real time plus an offset that only grows). The test plugin's `/scenario web reload` calls the first, its reset the second before Seasons', and `/scenario clock` moves both clocks. Each shard has its own web port (25702 + 10k), passed to the bot runner as `--web-port`; scenarios write it into `web.yml`.
