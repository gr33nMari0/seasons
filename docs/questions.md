# Open questions

Ambiguities found while building, the reading taken, and what to confirm. Newest last.

## M0

1. **Java package and Maven group.** The spec names no package. Taken: `com.petepeterepeat.seasons` (from the play.petepeterepeat.com domain in the runbook), with `com.petepeterepeat.seasons.lib` for relocated libraries. Renaming later is a mechanical refactor, but it changes the persistent-data keys (`seasons:` namespaces are unaffected; only class names move).
2. **Mineflayer trails 26.3.** Mineflayer 4.39.0 (the latest) supports up to Minecraft 26.1. Taken: the bots speak 26.1 and the scenario servers install ViaVersion and ViaBackwards so they can join a 26.3 server. Test servers only; recorded in `docs/adr/0001-viaversion-on-scenario-servers.md`. Drop them when Mineflayer supports the newest drop. Confirm this is acceptable, since bots then see the world through a protocol translation.
3. **bStats plugin ids.** Each jar needs its own bStats plugin id, registered on bstats.org by the owner. Taken: bStats is pinned in `libs.versions.toml` but not yet shaded or started; it is wired in once the ids exist (by M6, the public release). `THIRD_PARTY_NOTICES.md` will list it then.
4. **Curation permission nodes.** The spec says `seasons.curate.*` without naming the leaves. Taken: they are declared in M4 with the curation commands, default `op`.
5. **"Every supported version" in CI.** v1 supports only 26.3, so the spec's `build.yml` (one job) covers it. Taken: `minecraftVersions` in `gradle.properties` lists the versions, and `scenarioTest` runs one scenario server per entry, so adding the next drop is a one-line change. The CI compile against the newest Paper API with deprecations as errors comes with M6.
6. **Branch names.** The repository's first commit is on `master`, while the spec and the workflows use `main`. Taken: M0 is on `m0-skeleton`; rename `master` to `main` before creating the GitHub repository.
7. **Default branch protection and the GitHub repository** are not created by M0; they need the owner's account (`gh repo create seasons --public|--private --source . --push`).
8. **Dependabot and paper-api.** `libs.versions.toml` has two `paper-api` entries: `paper` (`26.3.build.+`, the oldest supported drop) and `paper-mockbukkit` (the exact build MockBukkit was made against). Dependabot can't tell them apart and proposed bumping the MockBukkit one past MockBukkit's own build (PR #6). Taken: Dependabot ignores `io.papermc.paper:paper-api`; `paper` changes when the supported drops change, and `paper-mockbukkit` is bumped by hand with each MockBukkit update. The spec's `dependabot.yml` gains that `ignore` entry.

## M1

9. **Where the planned end lives.** The spec lists it both in `seasons/<n>.yml` (command-editable, `schedule.plannedEnd`) and in the season state (`data/season.json`). Taken: `seasons/<n>.yml` is the source of truth, so `/season schedule end` and a hand edit plus `/season reload` both work. `season.json` keeps a copy, the time it was set and the reminders already sent; when a reload brings a different planned end, the reminders start over as if it had just been scheduled.
10. **Reminders already past, and "at least a week later".** Taken: a reminder whose threshold had already passed when the planned end was set is never sent (setting the end 5 minutes away sends no "10 minutes" reminder). If the server was down through several thresholds, only the nearest one is sent. Changing the planned end starts the reminders over. "At least a week later" describes TheRanch's practice, so a closer planned end is accepted with a warning, not refused.
11. **A restart during the end countdown.** Taken: a countdown that hadn't reached archiving is cancelled by a restart. The season stays Active, the server log and online admins are told, and `/season status` shows when it was interrupted until the next `/season end`. Ending is manual by design, so nothing ends by surprise after a crash. With `schedule.autoEnd: true` the countdown starts 5 minutes after startup, as the spec says. If archiving had already started, the end sequence runs again after journal recovery (archiving is idempotent per player and season) and the season reaches Intermission; offline players catch up at login.
12. **The stage `/season init` records.** The season in progress began before Seasons was installed, so there is no old world to lock. Taken: Active, Open stage.
13. **Line numbers for config errors.** Taken: a YAML syntax error is reported with file, line, column and message, which is what A40 checks. A value that parses but fails validation is reported with file, key path and message, because Configurate's nodes don't keep line numbers.
14. **Discord in M1.** A1 (an M1 scenario) needs reminders "in chat and on Discord", while "Discord webhooks" are listed under M4. Taken: M1 sends reminders through a small webhook sender in `integrations/`; M4 adds season end, awards, firsts, the dragon slayer, launch, Homecoming and the admin webhook to the same sender. Every post sets `allowed_mentions` to nothing, so no text can ping `@everyone`.
15. **Webhooks must be https, in tests too.** Taken: the validation rule stands. The scenario servers trust a self-signed certificate made at test time by `keytool`, and the bot runner hosts an https webhook receiver with it.
16. **A JSON library.** Data files are JSON, but the spec's dependency list has none. Taken: `configurate-gson`, recorded in `docs/adr/0002-configurate-gson.md`.
17. **An invalid config at startup.** Reload keeps the previous config, but at startup there is no previous one. Taken: a broken `config.yml` or `messages.yml` falls back to the bundled defaults (which are the conservative settings, such as `autoEnd: false`), and the problem is logged and shown in `/season status`. A broken season file means no planned end until it is fixed and reloaded.
18. **Scenario isolation.** Scenarios change persistent state (a season can be initialised once, an ended season stays ended), so each scenario file now runs on its own freshly wiped server, and a scenario can ask for several sessions with a server restart between them. Each scenario costs one server start.

## M1 part 2

19. **Cursor and crafting items at archive time.** As the spec says, they go back into the inventory first and the menu is closed. Items that don't fit are never dropped: they stay on the cursor or grid, and the menu stays open (closing it would drop them), until step 4 clears them with the rest. They are archived as the overflow, shown on their own page of the archive view, and checked again before the clear. Because nothing leaves the player before step 4, a crash or a failed write never loses them (the game itself doesn't save the cursor, so a hard crash before step 4 loses only what vanilla would). Unarchive puts the overflow into free slots, and any that don't fit go to the displaced-items file (23).
20. **Players from before Seasons was installed.** A player with no record whose player file existed before is taken to have played the season `/season init` recorded, and is archived into it once it ends. Their baseline is zero, so their archive's statistics are lifetime totals. Nobody gets a record before `/season init`.
21. **Advancements without a display.** Only advancements under `recipes/` count as recipe unlocks and are kept (with `recipes: keep`). Every other advancement, including ones without a display such as a datapack's, is archived and revoked. TheRanch runs no datapacks, so revoking those has no side effects there; a server whose datapacks rely on hidden advancements can set `resets.advancements: keep`.
22. **`/season archive` targets.** Online players only, into the season catch-up would choose (the last finished season they played that isn't archived). It never archives into the season in play, so running it mid-season or twice changes nothing.
23. **Unarchive needs the player online and empty-handed.** With `--force`, whatever the player carries is written to `archives/s<n>/<uuid>.displaced-<ms>.dat` in the same NBT archive format, so a curator can recover it later (curation is M4), and the unarchive is audited. Nothing is destroyed.
24. **New journal kinds.** `UNARCHIVE_STARTED` and `UNARCHIVE_DONE` join the data model's list, so a crash part-way through an unarchive is finished at the player's next login like an archive.
25. **Joins during the Archiving phase** are archived at login, as during the Intermission.
26. **The deaths objective has no scoreboard port.** The spec's port table has none, so `Players#deathsObjective` creates it.
27. **A13 and A14 in M1.** The M1 scenario list includes A13 (firsts) and A14 (season card), but the milestone list puts firsts and season cards in M4. Taken: they move to M4, and M1 is done without them. The data A14 needs (statistics minus the baseline, the furthest block, the advancement count) is already captured in each archive. Owner to confirm. **Decided by the owner (PR #10): rejected.** A13 and A14 stay in M1, built as M1 part 4 (see 55 to 60): firsts are a race from launch day, so tracking has to run when Season 3 launches, and the card lists the firsts. The dragon slayer first stays with the egg in M4.
28. **The tripwire in M1.** The milestone list puts the tripwire in M2, but A9 is an M1 scenario and the archive view ships now. Taken: a minimal tripwire in this part (checks on pickup, on items appearing in the world and on menu close, a 30 s sweep of online players, deletion and an audit entry). Reporting hits to the admin webhook waits for M4; until then each hit is logged as a warning.
29. **Launch celebration.** The spec's launch has a title, a sound and fireworks, and they all ship. A firework with effects can damage whoever stands next to it, so each launch firework carries a `seasons:celebration` tag and any damage it would do is cancelled, for players and every other entity. (An earlier draft dropped the fireworks; the PR #9 review restored them.)
30. **Restored advancements' times.** `/season unarchive` re-awards the archived criteria quietly (no chat announcement), but Paper's API can't set the time a criterion was awarded, so restored criteria carry the time of the unarchive; the archive file keeps the originals.
31. **Unarchive and later seasons.** "For mistakes only" is read as: unarchiving gives the items back and never leads to them being archived again by themselves. Login catch-up never archives into a season earlier than the latest one the player has entered, so unarchiving Season 2 during Season 3 doesn't send their Season 3 inventory into a Season 2 archive. Unarchiving an older season while a later one is archived leaves `archivedThrough` alone, so the later archive is never redone. An admin can still `/season archive` a player whose unarchived season is the one that just ended.
32. **Archive files are never overwritten.** If an archive file for that player and season already exists when archiving writes one (after an unarchive, or a crash before `ARCHIVE_STARTED`), the old file is moved aside as `<uuid>.superseded-<ms>.dat` first, like the displaced and unarchived files.
33. **Launch waits for every online player to be archived.** `/season launch` is refused while anyone online played the season that ended and isn't archived into it, or has an archive or unarchive open in the journal. Otherwise a failed archive would carry its items into the new season. The fix is `/season archive` or `/season reprocess`, or the player logging out (they then catch up at their next login).
34. **Held at login.** A player is held, as during archiving, from the moment they join until recovery and login catch-up have run, usually a tick or two, so they can't drop or hand over items before the checks.
35. **Hidden advancements.** The visible total counts advancements with a display that isn't hidden, as the advancement screen does, and so does the completed count. Hidden ones are still archived and revoked like the rest.
36. **Who owns a cell is kept in the gallery file only.** The data model lists cell owners in the gallery files; the player record doesn't copy them, so there is one place to change and nothing to fall out of step. `/hof gallery info` and `/hof cell info` show them.
37. **Game modes in the Hall.** Inside a gallery's bounds, players are in adventure mode except an owner in their own cell while they may decorate it (survival). Leaving the Hall puts back survival only for players Seasons switched. Creative and spectator players, and holders of `seasons.hof.bypass`, are left alone. **Amended by 252:** creative players build in the Hall.
38. **`claim` and `ordered` before M5.** `/hof claim` isn't built yet, so `claim` behaves as `manual` (admins assign) until it is. `ordered` hands out cells in gallery order to players sorted by name. **Amended by 167:** `claim` is built.
39. **No broadcast when the window opens.** Each player is told their own cell ("Your Hall of Fame cell for Season 2 is c1 in season-2."), as the spec says; there is no extra chat broadcast.
40. **The lock.** `decorating.lockAtEnd: true` closes the window at the end of the countdown, before anyone is archived. An owner archived then (or archived later in the Intermission) gets `decorating.afterArchive` once, from their archive; it is kept in `season.json`, so it survives a restart. `/season decorate close` ends every cell's time at once, and launch ends it too (the next season's state starts with no window).
41. **Swap requests live in memory.** A restart within the 60 seconds drops a waiting request; the player asks again.
42. **An imported double chest** is one container and one archive anchor, at the half its slots start in; the other half is a protected Hall block like any other. Its sixth row doesn't fit beside the page buttons, so it continues on a page of its own.
43. **The imported figure's head.** The owner's player head stays in the record (and on the gear page of the archive view), but the mannequin doesn't wear it: the mannequin wears that head's skin instead, as the spec's table says.
44. **Imported records** have an empty inventory, no advancements or statistics, and ender chest policy `keep`; the player record is untouched (`archivedThrough` stays as it was), since Season 1 predates Seasons. Sign text goes into the record for the season card (M4).
45. **The import saves the world.** A crash after a cell is emptied but before the world is saved would bring the items back into the cell while the record also holds them. So the import saves the dimension right after emptying a cell, before writing `IMPORT_DONE`, and the undo saves it after putting items back and before setting the record aside. Recovery empties whatever still matches the record.
46. **An interrupted undo is left to an admin.** Recovery reports it rather than guessing which items went back; running `/hof import undo` again puts back only what is missing.
47. **Dry-run counts.** A cell already imported is listed as "already imported" and counted as neither ready nor flagged; a cell whose owner already has a Season 1 record is flagged. An item frame's item becomes a trophy anchor at the frame's block.
48. **Display copies are tagged.** The items figures wear and trophies show are copies tagged `seasons:archived`, like the archive view's, so the tripwire deletes any that ever turn up anywhere else.

### PR #10 review fixes

49. **A cell that changes during an import.** The import scans the cells first and empties them later, so a chest emptied, or a stand or frame removed, in between would leave its items both in the record and with whoever took them. Taken: a fresh import stops at that cell, sets its record aside, audits it and changes nothing there. Only recovery after a crash treats an empty source as already emptied (as archiving does for a cleared inventory). If emptying a source fails part-way, the journal entry stays open and the next start finishes the cell.
50. **Unarchiving an imported record.** `/season unarchive` would give back nothing (an imported record has no inventory) and set the record aside where `/hof import undo` can't find it. Taken: it is refused and points to `/hof import undo`.
51. **Game modes in the Hall, amending 37.** Seasons remembers in the player record (`hallAdventure`) that it switched a player from survival to adventure, so a restart doesn't strand them in adventure, and leaving the Hall puts back survival only then. A player already in adventure for another reason stays in adventure, and an owner is put in survival to decorate only if Seasons put them in adventure. Players without a record (before `/season init`) are remembered in memory only. **Amended by 245:** leaving freely restores survival through the same mark.
52. **Gallery files Seasons writes.** A double chest's archive anchor is the half its slots start in if that half is in the cell, else the half that is. Before writing anything, the import checks that the gallery it will save keeps every rule, and stops at that cell if not. **Decided by the owner (PR #10):** a broken gallery file at startup is left out and nothing else is; see 61.
53. **A6 and the zone lock.** A6's "locks the old-world zones" needs the zones, which are M3. Taken: M1 does everything else in A6, and the lock is checked again when zones land in M3. **Confirmed by the owner (PR #10).** A6 runs again in full once zones land.
54. **`/season config get|set`.** It is one of the `seasons.admin.config` commands with zones and markers, and no acceptance scenario covers it. Taken: it ships with those commands in M3. **Confirmed by the owner (PR #10).**

## M1 part 4: season firsts and the season card

55. **What counts as a first.** Each advancement that has a display (so no recipe unlocks), the Nether and the End (arriving in the dimension), and carrying a diamond, an elytra or an item on `firsts.rareItems`. "First diamond" is read as the first to carry one, like the rare items, since a diamond can come from a chest as well as ore. Only while the season is Active, and not for a player held by archiving, unarchiving or login catch-up, so `/season unarchive` giving advancements back never makes a first. The dragon slayer comes with M4.
56. **Where firsts are kept.** In `season.json`, as the data model says, for every season (key, label, player, name, time): after launch the next season starts with none of its own, and earlier seasons' cards still read theirs. The archive record doesn't copy them yet; Seasons Web (M7) can read them from the season state.
57. **The inventory sweep for firsts** runs every 10 seconds, its own task beside the tripwire's 30-second one, so a rare item is noticed well within the 30 seconds the spec allows.
58. **The season card is a book, never an item.** Right-clicking a cell's plaque anchor opens it with `Player#openBook`, so nothing is given, placed on a lectern or left behind. The plaque's text display keeps the name, season and advancement count, and says to right-click for the card. A card for an imported Season 1 cell shows "Season 1 · imported" and its signs, with no statistics.
59. **What the highlights add up.** Play time from `minecraft:play_time`; travelled from walking (on land, on and under water), sprinting, swimming, flying, elytra, boats, minecarts and horses; diamonds mined from diamond ore and deepslate diamond ore; blocks placed from every block item used; blocks mined from every block mined. The four block counts aren't General-tab statistics, so Seasons takes them with the baseline and at archive time under `seasons:` ids, and only the General tab is listed on the card's further pages. Each statistic there is named by the client in its own language.
60. **Statistic ids.** Bukkit still names some statistics by their pre-1.13 names (`play_one_minute`, `chest_opened`). The Paper adapter reports the game's own ids (`play_time`, `open_chest`), which the stats files and the client's translations use. Baselines taken before this change used Bukkit's names; no server ran those builds, so nothing migrates them.
61. **A broken gallery file at startup**, amending 17 and 52. Seasons loads every other file and leaves out only the broken gallery, or a gallery that breaks a rule with another. `/season status` shows the problem, and admins are told a few seconds after they join. `/season end` (and `schedule.autoEnd`) and `/season launch` are refused until it is fixed and `/season reload` succeeds, since the end would otherwise archive that gallery's players without cells; `/hof gallery create` refuses its id, so the broken file isn't written over. A reload still swaps every file in or none, as the spec says.


## M2 part 1: visiting the Hall

62. **The Hall entry.** Plain `/hof` lands at the entry of the newest season gallery that has one. With none, `/hof` is refused ("The Hall of Fame has no entry yet."). Before `/season init` it is refused too, since there is no season and nobody has a record to keep a saved spot in. **Superseded by 244:** plain `/hof` lands at the Hall spawn.
63. **`/hof <season>` or `/hof <player>`.** A whole number names a season (that season's gallery entry); anything else is a player, online or by the last name in their record, and lands at their newest cell's entry anchor (else in front of its figure). A player whose name is all digits can't be visited by name.
64. **`/hof` from inside the Hall** moves the player within it with no entry checks except the rate limit, and keeps the saved spot they first left from. **See 244:** unchanged, with the Hall spawn as the destination.
65. **Monsters nearby** uses vanilla's sleeping box (8 blocks across, 5 up and down) around the player, counting any hostile mob (`Enemy`) except a zombified piglin that isn't angry. Paper has no "prevents rest" API, so this is the closest public reading.
66. **Hazards and movement.** Being on fire counts as a hazard (the teleport puts fire out, which would make `/hof` an escape button), and being in water at all counts as swimming. "On the ground" is worked out from the blocks under the player's feet, not from what the client says. The order is: rate limit, cooldown, bed, hazards, movement, monsters, recent damage; the first that fails is the one named, so standing in lava says "lava", not "hurt". The new keys `onGround`, `noHazards`, `cooldown` (0s) and `rateLimit` (5s) join `hof.entry`; missing keys take the bundled defaults, so `schema-version` stays 1.
67. **Entering the Hall another way.** Walking in after Homecoming, or another plugin's teleport, saves the spot they came from as their return point, so leaving takes them back there. Pearl and chorus teleports into, within or out of the Hall are refused; one that would have carried them out returns them to their saved spot instead. Walking or riding in on a mount is refused at the edge. **Amended by 245.**
68. **`/hof leave` with no saved spot** is refused outside the Intermission, since it would otherwise be a free teleport to a bed or the spawn. During the Intermission everyone stays in the Hall. **Amended by 246:** with no saved spot, `/hof leave` goes to the season spawn.
69. **Teleports out of the Hall.** Any teleport that isn't Seasons' own (admin `/tp`, other plugins) counts as leaving and returns the player to their saved spot. Admins who need to move visitors use `seasons.hof.bypass`. Seasons' own moves (launch, archiving to a cell) never count. **Amended by 245:** with `hof.sealed` other than `always`, a teleport out just leaves.
70. **The saved spot is dropped** when a player is archived (they go to their cell) and when they enter a new season, so nobody returns into a season that ended. It is written to the player record at once, before the teleport, not coalesced.
71. **Death in the Hall** isn't handled specially: respawning outside the Hall counts as leaving, so the player is sent to their saved spot. Hall damage rules come with M2 part 2.
72. **Scenario stand-ins for movement.** Mineflayer still trails 26.3 (ADR 0001), so A27's walking, pushing and falling are moves the test plugin makes as the client would (`/scenario move` fires `PlayerMoveEvent`, then puts the player there); the pearl is a real one. Sneak-clicking a bed, using items, dropping and sitting also go through the test plugin (ADR 0003).
73. **A spot return safety would turn down is turned down at `/hof`** (review of #11). Return safety checks more than the entry checks do (magma underfoot, monsters within `hof.returnSafety.hostileRadius` rather than vanilla's sleeping box), and an unsafe saved spot sends the player to their bed or the spawn. So `/hof` also runs the return checks on the spot the player leaves from and refuses with the reason ("This spot isn't safe to come back to (magma)."); otherwise a bed and a magma block would make `/hof` then `/hof leave` a teleport home from anywhere. It comes after the other checks, so their messages are unchanged, and it isn't a setting, since turning it off would reopen that teleport. Return safety now finds the floor just under the feet, so a spot on a slab, a bed or farmland counts as safe.
74. **`/hof leave` works only inside the Hall**, amending 68. A saved spot can be left over outside it (an entry teleport another plugin cancelled, a crash between the teleport back and forgetting the spot); from outside, `/hof leave` would be a teleport from anywhere. A failed entry teleport drops the spot it just saved, and the sweep drops the saved spot of a player it first sees outside the Hall after they join, which covers the crash. Walking back in keeps a saved spot they already have, so stepping out and straight back can't swap it for a spot just outside the Hall. **Amended by 245.**
75. **Bypass holders leaving the Hall** drop their saved spot, since nothing sends them back.

## M2 part 2: protecting the Hall

76. **What visitors may use.** Deny by default: in the Hall a visitor can open a container (as a view-only copy), use anchors and plaques, step on exit plates, sit on cushions, and open wooden doors, trapdoors and fence gates, since "walk into any cell" needs a door to open. Everything else is refused: levers, buttons, beds, workstations, lecterns, signs, cauldrons, composters, note blocks, item frames, armour stands and other entities. A refused click on a block that does something (`Material#isInteractable`) says so and is audited; a click on a plain wall is refused quietly. **Amended by 248 and 252:** links work; builders use anything.
77. **What an owner may do while decorating their own cell.** Place and break blocks, place, use and break item frames, glow item frames, paintings, armour stands and cushions, use any block, fill and empty water buckets, light candles and campfires, and open their own containers for real. A container with something in it can't be broken ("Take everything out of it first"), so nothing spills. The owner may pick up items in their own cell while they may decorate it, so what they break comes back to them; everyone else still picks up nothing in the Hall.
78. **Liquids and pistons.** Lava can't be poured anywhere in the Hall. Water flows, and pistons move blocks, only within one cell whose owner may still decorate it; nothing flows or is pushed across a cell's edge, the Hall's edge, or inside a locked cell.
79. **Damage in the Hall**, which question 71 left open. Nothing in the Hall takes damage, players included, except from `/kill` and the void. An entity hit by a player (an owner breaking their own armour stand) is decided by the Hall's rules instead.
80. **Access modes `bounds` and `gate`** aren't built yet. Rather than run as `open`, a config naming them is refused on load and reload with a message saying so. **Lifted on `m3-finish`** (168, 169).
81. **A decorated pot** has no menu to open. Right-clicking one in the Hall, unless you are its decorating owner, puts nothing in and opens a view-only copy of its one slot instead.
82. **Auditing blocked interactions.** Each refused change or use in the Hall is written to the audit log (`hall-blocked`, the player, the cell or `hall`, `denied`, what and where). The same player doing the same thing in the same place within 10 seconds is counted, not repeated: one entry when it starts and one with the count when it stops. Changes by holders of `seasons.hof.bypass` are allowed and audited the same way (`hall-bypass`). **Amended by 252:** creative builders are audited as bypass holders are.
83. **Reconciliation isn't journalled.** The journal covers items moving; displays only show tagged copies, and a repair is idempotent, so a crash mid-repair is put right by the next pass. Each repair is audited. Reconciliation runs when a chunk's entities load (it never loads chunks itself), every 5 minutes for cells whose chunks are loaded, and on `/hof reconcile`, which loads them. The work is queued and done on the server thread within about 1 ms a tick.
84. **Containers not on `cells.containers`** can't be placed in the Hall, even by a decorating owner, and neither can an ender chest; one already there (built by an admin) opens for nobody but bypass holders. Colours count as the same container: `shulker_box` covers every coloured shulker box. **Amended by 252:** builders may place and open ender chests.
85. **Cushions** are placed through `EntityPlaceEvent` and broken through Paper's `EntityBreakByEntityEvent`, both present in the 26.3 API.
86. **The tripwire on chunk load.** When a chunk's entities load, item frames, armour stands and items on the ground are checked for archived copies; when a chunk in the Hall loads, so are its containers. A hopper moving an archived copy anywhere is stopped and the copy deleted.
87. **After their archive an owner takes nothing out of their cell** (review of #12, amending 77). The spec says cells lock at the end and containers are view-only from then on ("a stash gains nothing"), and also that owners get `decorating.afterArchive` to arrange their cell (A46). Both hold: in that time the owner still places and breaks blocks, places entities and turns item frames, but their containers open as view-only copies, a block they break drops nothing, they pick nothing up, and hitting or using an armour stand or hitting a frame is refused. Before the end, while the decorating window is open, 77 stands: they open their containers for real and pick up what they break. Otherwise a chest filled before the end, or blocks broken after it, would go with them to the new spawn.
88. **A double chest never reaches across a cell's edge or the Hall's** (review of #12). A double chest's inventory is both halves, so a chest placed outside the Hall, or in a neighbouring cell, beside a cell's chest would open the cell's items. A chest that would join another is refused unless both halves are in one cell its owner may decorate (outside the Hall nothing is decided). One already there, however it came, counts as in the Hall if either half is: it opens as a copy unless the opener may take things out of the one cell holding both halves, and no hopper moves items through it.
89. **Reconciliation finds a cell's displays anywhere in its chunks** (review of #12). A figure pushed out of its cell's bounds is removed when its cell is reconciled, as well as drawn again; one found in a chunk none of its cell's bounds touch is removed when that chunk's entities load. A display of a cell that isn't known, as when a gallery file is left out, is kept until it is.

## M3 part 1: zones and Homecoming

90. **Which season file the zone commands edit.** The runbook draws the old-world zones during Season 2, before launch, so they must go in the next season's file, as `/season spawn set` does; but a zone drawn during the Frontier stage must lock at once. Taken: `/season zone` edits the season being played while its old world is locked (Active or counting down, Frontier stage), and the next season's file otherwise (Season 2 under `/season init`, after Homecoming, the Intermission).
91. **When zones are in force.** A season's zones come from its own file and are in force only while that season is played (Active, or the end countdown), so nothing is enforced before launch, and launch locks them (A6). In the Frontier stage each zone is locked, unless unlocked on its own (question 100); Homecoming switches every zone to its `afterUnlock` mode, those unlocked or locked again on their own included (amended in review, question 109), and a zone locked again after Homecoming stays locked. Archiving and the Intermission enforce nothing: players are in the Hall.
92. **Drawing zones before the wand.** `box` takes both corners as coordinates until the wand comes in M5; with none it says so. `cylinder <radius>` is centred on the block the admin stands on, in their dimension, with `--max-y` and also `--min-y`. A box from the console is in the overworld; a cylinder needs a player.
93. **Shapes `outside`, `y-above` and `y-below`** aren't built in part 1. Rather than ignore them, a season file naming one is refused on load and reload with a message saying so, as access modes were (question 80). **Lifted in M3 part 4** (154): all three are built.
94. **Entry is checked on every move as well as by the sweep.** The spec's sweep (every 10 ticks, a tenth of the players each tick) stays the backstop, but a player's own move into a blocked zone, and a vehicle's with a player in it, is refused the moment the block changes: the move is cancelled, and they are dismounted, stopped and shown the title and action bar. Waiting up to half a second would let someone step in, open a chest and step out.
95. **The last valid position** is where the sweep or a move last saw the player outside every blocked zone. A player found inside goes back there, or to the season spawn if there is no such place or it is now inside a blocked zone (as when a zone is drawn around them or locked again with them in it), and is told why in chat.
96. **A spawn inside a zone** is a warning on reload, validate and startup, not a problem: the file loads, so an unrelated reload isn't blocked. `/season zone add` refuses a zone around the spawn and `/season spawn set` refuses a spawn inside a zone; `/season end --dry-run` names the zone (A41); `/season launch` and its dry run are refused, with a reason that doesn't name the zone (refusal messages only carry season numbers) and points at the dry run.
97. **Block mode inside the zone.** Nothing inside burns, is broken by an explosion (blocks, item frames, paintings, armour stands, animals), or is primed (TNT), even when the cause is inside too, as with lightning; endermen take nothing. Growth, liquids, pistons, hoppers and redstone wholly inside keep running, so farms in old bases still work at Homecoming.
98. **No-build mode, the strict reading.** Breaking crops is breaking, so "use a farm" means its machines (buttons, levers, doors) and their chests, and trading. Hitting an item frame, painting, armour stand or cushion is refused, so items in frames aren't taken by hitting them; other entities can be hit and used. Bone meal, stripping, waxing and lighting are building. The edge rule applies to no-build zones too: nothing flows, is pushed or is moved by a hopper across their edge.
99. **Announce mode.** Once per player, per zone, per day in the server's time zone, kept in memory, so a restart may announce someone again the same day. Posting to Discord as well is `zones.announceToDiscord` in config.yml, off by default.
100. **One zone at a time.** `/season unlock <zone>` and `/season lock <zone>` are built in part 1, since the spec says the manual command always works whatever a zone's condition. What they set is kept in `season.json` for the season and cleared at launch. Unlocking broadcasts "The <zone> is open!" and posts it to Discord; locking again isn't announced. No zone may be called `homecoming`.
101. **Unlock conditions** are checked once a second and at startup, so a date that passed while the server was down unlocks then. Homecoming unlocks every zone whatever its own condition ("every old-world zone switches to its afterUnlock mode"); a zone whose own condition comes true before Homecoming unlocks alone. `after` counts from the season's launch.
102. **Milestones.** `dragonKilled` holds once any ender dragon dies while the season is played; `playersReachedEnd` counts the different players who arrived in the End this season. Both are kept in `season.json`.
103. **What zones don't stop.** Redstone signals across an edge, and mobs and items wandering out of a zone by themselves (portals they can't use). Everything else the spec lists is stopped. (Amended in review: picking up an item lying just inside a blocked zone's edge is stopped after all, question 110.)
104. **Auditing.** Refused interactions with a zone are written as `zone-blocked`, and bypass holders' as `zone-bypass`, a repeat within 10 seconds counted as in question 82.
105. **Homecoming and the journal.** Like launch, Homecoming moves no items, so it has no journal kind: `season.json` (Open, `homecomingAt`) is saved first and the titles, fireworks, broadcast and Discord post follow only once it is on disk. A crash after the save leaves the zones unlocked and doesn't repeat the fanfare.
106. **`/season zone list`** shows the zones in force (the season being played) as well as those of the season the commands edit, when the two differ, each with the mode in force now; zones not yet in force show off.
107. **A player who logs in inside a blocked zone** is found by the sweep within half a second of joining, after any archive catch-up (players held by it are skipped), not by the join event; one who respawns inside is found the same way.
108. **Vehicles.** A boat's or minecart's move with a player in it is the player's move: refused, both go back where they came from and the player is dismounted. A ridden animal that isn't a vehicle to the server is caught by the sweep.
109. **Homecoming opens every zone** (review of #13, amending 91). The spec says every old-world zone switches to its afterUnlock mode in the same tick, so Homecoming clears what `/season unlock <zone>`, `/season lock <zone>` and zones' own conditions set before it. The milestones (the dragon's death, players who reached the End) are kept. After Homecoming, `/season lock <zone>` locks one zone again, as the spec's command table allows.
110. **Taking across the edge** (review of #13). A pickup does carry a position: the item's. A player can't pick up an item lying in a blocked zone, as from just outside its edge, unless they hold the bypass; the refusal is quiet, since the game asks every tick, and audited as `zone-blocked` with repeats counted. Reeling in an entity or item with a fishing rod is using it, so it is refused in a blocked zone and allowed in a no-build one. A player's hit on any entity, by hand or by projectile, is decided wherever it is, not only in the Hall: in a blocked zone every hit from outside is refused, and in a no-build zone hits on item frames, paintings, armour stands and cushions are refused, so a frame's item isn't knocked out and a stand's gear isn't dropped. Minecarts and boats are decided through their own damage event, and inside a blocked or no-build zone nothing but a player breaks them.
111. **Auditing zones** (review of #13, extending 104). Besides refused and bypassed interactions: every refused entry (walking or riding in, a teleport, a portal trip and its arrival, a new portal, a player the sweep finds inside) as `zone-blocked`, repeats counted; Homecoming (`homecoming`, by the admin who ran it or by Seasons when its condition came true); one zone unlocked or locked again (`zone-unlock`, `zone-lock`); and every `/season zone add`, `mode`, `after` and `remove` as `config`, with the path in the season file, the old value, the new value and who.
112. **Zone dimensions** (review of #13). The spec's validation rule "every dimension id exists" applies to zones: a season file with a zone in a dimension the server doesn't have is refused on load and reload, since the zone would lock nothing.
113. **Portal trips** (review of #13). On Paper 26.3 a nether portal trip fires `PlayerPortalEvent` before the game looks for a portal at the other end, then teleports the player to the portal it found with the `NETHER_PORTAL` cause, so a trip whose exit is an old portal inside a blocked zone is refused at that teleport (a30-real-portal, a real portal trip). As a backstop, a player who arrives in a dimension inside a blocked zone is put back where they last stood outside, at once rather than at the next sweep.

## Faster scenario suite

114. **Seasons' sweeps and the scenario clock.** Seasons' sweeps (the tripwire every 30 s, season firsts every 10 s, the Hall, visits, zones, reconciliation, the season tick) run on the server's scheduler, not on Seasons' clock, so moving the clock alone would leave them to come round in real time. On scenario servers only, Seasons' scheduler is wrapped so that moving the clock runs every delayed task that came due and every repeating task whose period passed, once each however many periods were skipped, as the next run would have. Real servers use the platform's scheduler unwrapped.
115. **The Paper jar for shards.** The shards boot Paper themselves, several at once, which run-paper's `RunServer` can't (Gradle won't run tasks of one project side by side without the configuration cache), so `scenarioTest` runs each shard in a Gradle worker (`buildSrc`, plain Java on the Gradle API). The spike worked: the Paper jar and the Via jars come from run-paper's own cache through its public download services (`DownloadsAPIService.paper`, `PluginDownloadService`), so the Paper build is not pinned. Paperclip unpacks Paper once into a folder the shards share (`bundlerRepoDir`).
116. **Docs-only changes.** CI skips the scenario shards when every changed path is under `docs/`, a Markdown file at the repository root, or `LICENSE` (`.github/scripts/docs-only.sh`). An empty or unknown change runs them. The final `build` job passes a skipped shard only for that reason.
117. **Branch protection.** At this change `main` had no branch protection (the API answered 404), so no check name was required yet. The final job keeps the name `build`, the check the spec's GitHub step 2 asks for; protecting `main` with it is left to the owner.
118. **Fresh mode is sharded too.** `-PscenarioIsolation=fresh` gives every scenario a freshly wiped server of its own, as before, but runs the shards side by side, so the nightly run takes minutes rather than the old 21.
119. **What a fresh server is.** A scenario server's fresh boot removes the animals the world generated before the first scenario, so every scenario, first or not, starts without them, in fresh mode too (any scenario server can reset, and its leak check compares with that fresh boot). No scenario depends on them.
120. **Gradle's downloads in CI.** setup-gradle's cache is written only on `main`, so on a pull request every job started empty and the six jobs fetched every dependency from Maven Central at once; Central answered 429 and a shard failed. The jars job now saves Gradle's downloads (`~/.gradle/caches/modules-2` and the wrapper) under a key of the build files' hash, and the shard and final jobs restore them.
121. **Every scenario ran in CI** (review of #14). Passing shard jobs alone don't show the suite ran: a shard count that differs from the matrix, or a shard that ran nothing, would leave scenarios out with every check green. The shard jobs take the count from the matrix (`strategy.job-total`), and the final `build` job runs `:testkit:scenarioCoverage`, which fails unless every session of every scenario file has a passing result on every supported version. A full local `scenarioTest` runs it too.

## M3 part 2: the ender vault and pets

122. **When season pages can be withdrawn from.** "Withdraw-only after Homecoming" is read as: while the season being played is in its Open stage (Active, or counting down from Open). In the Frontier stage, and between seasons (archiving and the Intermission), every season page is read-only, older seasons' pages included: they are old-world storage too, and anything taken during the Intermission would be carried into the next season. The Returned page can be withdrawn from at any time, except while the player is held for archiving.
123. **Which clicks withdraw.** A left click or a shift click on an item takes the whole stack. Every other click (right, number keys, the off-hand swap, drops, drags, double-clicks, creative clones) is refused like any click in a view-only menu and moves nothing. Nothing can be put in. After each withdrawal the menu opens again on the same page, built from the vault file.
124. **The withdrawal transaction.** Per click, queued per player and with the player held throughout: save the player's file, journal `VAULT_WITHDRAW` (the vault page as its season, 0 for the Returned page, and the inventory's hash before), take the item out of the vault file with a withdrawal id, give it whole or not at all, save the player's file, then journal the new kind `VAULT_WITHDRAW_DONE`. A failed give (full inventory, or they left) puts the item back in its slot. Recovery after a crash: if the vault file never recorded the withdrawal, nothing moved; if it did and the player's saved inventory still has the hash from before, the give didn't stick and the item goes back; otherwise it was given and saved. The vault file keeps each withdrawal (page, slot, time, item) as its withdrawal history.
125. **Unarchive and the vault** (a dupe found while planning). `/season unarchive` used to restore the ender chest from the archive's copy, which after withdrawals would hand back what had already been taken out. It now restores the vault page as it is now, and removes that page before moving the archive aside, so a crash between the two can't leave a page holding what the player was just given.
126. **An empty vault.** `/vault` with nothing in any page says "Your ender vault is empty." and opens nothing. After the last withdrawal the menu still opens again, empty, so the player sees the item gone.
127. **Removal reasons.** On Paper 26.3 `EntityRemoveFromWorldEvent` with `Entity#getRemovalReason`: only `KILLED` is final, a death ("died") that drops the registration at once. Every other reason, `DISCARDED` included, only updates the last known position and leaves the registration for travel to settle, since an animal discarded can come back: a parrot landing on its owner's shoulder is discarded and returns, same id, when it hops off (review of #15; see 136). Registered pets carry a `seasons:pet` mark (their owner's id), so only they are looked at. At shutdown Seasons records where every loaded registered pet stands, since unloads after it go unheard.
128. **Telling an offline owner.** A death or removal while the owner is offline is kept in their player record (`notices`) and shown at their next login, once.
129. **Names.** A pet keeps its name tag's text, as plain text; an unnamed pet is named from its type ("Wolf", "Skeleton Horse"). A name already used by another of the owner's pets gets the lowest free number: "Wolf 2". `/pet remove` matches names ignoring case.
130. **Who can register what.** The animal the player looks at within 5 blocks (`LivingEntity#getTargetEntity`), tamed by them as the game records it. Refusals, in order: not looking at anything in reach; not a tameable animal ("A villager can't be tamed"); not tamed; tamed by someone else; already registered; carrying a chest; at `pets.maxPerPlayer`. Registration is open while a season is played (Active, or the end countdown) and closed from the end until the next launch; `/pet list` and `/pet remove` always work. With `pets.enabled: false` `/pet add` is refused.
131. **When pets travel.** A pet travels once its owner has entered a later season than the one it was registered in: right after they reach the new spawn at launch, or after their login catch-up (archived, then sent to the spawn). Each login after catch-up also tries again for pets still due, which covers an owner who left part-way or a crash. A pet registered after launch waits for the next season. Pets travel one at a time, to where the owner stands.
132. **What travel does with each pet.** Found at its last known position (the chunk loaded asynchronously with a plugin ticket, waiting up to 5 seconds for its entities) or already loaded anywhere: still the owner's, no chest, then unleashed, taken out of any vehicle and off anything riding it, `PET_TRAVELLED` journalled, and teleported. A pet carrying a chest stays behind ("animals carrying chests can't travel"), one that can't be found is reported, and one now owned by someone else stays behind; all three are dropped, since registrations clear after travel. Only if the owner leaves part-way does a pet stay registered, for their next login. A pet inside a locked zone travels like any other: Seasons moves it, so no zone check applies.
133. **`PET_TRAVELLED` needs no recovery.** Pets aren't items, and travel is safe to run twice: the registration is dropped only after the teleport, so a crash before then means the pet travels at the owner's next login. The journal entry is written before the teleport, as every world change's is.
134. **`/season status` and pets.** After a launch, while the season is played, status shows "Pets: N waiting to travel": pets registered in an earlier season and not yet brought.
135. **Scenario stand-ins** (ADR 0003). A summoned animal is tamed with `/scenario tame` (the game's own taming needs a bot to feed it), given or relieved of a chest with `/scenario chest`, and put on a lead with `/scenario leash`. "Can't be found at travel time" is staged with `/scenario forget-pet`, which takes the `seasons:pet` mark off so a later `/kill` goes unnoticed, as when a pet's chunks are regenerated. Bots are aimed from the eyes with `/execute ... anchored eyes facing entity ... run tp`, since `/tp ... facing` aims from the feet. Player bots' commands in the pet scenarios are paced, since the game kicks a player who isn't an op for chat spam.
136. **Parrots on a shoulder** (review of #15). A registered parrot discarded within 3 blocks of its online owner, in the same world, is taken to have landed on their shoulder: the registration stays, marked `onShoulder` in the player record, and nobody is told anything. If travel then can't find it in the world, it is on the owner's shoulder and already with them, so it counts as come. Its next unload clears the mark. The shoulder itself isn't read, since `HumanEntity#getShoulderEntityLeft` is deprecated and the build treats deprecations as errors.
137. **No registering across a locked edge** (review of #15). `/pet add` asks the zones about the animal as it would about any entity a player uses (`Intent.UseEntity` at the animal's position), so a pet inside a blocked zone can't be registered from outside it before Homecoming, with the zone's edge message; a holder of `seasons.zone.bypass` may, as they may reach in. Otherwise a horse left in an old base would leave the old world early, saddle and armour included. After Homecoming, or in a zone left open, it can.
138. **Unarchive holds the player first** (review of #15). `/season unarchive` takes the player's hold before reading the archive and the vault page, and keeps it to the end, so no vault withdrawal can change the page or the inventory between the read and the restore. A player already held (a withdrawal under way) gets "busy".
139. **A withdrawal that fails part-way** (review of #15). If a withdrawal stops before its item is given while the server runs on (an exception, a failed write), the item goes back in the vault at once and `VAULT_WITHDRAW_DONE` closes it, rather than waiting for recovery at the next login, which would judge it by an inventory the player has changed since. Journal recovery tells withdrawals apart by their id, the start of each entry's payload, as well as by player and page, so a later withdrawal from the same page never hides one still open.

## M3 part 3: BlueMap, spawn candidates and shared waypoints

140. **Where shared waypoints live.** The spec keeps markers "in Seasons' data" but names no file for them. Taken: `<world>/seasons/markers.yml`, a command-editable file like the season and gallery files, in the world folder so a world backup carries it. It is read and validated with every other file (a set or name that doesn't make sense, two names that differ only in case, a position that isn't three numbers, or a dimension the server doesn't have is a problem), written with backups, and a hand edit takes effect on `/season reload`. The map shows only what Seasons' files hold, so BlueMap's own files never matter.
141. **What `<set>` is.** Each set (`megaprojects`, `hubs`) is a marker set of its own on BlueMap, beside Seasons' own `Seasons` set, so players can switch them on and off separately; its label is its id. `/season marker remove` takes the set and the name, as add does. A name is the rest of the line, 1 to 64 characters, plain text (never formatting, and escaped wherever BlueMap would read HTML), and names in a set are told apart ignoring case. There is no `/season marker list`, since the spec lists add and remove only; BlueMap and `markers.yml` show them.
142. **Which spawns are shown.** "Season spawn points" are the spawns of seasons that have launched: the season being played (or just ended) and every earlier one with a spawn in its file. The next season's spawn appears at its launch, not when it is set, so `/season spawn set` at a spot nobody voted on reveals nothing early. "Spawn candidates before launch" are the next season's candidates, shown until it launches; the one chosen stays shown as a candidate until then. Candidates stay in the season's file afterwards, as the spec's example file shows.
143. **Which zones are shown.** The map mirrors what is enforced: each zone in force, styled by its mode now. Locked (`block`) and no-build zones are areas as the spec says; an `announce` zone is shown too, as its own style, since it is locked until it unlocks; a zone that is `off` isn't shown. So nothing is shown before launch or between seasons (no zone is in force; the next season's zones appear at launch), and Homecoming replaces locked areas with no-build ones, or removes them, in the same second the zones change. Areas are extruded between the zone's y limits, or the dimension's build heights where it has none; the Hall's galleries and the zone's own exemptions are cut out of them. Map Link does bring these areas onto Xaero's maps: it reads BlueMap's `shape` and `extrude` markers as areas, flat (it reads no heights), holes included, and drops any area larger than its `maxChunkArea` (164; [thebuildcraft/MapLink at 595f7f4](https://github.com/thebuildcraft/MapLink/tree/595f7f4cc24bfc55f332f47da149c90737216bca), `BlueMapConnection`, `BlueMapMarkerSet`). **Decided.**
144. **The Hall and the museum.** One point for the Hall where plain `/hof` lands (the newest season gallery's entry, else the middle of its floor), and one per museum gallery (its entry, else the middle of its floor).
145. **Candidates stay out of zones, as the spawn does** (96). `/season spawn candidate add` refuses a spot inside one of the next season's zones, and `/season zone add` refuses a zone around a candidate in the file it edits, as it does around the spawn; the remedy is to remove the candidate. A hand edit that puts a candidate inside a zone loads with a warning. A candidate (and a waypoint) in a dimension the server doesn't have is a problem on load, by the validation rule that every dimension id exists; the spawn's dimension is still checked at launch, as before.
146. **The 24,000-block rule.** It applies to overworld spawns, since strongholds are an overworld thing: a spawn whose block's middle is more than 24,000 blocks from 0, 0 across x and z. It is a warning only: on `/season spawn set`, on `/season spawn candidate add` (a candidate may become the spawn), in the candidate list, on startup, reload and validate, and in `/season end --dry-run` (A41). Distances are measured as the furthest block's are, from the block's middle and rounded down.
147. **Publishing.** Once a second, on the server thread, Seasons checks whether the files or the season state are new objects (every reload, command edit and state change makes one), builds the model only then, and hands it to BlueMap only if it differs. A publishing thread of its own takes the latest model, resolves each dimension's BlueMap world from Paper's `World` (looked up on the server thread), and replaces Seasons' sets on every map of that world (a candidate's preview map included), leaving every other plugin's sets alone. A failure is tried again after 1, 2, 4 and 8 seconds. BlueMap drops API markers on reload and then starts its API again, which is when Seasons publishes again; when Seasons stops (or a scenario resets it) it stops listening and takes its sets down. Nothing relies on a set being hidden by default, since Map Link ignores that flag.
148. **Text on the map.** Labels come from a new `map:` section of `messages.yml` as plain text. BlueMap escapes a marker's label itself, but shows its detail as HTML, so Seasons escapes the detail (the label again).
149. **Spawn edits are audited.** `/season spawn set` now goes through the same edit path as the zone commands (`ConfigEdits`), so it is audited as a config change (`seasons/<n>.yml spawn`, old, new, who) like candidates (`spawnCandidates.<name>`) and waypoints (`markers.yml sets.<set>.<name>`).
150. **Without BlueMap, or with the wrong one.** With no BlueMap plugin Seasons never touches BlueMap's classes (they are on its classpath only when BlueMap is installed) and publishes nothing; `/season status` says so, and `/season marker add` says the waypoint shows once BlueMap is installed. A BlueMap whose API doesn't link logs a warning and publishes nothing.
151. **Testing against a real BlueMap** (ADR 0004). One scenario, `m3-bluemap`, runs on a server of its own with BlueMap 5.29, set to download the game's client jar (it starts its API only with it) and to run without its web server. Every other scenario server has no BlueMap.
152. **A command edit that doesn't take is put back** (review of #16). `ConfigEdits` wrote the file, then loaded every file, and left the file changed when the load failed: the admin heard "wasn't saved", nothing was audited, and the change went live at the next successful reload. Worse, a waypoint added by command beside a hand edit not yet reloaded (`tower` by hand, `Tower` by command), or two admins adding the same name at once, could leave a `markers.yml` the load refuses, which stopped every later reload and, at the next start, every other file (153). Taken: on the writer thread, the file is read before the edit and, if the edit or the load fails, put back as it was (or removed, if there was none) before the writer takes the next edit, so a command edit is on disk only while it is in force. The backup the edit kept is of that same content. The reason the admin hears is the first problem worded as `/season reload` words it. This holds for the zone, spawn and marker commands alike.
153. **A broken `markers.yml` at startup is left out** (review of #16), amending 17 and 61. A `markers.yml` with a problem took every file down with it at startup, the season files included, so after a restart no zone was in force and the old world was open before Homecoming. Taken: like a broken gallery file, it is left out at startup and nothing else is. No shared waypoints are shown, `/season status` shows the problem, admins hear about it a few seconds after joining, and `/season marker add|remove` refuse until it is fixed and `/season reload` succeeds. A reload still swaps every file in or none, so it fails until then. Unlike a broken gallery, it doesn't hold `/season end` or `/season launch`: waypoints play no part in a rollover.

## M3 part 4: the outside and height shapes, and /season config get|set

154. **The `outside` shape is a footprint** (lifting 93). "Outside of a circle or box" is read across x and z: an `outside` zone holds every column beyond its circle or box, at every height, and has no y limits of its own (`y-above` and `y-below` are for heights). In a season file it is `shape: { outside: { circle: { center: [x, z], radius: r } } }` or `{ outside: { box: { min: [x, z], max: [x, z] } } }`. A circle counts blocks as the cylinder does (a block is inside when its middle is within the radius), so `outside circle r` holds exactly the blocks `cylinder r` with the same centre leaves out. A box holds both its corners, so its outside starts one block past them. Season files naming `outside`, `y-above` or `y-below` are no longer refused.
155. **`y-above` and `y-below` include their y**, as `minY` and `maxY` do: `y-above: 128` holds y 128 and up, `y-below: 127` holds 127 and down, so the nether roof rule can be written either way. Both cover the whole dimension across x and z. A y beyond the dimension's build heights isn't refused: it holds no block, or every block, and then the spawn check refuses or warns.
156. **Drawing them by command.** `outside circle <radius>` is centred on the block the admin stands on, as `cylinder` is, so only a player can run it; `outside box <x1> <z1> <x2> <z2>` works from the console too (in the overworld) and, with no corners, says to give them until the wand comes in M5; `y-above <y>` and `y-below <y>` are in the admin's dimension, the overworld from the console.
157. **Validation through the zone's own shape.** The spawn and candidate checks of 96 and 145 ask each zone whether it holds the spot, so they hold for every shape with no new rule: for an `outside` zone the spawn must be inside its circle or box, and for a height zone below a `y-above` and above a `y-below`. `/season zone add` refuses a zone of any shape that would hold the spawn or a candidate, `/season spawn set` and `candidate add` refuse a spot inside any zone, and a hand edit loads with a warning.
158. **Outside zones on the map.** An `outside` zone in force is shown as a ring: its circle or box as a hole, out to an outer edge `max(2 × radius, 5000)` blocks beyond it (a circle around a circle, a rectangle around a rectangle; a box's radius is half its longer side), not to the edge of the world. Map Link copies BlueMap's areas onto Xaero's maps (164), and an area reaching the world's edge could never be shown there or drawn sensibly on BlueMap; the ring shows the frontier where players meet it. The marker sits at the circle or box's centre, where its label belongs. Exemptions and Hall galleries wholly beyond the inside and wholly within the outer edge are holes too; one that crosses either edge isn't, since crossing holes break the area's shape, though the zone is enforced there all the same, and the zone beyond the outer edge is enforced but not drawn. Map Link still leaves a ring out when its bounding boxes pass `maxChunkArea` (164): with the defaults only a ring around a circle of radius up to about 600 blocks fits; a larger frontier shows on BlueMap only, and the frontier border (160) is the in-game way to see it. **Decided.**
159. **Height zones aren't on the map.** A `y-above` or `y-below` zone covers every column, so as an area it would cover the whole map: BlueMap's top-down view would show every block of the dimension as locked, and Map Link, which reads no heights and drops an area that large (164), wouldn't show it on Xaero at all. Players meet one at its height, through the title and the action bar, and `/season zone list` shows it. **Decided by Peter** (review of #18): height zones stay off the map.
160. **The frontier border.** `zones.frontierBorder` in config.yml, off by default. Only an `outside` circle whose mode now is `block` gets one: the game treats a border as a wall a player can't walk through, so a border on a zone players may cross (no-build, announce, off) would stop them where the zone doesn't, and for the same reason it is drawn around the circle, never inside it. The border is the smallest square holding the circle and the zone's own exemptions; Hall galleries are left out, since players reach them by `/hof`, not on foot, and in the Hall they are outside the square. With several such zones in a dimension, the smallest square is shown: it holds every spot inside all of them. A player sees it only in that dimension, standing inside the square, without `seasons.zone.bypass`; everyone else is given back the world's border, so nobody sees one from the wrong side. The sweep keeps each player's border right (within half a second, so after `/hof`, a portal or a teleport too); a change of dimension or a respawn, where the game sends the client the world's own border, sends the frontier's again at once (review of #18: before, a player who died and respawned inside the square kept the world's border until the zones changed); everyone's is checked as soon as the zones in force change (reload, launch, Homecoming, one zone unlocked or locked), a packet goes only when a player's border changes, and everyone gets the world's back when Seasons stops. The world's own border is never read or changed.
161. **`/season config` reaches config.yml only.** Its settings by key path, as the bundled config.yml lists them (`hof.entry.cooldown`); a section (`hof.entry`) lists each of its settings with `get` and is refused by `set`; `schema-version` isn't a setting. Season files, galleries and waypoints have their own commands, and messages.yml and secrets.yml are edited by hand. `get` shows the value in force as the file (or the bundled default) writes it.
162. **Set writes in place.** Configurate doesn't read YAML comments, so saving config.yml through it would wipe its documentation and the admin's notes. `set` changes only the value's characters (a value on the lines below its key, such as a block list, is moved onto the key's line), adds a key the file lacks under its section, making missing sections, and keeps every other byte; YAML anchors, aliases, merge keys and several documents are refused with a request to edit by hand (ADR 0005, SnakeYAML). The value is read as one YAML value and written back in flow style, quoted only where needed; one that equals the setting's text now changes nothing. Then it goes through the edit path the other command edits share: every file loaded and swapped in, put back with the reason if anything fails, a backup kept, and audited as `config.yml <path>`, old, new and who. A hand edit not yet reloaded goes live with it; a broken one makes `set` fail, with the reason as `/season reload` words it.
163. **Secrets.** Only config.yml's settings are reachable, so secrets.yml and the environment never are, and neither is anything else pasted into config.yml (a key the bundled file doesn't list is "no setting"). A path naming a secret (`discordWebhook`, `adminWebhook`, `secrets.*`, or any path containing `webhook`, `secret`, `token` or `password`) is refused for `get` and `set` before anything is read, pointing at secrets.yml. Paper logs every command a player types, so a URL typed into `/season config set` is in the server log before Seasons refuses it, and nothing Seasons does can take it out again; so the refusal (`config.secret`) also says "If you typed one here, it is now in the server log; rotate it." **Decided** (review of #18).

### Map Link, identified (after #18)

164. **What Map Link does.** The spec's Map Link is [thebuildcraft/MapLink](https://github.com/thebuildcraft/MapLink), formerly Remote Player Waypoints for Xaero's Map: a client-only mod, nothing on the server. Its own description: "Synchronizes player positions, marker positions and area overlays from Bluemap, Dynmap, Pl3xMap or Squaremap with Xaero's Minimap and Worldmap." Read in its source ([thebuildcraft/MapLink at 595f7f4](https://github.com/thebuildcraft/MapLink/tree/595f7f4cc24bfc55f332f47da149c90737216bca): `connections/BlueMapConnection`, `mapUpdates/BlueMapMarkerSet`, `clientMapHandlers/XaeroClientMapHandler`, `ModConfig`) in the review of #18, which asked whether it only syncs player positions. It doesn't: **it imports marker sets, points and areas both.** **Decided**; what it does, against what Seasons publishes:
    - It reads BlueMap's public web map over HTTP, as each player configures it: `settings.json`, then each map's `maps/<map>/live/players.json` and `live/markers.json`. So BlueMap's web server must be reachable from players (TheRanch: map.petepeterepeat.com), and it shows what BlueMap's web map serves, players hidden there included. Seasons' scenarios read the markers through BlueMap's API on a BlueMap with no web server (ADR 0004), so they show what BlueMap holds, not what its web map serves.
    - Players: shown on Xaero's maps from `players.json`.
    - Points: `poi` and `html` markers become waypoints, by label, with their icon. Seasons' spawns, candidates, Hall, museum and shared waypoints are all points, so all of them appear.
    - Areas: `shape` and `extrude` markers become area overlays: the outline and every hole, with their line and fill colours; heights aren't read, so an extruded area is shown flat (143). Line markers (and any other type) are left out; Seasons publishes none.
    - A marker set's `defaultHidden` isn't read (its model has no such field), so a set hidden by default on BlueMap still shows on Xaero; a player chooses sets and markers in Map Link's own settings (147).
    - Each area is rasterised into Xaero chunk highlights on the player's machine, and an area whose bounding boxes (its outline's plus each hole's, in chunks) add up to more than `maxChunkArea`, 500,000 by default (about 11,300 blocks square), is left out altogether. So a height zone never could show (159), an `outside` zone shows only as a small ring (158), and a large circle doesn't show: TheRanch's `old-world` at a radius of 12,000 is about 2.25 million chunks, so with Map Link's defaults it appears on BlueMap but not on players' Xaero maps. Seasons publishes each zone as one area, as the spec says, and doesn't split it; a player who wants it on Xaero raises `maxChunkArea` in Map Link's settings (about 2,500,000 for a 12,000-block circle, which costs memory and a few seconds of rasterising), and the runbook's check before launch should look at the old world on a Xaero map with Map Link.

Anyone without a cell when they are archived gets a random free cell, as under `random`, so nobody who played is left without displays while a cell is free. Swaps and `/hof cell assign` work in `claim` galleries.
168. **Access `bounds`.** A cell's bounds become an edge inside the Hall, as a blocked zone's is outside it: anyone but the cell's owner while they may decorate it is refused entry by any route (a move, a vehicle, a teleport) and put back where they last stood outside it, and the Hall sweep moves anyone found inside to the gallery's entry, an owner whose time has run out included. Seasons' own moves count: archiving sends an owner to their cell only while they may decorate it, and to the gallery's entry otherwise. `/hof <player>` for a cell in a `bounds` gallery lands at the gallery's entry, since the cell's entry anchor is inside it. A cell without bounds has no inside to keep anyone out of, so it isn't a problem, as in any gallery. Bypass holders walk in. Refused entries are audited as `hall-blocked`, repeats counted (82). **Amended by 251:** nobody is moved out of a cell by default.
169. **Access `gate`.** A cell's two gate anchors are opposite corners of a plane one block thick, of at most 64 blocks, inside its bounds (a problem on load otherwise, and so is a cell with only one). The plane is the configured block, the new `cells.gateBlock` (default `iron_bars`), while the cell is locked, and air while its owner may decorate it; a cell with no owner yet is shut. Once a second, every gate whose chunks are loaded is compared with what the cell's state says (the window opening, an owner's time running out, `/season decorate close`, launch, a reload and startup all come down to that), and one that differs is set, writing `GATE_SET` to the journal before each change, as every world change is; the next pass is all recovery needs. **Amended on review of #19:** a gate plane may not hold any anchor but its own two corners, nor the gallery's entry, an exit or the launch button (a problem on load, with its key path). A gate is never set over a block with contents of its own (a container, sign, lectern or decorated pot: a block entity), so no item is lost: it is left as it is, audited (`gate`, `left alone`) and admins are told, until the block is gone. A gate that doesn't stay set, three tries with no pass finding it right, is left alone the same way until what it should be changes or the config is reloaded, so it can't fill the journal. Gate blocks are Hall blocks: nobody but bypass holders places or breaks anything in the plane, even while it is open, and a gate changed behind Seasons' back is put back by that pass and audited as `reconcile`. A player inside a cell when its gate shuts is moved to the gallery's entry. A cell without gate anchors in a `gate` gallery stays walk-in. Otherwise a gate cell is an `open` cell. **Amended by 250:** doorway gates, open unless shut on purpose, waiting for an empty cell.
170. **The armour-stand figure.** A gallery with `renderer: armour-stand`, or a platform without mannequins (`Capability.MANNEQUINS`), gets the spec's fallback: an armour stand with arms, every equipment slot locked, invulnerable, without gravity, silent, wearing a player head with the archived skin, its display tag and copies tagged `seasons:archived` like a mannequin's. The helmet goes on the cell's first trophy anchor, or is only in the archive view if the cell has none. A changed renderer is drawn again by reconciliation.
171. **A figure's pose.** "Standing pose (configurable per cell)": a cell may set `pose` in its gallery file, one of the poses a mannequin keeps: `standing` (the default), `crouching`, `swimming`, `fall-flying` or `sleeping`; anything else is a problem with its key path. An armour-stand figure stands whatever the pose. Reconciliation draws again a figure of the wrong kind or pose.
172. **The launch button.** The spec's "op-only button block registered as a `launch` anchor in the Hall" isn't in a cell, so it is a gallery's, like its entry and exits: `/hof gallery launch <gallery> [at]`, inside the gallery's bounds, with `none` to remove it. During the Intermission, a holder of `seasons.admin.season` who right-clicks it is asked to press again within 10 seconds, and the second press runs `/season launch` as them, with its refusals. Anyone else is refused with a message and audited as `hall-blocked`; outside the Intermission a press runs `/season launch`, which says why it can't. The block is any block the admin chose; Seasons takes over every click on it, so a button sends no redstone signal. **See 248:** links work the same way for everyone.

## M4 part 1: the dragon egg and the museum (branch `m4-dragon-museum`)

178. **Which kill counts.** The first ender dragon to die in `minecraft:the_end` while the season is Active. It is kept in `season.json` under `dragon.kill`: the slayer, their name then, when, and where the egg went. Later deaths in the season have no slayer, fanfare or hand-over; vanilla drops them no egg, as the flag is set again by the first. A dragon dying outside the Active phase counts for nothing, and launch clears the flag again.
179. **The damage tally.** Every `EntityDamageEvent` on the End's dragon at `MONITOR`, cancelled ones left out, whose damage source has a player as its causing entity: a hit, an arrow, a trident, a crystal or TNT they set off. That is the supertype of the feature map's `EntityDamageByEntityEvent`, so damage with a causing player and no damaging entity counts too. Each hit counts its final damage, never more than the dragon's health before it, so an overkill doesn't skew "most damage". The tally is per dragon (by entity id) and starts again for a new one. It is saved in `season.json` under `dragon.fight` at most once a second and when Seasons stops, so a restart mid-fight keeps it (`m4-dragon-restart`).
180. **The slayer.** The player the death event's damage source names as its causing entity: the final blow, an arrow's or a crystal's included. A blow that would kill the dragon leaves it at one health point in its dying phase, and the death comes at the end of that; Paper's death event still carries the killing blow's source (A37 shows the arrow's shooter credited over a player who dealt more). With no player behind the final blow, whoever dealt the most damage; on a tie, the first of them to hit it. With nobody, there is no slayer: the kill is recorded with none, the egg stays on the portal as in vanilla, and nothing is announced.
181. **`dragon.newEggEachSeason: false`** leaves the flag alone at launch, so a season's first kill drops no egg (unless no dragon was ever killed); it still has a slayer, a fanfare and a first. **`dragon.eggTo: portal`** leaves the egg on the portal, with the same fanfare and first.
182. **The flag with the End unloaded.** If launch finds no End with a dragon fight to clear the flag on, `dragon.flagPending` is set, admins are told, and the flag is cleared when the End loads (`WorldLoadEvent`) or at the next startup.
183. **Where the egg appears.** The game puts the egg on the highest block of the exit portal's column, so that block is checked once a second for 30 seconds after the kill (the death animation takes 10). An egg already standing there when the dragon died (the scenarios' old egg, or one left by a kill with no slayer) is left alone: the new one stands on top of it. If none appears in time, the kill is marked `missing`, it is audited and admins are told.
184. **Handing the egg over** is one transaction, through the vault so that it is exactly once: `season.json` says the egg is being taken and where, the journal gets `EGG_DELIVERED`, the egg leaves the portal, it goes on the slayer's Returned page under the reference `egg-s<season>` (adding it twice changes nothing), and then, if the slayer is online, the vault's own withdrawal gives it to them, with its own journal entries and recovery. A full inventory, or a slayer who has left, keeps it on the Returned page, which they can take from at once (A38). After a crash, startup finishes the job: an egg the vault has is done; otherwise it is taken off the portal if it is still there (the world may not have saved its removal) and put on the Returned page, since the slayer is offline then (`m4-egg-crash-cleared`, `m4-egg-crash-returned`).
185. **The fanfare** comes at the death, not at the hand-over: a title and sound for everyone online (Seasons' celebration, which also sets off a firework over each of them), five fireworks over the exit portal, a chat broadcast and a Discord post ("Pat slew the ender dragon in Season 3!"). The season first `dragon` is recorded with it, and `/season firsts` and the season card read it as "slew the ender dragon"; it has no "Season first!" line of its own, since the fanfare announces it. When the egg arrives the slayer is told it is theirs, or that it waits on their Returned page.
186. **An offline slayer** finds the egg on the Returned page when they next open `/vault`; nothing tells them at login. A notice at login can come with the other notices if players ask.
187. **Museum plinths.** A museum gallery's cell is a plinth: no owners, one trophy anchor, and optionally a plaque anchor. `/museum add|remove <anchor>` takes the plinth as `gallery:cell`, as `/hof cell` names cells; anything else is "There is no museum anchor".
188. **The egg wall.** A trophy anchor in a museum gallery may carry `egg: <season>`: that season's egg plinth. It is set by editing the gallery file and `/season reload`, as a gallery's own settings are (166), until the wand and stamping (M5). Only a trophy anchor can carry it, only in a museum, and only one per season across all museums; anything else is a problem with its key path.
189. **`/museum add <anchor> [label]`** puts the op's main-hand stack on the plinth, in one transaction journalled with the new kinds `MUSEUM_STARTED` and `MUSEUM_DONE` (an operation, as the vault's withdrawals are): save the op's file and journal their inventory's hash, write `data/museum/<gallery>.<cell>.dat` and the trophy's line in `museum.yml` (label, the season being played, the op's name as credit, a transaction id), take the stack if it is still the one held, save the op's file, then `MUSEUM_DONE`. After a crash the op's saved inventory, compared with the hash, says whether the stack was taken: if not, the trophy comes off the plinth again (`m4-museum-crash-stored`, `-taken`). Refused, each with its reason: not a player, an unknown anchor, an empty hand, an item tagged `seasons:archived`, a plinth that already holds something. Plaques read "label · Season 3 · credit", or "Season 3 · credit" without a label. Both commands need `seasons.admin.hof`, as the spec's Hall admin table has them, and are audited as `museum add` and `museum remove`.
190. **`/museum remove <anchor>`** gives the item back whole or not at all: the trophy moves under `removed` in `museum.yml` (and its file under `data/museum/removed/`) while it is given, then is forgotten; a full inventory puts it back on the plinth. After a crash, an item the op's saved inventory doesn't have goes back on the plinth.
191. **What plinths show** is drawn by reconciliation, as cells are: a copy of the item tagged `seasons:archived` over the trophy anchor, and the plaque over the plaque anchor or else over the trophy. Before this, reconciliation saw a museum cell as ownerless and would have removed anything shown there as a stray; museum cells now take their plan from the museum. `/museum add` and `remove`, recovery and the end of a season redraw the plinths they touch at once.
192. **The egg on its plinth** is worked out, not stored: a plinth for Season N shows a dragon egg with "Season N · slain by <name>" once Season N has ended (its end sequence has started) and has a dragon slayer first. A season with no slayer shows nothing, and an item put on the plinth by hand (the runbook's original egg) is shown instead. `museum.yml` holds only what was put there by hand; the slayer is in `season.json`'s firsts, which are kept across seasons. The end sequence draws the season's plinth when it starts, and reconciliation keeps it drawn.
193. **The end dry run** warns when no museum has an egg plinth for the season ("Museum: no egg plinth for Season 3, so its dragon egg won't be shown…"). It is a warning: the season can still end.
194. **Not in this part.** The `DragonSlain` API event waits for seasons-api to have events at all; the curator's museum action comes with curation, and the dragon credit on the season card and the slayer award with M4 part 2. They are listed under On hold in `docs/progress.md`.
195. **The egg is frozen while it is awaited and taken** (review of #22). From the kill until Seasons has taken the egg off the portal, or given up on it, no dragon egg in the exit portal's column can teleport (`BlockFromToEvent`), be clicked, broken or blown up, and no piston within 16 blocks of the portal moves; otherwise a click between Seasons seeing the egg and taking it would leave the egg in the world and put a second one in the vault. If the egg still isn't there when Seasons comes to take it, it left some other way and is still in the world: the slayer is given none, the kill is marked `missing`, it is audited and admins are told. Only after a crash does an egg already gone count as taken.
196. **A crash rolls the End back, not Seasons** (review of #22). The End's blocks and its dragon fight are saved by the game, at autosave or shutdown, while `season.json`, the journal and the vault are written at once. Once the season's first kill is past, startup and the End loading set the previously-killed flag again, so no later kill drops an egg, and take off an egg standing where the vault's egg was taken from. That spot is remembered with the kill until the End is next saved (`WorldSaveEvent`) or the server stops cleanly, so an egg a player later puts back on the portal as a display is left alone. A crash that rolls the End back to before the dragon died, while the egg is still awaited, is not put right: the dragon may come back alive and a later kill counts for nothing, as the season's first kill is recorded.
197. **A museum plinth with a change a crash left open takes no other** (review of #22). Until recovery settles an interrupted `/museum add` or `remove`, which waits for the op who started it, `/museum add` and `remove` on that plinth are refused ("Something is still moving in or out of…"), as is a second change while one is running. Otherwise another op could take out an item the first op still holds, or add one that recovery then overwrites.
198. **A museum cell may have several trophy anchors** (review of #22, superseding "one trophy anchor" in 187), as the spec's anchor table allows, such as an egg wall in one cell. What `/museum add` puts there shows over the first trophy anchor, with its plaque over the plaque anchor or the trophy; each trophy anchor with `egg: <season>` shows its own season's egg, with its plaque over itself (over the plaque anchor if it is the first), unless the hand-placed item stands there.

Names come from messages.yml under `awards.names`; an award without one is named after its id ("most-jumps" reads "Most jumps").
209. **Honours in the archive.** The data model puts firsts and awards in the archive record. Each archive copies the player's firsts of the season, and the awards they won if the season has them yet, when it is made; the winners' archives get their awards when the Intermission works them out, written in place (format-version 3, the items, hash and DataVersion untouched). Version 2 archives read with none. Cards, plaques and the museum read the season state, as before (56).
210. **The deaths display moves at once.** A reload that changes `deaths.display` moves the current season's objective (a season that was launched; the season `/season init` recorded has none). Showing a season's objective takes every other Seasons deaths objective off the screen, so `none` clears the tab list and a launch with `sidebar` leaves no earlier season's in the list. Earlier objectives are kept.
211. **`/scenario stat`** (ADR 0003) sets statistics for the award scenarios, which bots can't earn in time. The dragon slayer winning is shown by unit tests (`AwardsTest#eachMeasure`) rather than a dragon fight, which would make `m4-awards` an isolated scenario.
212. **A late archive counts** (review of #23, superseding the reading in 199 that left it out). The spec computes awards "at season end" over everyone who played it, and a player offline then is archived at their next login (A5), so their season-end statistics only reach Seasons then. Each archive into a season whose awards are already worked out works them out again, with the award list they were first worked out with (not today's config.yml), so a later config change never rewrites a past season. If the result differs, it is announced as a change ("Season 2 awards have changed:", then every award given) in chat and on Discord, the cells of every winner before and after are drawn again, and their archives' honours rewritten. An archive that changes nothing is quiet. This holds after launch too, since an archive made then is still that season's. The season state records which players' archives were counted, so a startup that finds an archive they didn't hear of (a crash just after `ARCHIVE_DONE`) works them out again. The dragon slayer award goes to the season's slayer from its firsts, archived or not; their trophy and archive line follow when they are archived.
213. **What a crash leaves undone after awards are worked out is finished at startup** (review of #23). Each result is saved with what is left: drawing, announcing, copying into archives (`pending` in `season.json`). Startup does whatever is still pending. The announcement is made before the copy and the pending mark is cleared after both, so a crash in between announces it once more rather than not at all; once announced, a copy that failed is retried at each start without announcing again, and admins are told. Copying rewrites only the archive's `honours` tag and writes every other tag back as read, items included. An archive that can't be read is left out of the awards and named to admins, rather than stopping the season's awards.

## M4 part 3: curation and Discord (branch `m4-curation-discord`)

214. **Telling the owner "on Discord".** A webhook can't message one person, and Seasons has no bot and no link from players to Discord accounts. Taken: each action is posted to the public channel naming the owner, the item and what happened to it ("1 × minecraft:diamond_sword from Pat's Season 2 archive was returned to them."), without the reason; the reason goes to the owner in-game (at once, or as a notice at their next login) and to the admin webhook. The museum action offers the museum's free plinths: cells with a trophy anchor whose first trophy anchor isn't an egg plinth, holding nothing, with no change running; the plaque reads "Season 2 · Pat", crediting the owner.
215. **Typing the reason.** Paper's dialog API, which has text input, is still marked experimental, which the spec says to avoid. Taken: after the action is chosen the menu closes and the curator types the reason in chat. Seasons takes that line at the lowest priority of `AsyncChatEvent` and cancels it, so no player sees it, nor does a chat bridge that ignores cancelled chat, as chat bridges usually do (worth checking against TheRanch's bridge). "cancel" leaves the item where it is; a blank line asks again; two minutes without an answer times out. With `curate.requireReason: false` the action runs as soon as it is chosen, recorded as "no reason given".
216. **The recycle bin.** 30 days is fixed, as the spec says, not a setting. Items older than that leave the bin within the hour (a sweep at startup and every hour) and at once when someone tries to undo one; either way the purge is audited. Ids are short and unique (`mhy3k2a1-4`), shown to the curator, in the audit entry and in the admin alert.
217. **The transaction and its recovery.** The item is first kept aside (`data/curate/<id>.dat`), then `CURATE_STARTED` is journalled (player: the curator, season: the archive's; for an undo, the owner), the archive saved without it, the item delivered, the copy forgotten and `CURATE_DONE` journalled. Owner and curator are held throughout, and an action is refused while either has an operation open in the journal. Recovery: an archive that still holds the item means nothing moved; otherwise an item that arrived (on the Returned page under `curate-<id>`, on the plinth under the id, in the bin, or for a take a curator whose saved inventory changed) stands, and one that didn't goes back from the kept copy. A take waits for the curator to log in, as the museum waits for its op. A delivery that fails while the server runs on puts the archive back at once.
218. **Undo.** `/hof curate undo <id>` needs `seasons.curate.destroy` (and `view`, which the curate command needs), puts the item back in the slot it came from and draws the figure again. It is refused, the item staying in the bin, if that slot holds something now or the archive was unarchived. The spec's command takes no reason, so none is asked; it is audited and the owner is told.
219. **The view after an action.** The curator view isn't reopened after an action; run the command again. Cancel in the action menu goes back to the view. If the archive changed between opening the view and the action (another curator, or a second action from an old view), nothing moves and the curator is told.
220. **Imported cells.** A record made by `/hof import` can be curated too: its stand's gear, containers and frames, as its archive view pages show them. `/hof import undo` then puts back what is left.
221. **Displaced items from `/season unarchive --force`** aren't in the curator view: the spec's command opens one archive, and a displaced file has no command of its own. They stay recoverable by hand, as before, and stay listed under On hold.
222. **Admin alerts.** The admin webhook gets tripwire hits, reconciliation repairs, recovery runs (each operation that finishes or fails; one waiting for its player isn't reported until it settles) and curation actions. Alerts that come within two seconds of each other share a post, a line each, no post over 1,900 characters; without an admin webhook nothing is posted. Each webhook has its own sender thread and queue, so a rate-limited one doesn't hold up the other.
223. **The season's end and launch on Discord.** The end is posted when the Intermission begins ("Season 2 has ended. Welcome to the Intermission!"), the launch when everyone has arrived ("Season 3 has begun!"), with no coordinates, since the spawn's area isn't published until players are there.
224. **The item snapshot** in a curation's audit entry is the item's vanilla NBT, base64-encoded, after the readable description, so the exact item can be rebuilt from the audit log.
225. **`/hof import undo` and curation** (review of #24). An imported record can be curated (220), so an undo must never put back an item a curator is moving out of the record. An undo holds the cell's owner from reading the record until it is set aside, as `/season unarchive` does, so neither runs while the other holds the owner. It is also refused while a curation a crash left open names the owner (journalled under the curator, so the owner's own open operations don't show it), until recovery settles it; the reason is "its owner's record is busy".

## M5: cell tooling (branch `m5-cell-tooling`)

226. **Wand clicks.** Sneaking, a left click sets corner 1 and a right click corner 2 (the usual convention of building tools); a plain right click opens the anchor menu; a plain left click does nothing. Every click with the wand on a block is Seasons', so it never breaks, opens or uses the block. The wand is the item `wand.item` in config.yml (default `minecraft:blaze_rod`) marked `seasons:wand` in its persistent data; a plain item of that kind is no wand. Only holders of `seasons.admin.hof` get one, and a wand held by anyone without it, or without `seasons.admin.config` for corners, is just an item. A corner on its own is shown on the action bar; a finished selection, the menu's results and refusals in chat.
227. **Where a wand anchor goes.** An archive or plaque anchor is the block clicked (the chest, barrel or lectern); a figure, entry, trophy or gate anchor is the block in front of the face clicked, where something stands or hangs. Each faces the admin, as `/hof cell anchor` does when the admin looks at a block, rounded to 45°. The cell is the one whose bounds hold that block; outside every cell the click is refused with a message. "Remove" is offered where the block already is an anchor and takes off every anchor on it. Each choice saves through the same code as `/hof cell anchor` and `unanchor`. **Amended by 253:** outside a cell the wand offers a link, and a gate corner beside a cell.
228. **Which cell the wand's corners set.** `/hof cell new` (and `/hof cell info`) makes that cell the admin's wand cell. A selection whose two corners are both inside that cell's gallery becomes its bounds at once, with the refusals of `/hof cell bounds`; any other selection is only a selection. `/hof cell bounds <cell>` and `/hof gallery bounds <gallery>` with no corners take the selection, which is how the import runbook's "wand-select each cell's bounds" works for any cell.
229. **The selection.** One per admin, in memory, with its dimension. Corner 1 always starts a new selection and corner 2 finishes it, so a half-made box from an earlier selection is never applied; a corner 2 in another dimension than corner 1 starts a new selection too, and logging out forgets it. `/season zone add <id> box` with no corners takes it, in its dimension; `outside box` takes its x and z (amending 92 and 156). Corners typed in still win. With no complete selection the command asks for corners as before, and says the wand can select them.
230. **Where templates come from.** The spec says to save a template with a structure block into `templates/`, but a structure block saves into the world's own structure store, not a plugin's folder. So `/hof stamp <name>` looks, in order, for `<world>/seasons/templates/<name>.nbt` (copied there by hand, from another world or a backup), then a structure a structure block saved as `seasons:<name>` (in memory or under the world's `generated/seasons/structures/`), then the jar's defaults. The reply says which it used. An unknown name lists every template there is.
231. **An archive marker.** Markers become air when stamped, and an archive anchor must be a block a visitor can click. So an archive marker anchors the block directly below it: the builder stands the marker on the chest or barrel. A marker over air is refused. Every other marker anchors its own block.
232. **Which way a template's figure faces.** Towards +z of the template (south as saved, yaw 0), turned with the template, so builders leave the open side of a cell there. Every anchor of a stamped copy gets the turned yaw: 0, 90, 180 or -90.
233. **Where copies go.** The first copy's minimum corner (before turning) is the block the admin stands in, so only a player can stamp. Copies are turned about that corner as the game turns structures (`--rotate 90` is clockwise seen from above), and each next copy is `--step` further on; the default step is the turned copy's width along +x, so copies stand side by side. New cells take the gallery's next free ids `c1`, `c2`, …; their bounds are the copy's footprint. The count is 1 to 64.
234. **What a stamp may replace.** Only air: every block the template sets (its own air included; structure voids set nothing) must be air in the world, or the stamp is refused naming the first block in the way. Every copy is checked first, inside the gallery, clear of other cells and galleries, and over air, so a refused stamp changes nothing. A stamp is journalled (`STAMP_STARTED` with its plan saved under `data/stamps/`, then `STAMP_DONE`), the dimension saved before the gallery file is written as the import does (45), and an interrupted one is finished at startup by placing its copies again, which a placement over itself leaves unchanged. One stamp runs at a time. Stamps are audited.
235. **What a template may hold.** No items at all: a container, lectern, jukebox, shelf or pot holding anything, or an entity carrying anything, is refused, since stamping it into cells would make items from nothing and the Hall's containers are a decorating owner's to fill. Nor hoppers, droppers, dispensers, crafters, ender chests, lava or hopper minecarts, which the Hall doesn't allow (A23). Any structure block that isn't a Seasons marker is refused. A season gallery's template needs one figure marker; at most one plaque and one entry; none or two gate markers.
236. **Egg plinths by wand.** In a museum gallery the anchor menu also offers an egg plinth for the newest seasons up to the next one that have none (at most three), so the egg wall no longer needs a hand edit (188). Stamped trophy markers are plain trophies.
237. **The gallery's own points.** Entry, exits and the launch button stay command-only: the spec gives the wand cell anchors and bounds. **Amended by 253.**
238. **The default templates.** `alcove` (5 × 5 × 5: a floor, three walls and a roof, a barrel with an archive marker on it, figure, plaque, trophy and entry markers, open towards +z) and `plinth` (3 × 4 × 3: a floor, a plinth block with a figure marker on it, a plaque marker in front and a trophy marker beside it). The plinth serves both a season gallery's "row of plinths" and a museum, where its trophy anchor takes `/museum add` and the figure anchor is never used. They are written by a generator in core's tests (`DefaultTemplates`, with the plain NBT writer core already has; `./gradlew :core:writeDefaultTemplates`), so the binaries can be reviewed as code, and `DefaultTemplatesTest` checks the committed files match it. Core's build puts them in the jar under `templates/`.
239. **Review of #25: the wand cell, amending 228.** A selection becomes a cell's bounds only for the cell just made by `/hof cell new`, only while it has no bounds, and only once: after that, and after `/hof cell info`, a selection is only a selection, so a stray selection can never move an owned cell. `/hof cell bounds`, by command or by wand, is refused when the cell's anchors wouldn't all sit inside the new bounds ("Move or remove it first"), so a gallery file is never written that the next start would leave out. **Amended by 250:** gate corners beside the bounds are allowed.
240. **Review of #25: what a template may hold, amending 235.** A loot table counts as holding items (it fills a chest, barrel, pot or suspicious block when first opened or brushed, and a chest minecart or boat likewise); so do a dropped item, an arrow or trident that can be picked up, and an ominous item spawner. Spawners, trial spawners and vaults, and spawner minecarts, are refused as blocks and entities the Hall doesn't allow. A mob's loot table is what it drops when killed, as a block drops itself when broken, which the Hall's rules stop; it isn't counted. Creatures in a template don't appear in the Hall at all, since the Hall lets no creature spawn but Seasons' own and commands' (M2).
241. **Review of #25: placing a copy again, amending 234.** Every entity a stamp places is marked `seasons:stamp` with the stamp's id and the copy's index. Placing a copy, live or in recovery, first waits for the entities around it to load (giving up, with the stamp left to recovery, after 10 seconds), removes any entity already marked for that copy, then places it and marks what it added, all in one tick, so a copy placed again is still one copy, entities included. The mark stays on the entities; nothing else reads it. A stamp's plan (`data/stamps/<id>.plan`, now starting `format-version=1`) and its template are written as every Seasons file is (temp file, fsync, rename) before `STAMP_STARTED`.
242. **A stamp holds its gallery, amending 234.** Copies are checked against the gallery when `/hof stamp` runs, but placed over the following ticks and written as cells at the end, so an edit in between could take a copy's cell id or overlap its footprint, and the gallery file written last would break a rule the next start leaves it out for. So from the checks until its cells are written, a stamp holds its gallery: `/hof cell new`, `/hof cell bounds` (by command or wand), `/hof gallery bounds`, `entry`, `exit` and `launch` on it are refused, saying a stamp hasn't finished, and so is another stamp into it. Anchors, assignment and everything else that doesn't change what the stamp checked go on. A stamp that stops once `STAMP_STARTED` may be journalled keeps the hold until recovery finishes it at the next start (a recovery that fails keeps it until the start after), since recovery places the plan's copies with the plan's cell ids; a stamp refused before that lets go at once. **See 259.**

## Post-M5: hub, links and decoration (branch `post-m5-hof-preparation`)

The owner changed the spec for this part (decision log): the Hall is a hub plus wings, a free place to visit and leave, with links between it and each season's spawn, doorway gates that shut only on purpose, and decoration by builders. These readings fill in what the spec leaves open.

243. **`hall.yml`.** `<world>/seasons/hall.yml` holds the hub (`hub: { min, max }`), the Hall spawn (`spawn: { pos, yaw }`), the Hall's exits (`exits: [[x, y, z]]`) and the links, in the Hall's `dimension`. It is read and written as gallery files are (backups, atomic writes, `/season reload` for hand edits), and validated with them: a hub overlapping a gallery, a Hall spawn outside the hub or a malformed link is a problem. Like a broken gallery file (61), a broken `hall.yml` at startup is left out and nothing else is: `/season status` shows it, admins are told after joining, the `/hof hall` and `/hof link` commands refuse so the file isn't written over, and `/season end` and `/season launch` are refused until it is fixed, since the Intermission keeps everyone in the Hall. A reload still swaps every file in or none.
244. **The Hall spawn, superseding 62.** Plain `/hof`, leaving during the Intermission, and a gallery with no entry of its own all use the Hall spawn. With none set, plain `/hof` says "The Hall of Fame has no spawn yet." and nothing falls back to a gallery's entry. `/hof hall spawn` with no position takes the block the admin stands in and their facing; it is refused before there is a hub, and outside it. `/hof hall hub` is refused if the box would leave the Hall spawn outside it, or overlap a gallery. 64 is unchanged: `/hof` from inside the Hall still moves without checks.
245. **Leaving freely, amending 67, 69 and 74.** With `hof.sealed: intermission` (the default) or `never`, a player who leaves the Hall's bounds by walking, falling or another plugin's teleport outside the Intermission just leaves: their saved spot is dropped and the game-mode sweep gives them back survival if Seasons put them in adventure. Ender pearls and chorus fruit are still refused inside the Hall (so a pearl out is refused, not followed by a return). During the Intermission, `intermission` and `always` bring a leaver back to the Hall spawn (or their saved spot under `always`, if they have one); `never` doesn't. `always` is the behaviour before this part. Walking in from outside still saves where they came from (67), whatever the setting, so `/hof leave` takes them back.
246. **`/hof leave` with no saved spot, amending 68.** With `hof.leaveWithoutSpot: season-spawn` (the default), outside the Intermission it takes a player in the Hall to the current season's spawn through return safety, restoring survival if Seasons switched them. A season with no recorded spawn (the one `/season init` recorded) uses the world spawn, unless that is inside the Hall, when it is refused as before. `refuse` refuses as before. During the Intermission it still says everyone stays.
247. **Arriving by respawn or first join.** A player first seen in the Hall after joining, or who appears in it from further than 4 blocks away with no move or teleport reported (a respawn at a Hall spawn that is the world spawn), has no saved spot: nothing is saved, so dying can't become a trip back to where one died. Walking in still saves (67). A first-time joiner after launch who arrives inside the Hall (the world spawn is the Hall spawn) stays there rather than being sent to the season's spawn, amending the decision that late joiners go straight to the new spawn for this case only; players offline at launch are still sent there (A5). Leaving the Hall freely gives back the game mode at once, and the mode saved for `/hof leave` is the one outside the Hall, so stepping out and straight back in never remembers adventure.
248. **Links, generalising 172.** A link is a block with an id (`/hof link add <id>`, the looked-at block within 6 blocks, or `x y z`), in any dimension, inside the Hall or not, at most one per block. Right-clicking it with either hand, or standing on it (or on the block above it, as exits count), takes the player along it; Seasons takes over the click, so a button gives no signal and a sign opens no editor. Standing on one fires once until the player steps off it. A link block outside the Hall can't be broken, changed or blown up except by builders, as Hall blocks can't. Without a destination it says it leads nowhere yet. Taking one is limited by `/hof`'s rate limit (a link is a trip like `/hof`).
249. **Where links go.** `hall`: the Hall spawn; from outside the Hall, every entry check but the bed (so not while hurt, falling, burning or near monsters) and the unsafe-spot check of 73; the spot saved is where the player stood (the link), or none with `hof.links.returnToLink: false`. From inside the Hall it is a walk across, as `/hof` is (64). `season <n>`: that season's recorded spawn, refused ("Season <n> has no spawn") when it has none. A spot: as set by `/hof link to`. Going anywhere but the Hall: refused during the Intermission and the archiving before it; refused when the destination is inside a zone that is blocked now and the player doesn't hold `seasons.zone.bypass`, saying until when ("That leads into land locked until Homecoming."); otherwise the player goes there through return safety (an unsafe destination falls back as `/hof leave` does), with arrival immunity, their game mode back if Seasons switched it, and no saved spot left behind.
250. **Gates, amending 169 and 239.** A gate corner may sit inside its cell's bounds or in the layer just outside them (the bounds grown by one block each way); the plane between the corners must be inside the gallery and overlap no other cell. `/hof cell anchor … gate`, the wand and `/hof cell bounds` accept such corners, and 239's "anchors outside" refusal leaves gate corners beside the new bounds alone. Each cell keeps whether its gate is shut (`gate: shut` in the gallery file). With `cells.gates: open` (the default) a gate is air unless shut, whatever the decorating window says; `auto` keeps 169's behaviour (air only while the owner may decorate). `/hof cell gate <cell> open|shut` and `/hof gallery gate <gallery> open|shut` are admins'; `/hof gate open|shut` (`seasons.hof.gate`, everyone) is an owner's, for the cell they own in the newest season they own one, and is refused in a gallery whose access isn't `gate`. A gate doesn't shut while anyone but a bypass holder stands in its cell or its plane (head or feet); it shuts at the first pass after they leave, and admins hear once that it is waiting. With `cells.moveOut: true` a shutting gate moves them to the gallery's entry instead, as before. Opening and shutting gates doesn't change anything a stamp checks, so a stamp's hold (242) doesn't stop it.
251. **`bounds` cells, amending 168.** With `cells.moveOut: false` (the default) entry into a cell a player may not be in is refused at its edge as before, but the sweep no longer moves anyone found inside: an owner whose time ran out walks out themselves. `/hof <player>` still lands at the gallery's entry for a `bounds` cell.
252. **Builders, amending 37, 76, 82 and 84.** With `hof.creativeBuilds: true` (the default) a player in creative mode is a builder, as a bypass holder is: they place, break and use anything anywhere in the Hall, any block included (hoppers, ender chests, workstations), open ender chests and real containers, and are audited as `hall-bypass`. Survival players keep 76's rules, so a hub's crafting tables, signs and ender chests stay as decoration that does nothing for them. Creative and spectator players were already never switched to adventure (37). Visits (pearls, drops, riding in, leaving) treat creative players as anyone else; only `seasons.hof.bypass` exempts from those.
253. **The wand outside cells, amending 227 and 237.** A plain right click with the wand on a block in the Hall but in no cell (the hub, a hallway) opens a menu too (the cell is the one holding the block clicked or, failing that, the block in front of the face clicked, since a cell's floor isn't in its bounds): "link" makes the block a link with the next free id `l1`, `l2`, … and no destination (set it with `/hof link to`), and, when the block in front of the face clicked is beside exactly one cell (as 250 counts it), "gate" adds a gate corner there to that cell. Outside the Hall, and with nothing to offer, it is refused as before; links outside the Hall, such as at a season's spawn, are made by command. The Hall's spawn and hub stay command-only, the hub taking the wand selection.
254. **`/hof cell new <gallery>` with no id** takes the gallery's next free id `c1`, `c2`, … (as stamps do, 233), and makes it the wand cell as `/hof cell new` with an id does (239).
255. **`/hof hall check`.** Read-only, for admins. It lists, each on a line: a missing hub or Hall spawn; each gallery whose box doesn't touch the hub or a gallery that does (galleries are joined when their boxes share a face, so a diagonal corner doesn't count); a gallery with no bounds or no entry; cells with no bounds or no figure; each cell whose size differs from the size most of its gallery's cells have; links with no destination, whose block is air, or whose season has no spawn. It ends with each gallery's cells and free cells for its season, and "All clear." when there was nothing to report. Problems that stop a file loading can't be in a loaded Hall, so they are reload's to report.
256. **A spawn inside the Hall.** The plan named a season spawn or spawn candidate inside the Hall a problem that stops loading. Taken, as the safer reading: it is treated as a spawn inside a zone is, since a season file with a problem would take every file down at startup. `/season spawn set` and `/season spawn candidate add` refuse a spot inside the Hall; a hand edit putting one there is a warning on reload and validate; the end dry run reports it; and `/season launch` is refused until it moves (A41). The world spawn may be inside the Hall.
257. **`archive.arrival`.** `cell` (the default) sends everyone archived at season end to their cell as before (A4); `hub` sends them to the Hall spawn, or their cell if there is none; they still get their cell and their time to arrange it. A player without a cell stays where they are, as before.
258. **`launch.setWorldSpawn`.** `true` (the default) sets the world spawn to the new season's spawn at launch, as A6 says; `false` leaves it where it is, such as at the Hall spawn. Players offline at launch are still sent to the new spawn when they next join (A5), whatever the world spawn.
259. **What a link or the hub changes during a stamp.** The hub can't overlap a gallery, so `/hof hall hub` never touches what a stamp checks; a link added on a block inside a gallery a stamp holds is refused, as the gallery's entry is (242).
260. **Review of #26: links and gates, amending 243, 248 and 250.** Nothing writes `hall.yml` while it is left out, the wand's link menu included, and `HallService.saveHall` refuses it as a backstop. A link's own block stays when the world would destroy it because what holds it up is gone (a button's wall, a plate's floor): Paper's `BlockDestroyEvent` is cancelled for link blocks only, so a builder breaking a hub wall doesn't leave floating torches; a builder removes a link with `/hof link remove` or by breaking the link block itself. After any of Seasons' own moves, a link the player lands on counts as already stood on, so `/hof leave` back onto the plate they came by doesn't take it again until they step off and on. Standing on a link does nothing while the player is held for archiving (clicks were already refused by the hold). A gate counts a player as inside while any part of their box (0.6 wide, 1.8 tall) overlaps its cell or plane, not just the blocks of their feet and head, and checks again just before setting its blocks, after the journal entry, since someone may have walked in meanwhile; a `GATE_SET` entry with no change after it is harmless, as the gate is reconciled from what it should be.

## Post-M5: setting up the Hall (branch `post-m5-hall-setup`)

The owner asked for this part after setting up a test Hall by hand (decision log): the bed rule as a setting, leaving the Hall during the Intermission, a reset for test worlds, hand-built cells kept as they are, and setting up the Hall made easy. These readings fill in what the request leaves open.

261. **The bed rule as a setting.** `hof.entry.requireBed` (default `true`); `false` drops the bed check for everyone, so `/hof` works wherever the other checks allow, and `bedDistance` and `anyBed` do nothing. It is a config.yml setting (`/season config set hof.entry.requireBed false`), not a game rule: Paper's API has no custom game rules. Sneak-clicking a bed works either way. `bedDistance` is now 0 to 16, a problem on load otherwise: the check scans the cube around the player, 16 is about 36,000 blocks, and 64 would stall the tick.
262. **`seasons.hof.anywhere`** (default op, grantable to a group). Its holders skip every `/hof` entry check but the rate limit (the bed, monsters, recent damage, movement, hazards, the cooldown) and the unsafe-spot check of 73, which exists to stop `/hof` then `/hof leave` being a teleport home, something an admin can do with `/tp` anyway. `/hof leave` still runs return safety for them. It moves only its holder and protects nothing, so unlike the bypass nodes it defaults to ops.
263. **`seasons.hof.roam`, amending 245, 246 and 249.** Its holders (ops by default, or a LuckPerms group) are never held in the Hall. During the Intermission and the archiving before it, and under `hof.sealed: always`, leaving by walking, falling, flying or another plugin's teleport (`/tp`) just leaves, as it does outside the Intermission: the saved spot is dropped and the game mode comes back. `/hof leave` takes them to their saved spot, or with none to 246's season spawn (the season just ended); links out of the Hall work for them; `/hof tp` and `/season tp` take them out. Launch moves them to the new spawn with everyone. Spawn candidates and waypoints can be added where they stand. Pearls and chorus fruit stay refused inside the Hall. A roamer is archived at the end like anyone; one offline at the end is archived at login.
264. **Positions.** Every position argument takes `x y z`, each part a number, `~`/`~n` relative to the sender's block, or all three as `^ ^ ^n` along their facing, as vanilla commands do (read by the core itself, `command/Positions`, so every adapter reads them alike); or `here`, the block the sender stands in; or nothing, which keeps each command's old meaning (where the sender stands, or the looked-at block for `/hof link add`). Positions are in the sender's dimension; the console has none, so it must give absolute coordinates, and relative ones, `here` and `sel` are refused with a reason. A yaw, where a command takes one, follows the position; with none, the sender's facing (console: 0). Into the Hall from outside they save the spot as `/hof` does, so `/hof leave` returns there; out of the Hall they drop it, and during the Intermission are refused without `seasons.hof.roam`. 272. **Wand modes, amending 226.** In `block` mode (the default) a corner is the block clicked, as before; in `place` mode it is the block against the face clicked, where a placed block would go, so a cell's corner can be the air above its floor. Swap-hands (F by default) with the wand in the main hand toggles the mode, and the swap is taken over so nothing moves; `/hof wand mode block|place` sets it. The mode is per admin, in memory, forgotten at logout, and shown on the action bar whenever the wand is held. The anchor menu is unchanged: 227 already puts each anchor type on the block clicked or in front of it. `/hof sel pos1 [position]`, `pos2 [position]`, `info` and `clear` set and read the same selection by command, with 229's rules (pos1 always starts a new one); with no position, the block the sender stands in.
273. **Which cell the wand sets, amending 239.** While the wand is held, the action bar always says what a finished selection will do: "Next selection sets season-1:c2's bounds" or "Next selection is only a selection". When it does set them, the reply names the cell and its size and offers `/hof undo`. `/hof cell redefine <cell>` makes an existing cell the wand cell again (239 kept that to new cells), so its next selection replaces its bounds; anchors the new bounds would leave outside are listed and taken off (gate corners beside the bounds stay, as 250 allows), and `/hof undo` puts them back. 239's rule still holds for every other selection: a stray one never moves a cell.
274. **Swapping, moving, renaming and removing cells.** Within one gallery. `/hof cell swap <a> <b>` swaps the two cells' places (bounds, anchors, gate) while their ids, owners and gate states stay, so cells tagged in each other's places are put right in one step. `/hof cell move <cell> <dx> <dy> <dz>` moves a cell's bounds and anchors together; `rename <cell> <id>` gives it a free id, owners following. Each is refused when the result breaks a gallery rule (outside the gallery, over another cell, a gate plane over another cell), while a stamp holds the gallery (242), and, without `--force`, for a cell an owner has been archived into or is decorating, since the owner's decoration stays where it was built while the cell moves; with `--force` the displays are drawn again in the new place at once (`/hof reconcile <gallery>`). `/hof cell remove <cell>` removes a cell with no owner in any season, its displays (none, then) and its gate state; the blocks stay. All audited.
275. **`/hof undo`.** Puts back the Hall file (a gallery file or `hall.yml`) the sender last edited as it was just before, from the backup taken then, one level deep, if the file hasn't changed since; otherwise it is refused, saying it changed after their edit. It covers bounds, anchors, cell rows, swaps, moves, renames, redefines and removals, entries, exits, links, the hub and the Hall spawn; not stamps or imports (which change the world and have their own recovery and undo), assignment or gates. Then the gallery is reconciled. Audited as `undo`. Undos are kept in memory, so a restart forgets them.
276. **Outlines.** Drawn for an admin (`seasons.admin.hof`) while they hold the wand, and while `/hof show on` is in force (until `off` or logout): every box within `wand.outlines.range` blocks (default 48), nearest first, at most `wand.outlines.max` (default 64). Each box is twelve thin glowing block displays along its edges, coloured by kind (hub white, gallery aqua, cell yellow, the wand cell green, gates red, entries and the Hall spawn purple, exits and link areas orange, a half-made or finished selection magenta), with a text display over each cell and gallery giving its id (and the selection's size). They are spawned only for that admin (`Entity#setVisibleByDefault(false)` and `Player#showEntity`), not saved with the world (`setPersistent(false)`), and tagged `seasons:outline`, so a restart can't leave one; any `seasons:outline` entity found when a chunk loads is removed. They are worked out twice a second and sent again only when the boxes an admin should see change (they moved, a Hall file changed, a selection was made), and taken away when they aren't needed, the admin logs out or Seasons stops. They hold no items and nothing is journalled for them, since the journal guards items and records, which outlines never touch. Reconciliation and the tripwire leave them alone. A row preview (277) is drawn the same way. Particles were the other choice; they flicker, cost a packet per point every refresh and can't carry labels.
277. **Rows of cells.** `/hof cell row <gallery> <count> [--along <dir>] [--wall <n>] [--across <dir> <width>] [--like <cell>]` takes the wand selection (or `--from <box>`) as the first cell's bounds and repeats it `count` times (1 to 64) along `--along` (`+x`, `-x`, `+z` or `-z`; by default the gallery's longer axis, pointing away from the hub), each the box's length plus `--wall` (default 1, 0 to 4) further on, so 7 × 7 × 6 cells share one-block walls. `--across <dir> <width>` adds the mirror image of the row on the other side of a hallway `width` blocks wide in that direction. New cells take the gallery's next free ids numbered from the hub outwards, alternating sides when there are two (c1 near side, c2 far side, c3 near side, …), the order `ordered` assignment hands out (spec, Defining cells). `--like <cell>` copies that cell's anchors and gate corners, placed by their offset from its minimum corner and, on the far side, reflected across the hallway with their yaw turned to match. The command checks every cell first, as a stamp does (inside the gallery, clear of other cells, anchors inside), refuses the whole row with the first problem, and otherwise shows the row as outlines for 60 seconds: `/hof cell row confirm` writes it in one gallery-file edit (one `/hof undo` takes it all back), `cancel` or the minute drops it. Blocks aren't touched: the row tags what is built (to build and tag at once, stamp).
278. **Plaque size.** A plaque anchor may carry `scale` (0.25 to 4, default from the gallery's `plaqueScale`, itself 1.0 by default), applied to its text display. An admin holding the wand, sneaking and looking at a plaque's display or anchor block within 6 blocks, grows it by 0.1 per scroll up (a step back in the hotbar) and shrinks it per scroll down; the change of hotbar slot is cancelled, the new size shows on the action bar, and each scroll writes the gallery file, a small atomic write. `/hof cell plaque <cell> scale <n>` and `/hof gallery plaque <gallery> scale <n>` set it by command. Keyboard keys such as + and - never reach the server, so scrolling and the commands are the ways in. Lectern plaques have no size and are left as they are.
279. **Areas for entries, exits, links and the Hall spawn.** The Hall spawn, a gallery's entry and a cell's entry anchor may be a box (`{ pos, to, yaw }`) instead of a block; an exit (in the hub or a gallery) may be a box; and a link may have an area (`area: { min, max }`) beside or instead of its block. Each box is at most 32 blocks a side, as thin as one block in any direction, so a doorway plane, a hole in a ceiling and a frame in the sky all work; the Hall spawn sits inside the hub, a gallery's entry inside the gallery, a cell's entry inside its cell, as before, and a link area may be anywhere, inside the Hall or not. Arriving at a box lands on a free floor spot inside it (a solid block under two free ones), the one nearest its middle with no other player within 1.5 blocks, else the nearest, facing its yaw, so everyone arriving at once at season end spreads out; a box with no floor spot lands at its first corner and `/hof hall check` reports it. Passing through an exit or link area triggers it: walking into it, falling through it or flying through it, worked out on the line between each move's start and end so a fast elytra flight can't skip a one-block plane; it fires once until the player has left the area, as standing on a link does (248, 260). Passing through a link area into the Hall skips the movement checks as well as the bed, so an elytra flight can take it, and saves no spot, since it may be in the air: `/hof leave` then goes by 246. A single block works as before.
280. **Gates over decoration, amending 169, 250 and 260.** A gate plane may include an archway's blocks: shutting turns only the plane's air (and cave air) into `cells.gateBlock`, and opening turns only blocks of `cells.gateBlock` back into air, so stairs, lanterns or carvings in the plane stay as built. A block with contents in the plane is simply left, so it no longer holds the gate up (260); 169's "won't stay set" counts only the blocks the gate would change. Decoration made of the gate block itself would be cleared when the gate opens, so `/hof hall check`, `/hof cell gate` and the wand's gate corner report a plane holding the gate's own kind of block while the gate is open.
281. **Legacy galleries.** `kind: legacy` (`/hof gallery create <id> <season> --legacy`, or by hand) holds hand-built cells kept as they are, such as Season 1's barrier-sealed rooms. It is Hall, so all of the Hall's protection applies, with two additions for its real items: every container in it opens as a view-only copy for everyone but `seasons.hof.bypass` holders, creative builders included, and nobody but bypass holders breaks a container holding anything, takes from or changes an armour stand's or item frame's gear, or breaks a stand or frame holding something. Seasons draws no displays there, never assigns its cells (manual `/hof cell assign` is allowed, so `/hof <player>` lands there and the import later knows the owner), never locks, gates or moves anyone out of them, leaves it out of the end dry run's shortfall and doesn't require figure anchors or bounds. Reconciliation and the tripwire treat it as any Hall gallery: the tripwire only deletes items tagged `seasons:archived`, which hand-built cells don't have. `/hof hall check` lists it as legacy and skips the figure and size reports for it. `/hof import` works on a legacy gallery as on a season one and, once every cell is imported, makes it `kind: season`; `/hof import undo` leaves it a season gallery, which `kind: legacy` by hand turns back. A legacy gallery's season can also have a season gallery, which takes its rollovers.
282. **Armour stands placed in the Hall.** Placing an armour stand fires Paper's `EntityPlaceEvent` and then a `CreatureSpawnEvent` with reason `DEFAULT`; the Hall's rules allowed the first for an owner decorating (77) or a builder, and its spawn guard then cancelled the second, so nobody could place one. The spawn guard now lets through a creature spawning with reason `DEFAULT` in the same tick, at the same block and of the same kind as a placement the Hall's rules allowed; a dispenser's (`DISPENSE_EGG`) and any other creature spawning in the Hall stay refused.
283. **`/season reset`.** For server operators only: `Player#isOp()`, or the console, never a permission node, so no group can be granted it. Step 1, `/season reset [--keep-hall]`: refused during a countdown or archiving, while anyone is held for archiving, a stamp or import runs, or the journal has an open operation; otherwise it warns, in red, that this permanently deletes every archive (with counts of players, archives, vault items, museum items and items in the recycle bin), every player record, season and gallery file, and that archived items can't be given back afterwards, and asks for `/season reset confirm` within 60 seconds. Step 2, the confirm: a second warning, and "Please type DELETE" in chat (the console types `/season reset confirm DELETE`); anything else typed, logging out or 60 seconds cancels, and is said. Then, in order: the whole `<world>/seasons/` folder is zipped to `plugins/Seasons/reset-backups/<world>-<time>.zip` and the zip fsynced (a failed backup stops everything); every Seasons display is removed, cell by cell, loading each cell's chunks; the `seasons_deaths_s*` objectives are removed; anyone Seasons switched to adventure gets their game mode back; the folder's files are deleted, except with `--keep-hall` `hall.yml`, `galleries/*.yml` (with every owner, gate state and decorating time taken out) and `templates/`; the reset is written to the server log (the audit log goes with the folder); and Seasons disables itself, telling everyone with the node that the next start is a fresh install. Nothing in `plugins/Seasons/` (config, messages, secrets) is touched, and removing the plugin is deleting its jar and folder. The world spawn, gate blocks, link blocks and players' advancements are left as they are. The backup is the only way back, by stopping the server and unzipping it. **Amended on review of #27:** the confirmed reset first writes the zip, then `plugins/Seasons/reset-pending` (whether the Hall is kept and every gallery box, or each cell's box in a gallery without bounds, fsynced) and a `RESET_STARTED` journal entry, before its first change to the world; a failed journal write stops it there. Then every Seasons menu an online player has open is closed (view-only, paged, withdraw-only and choice menus, nothing else), since a copy in one would be takeable once the listener that keeps it view-only is gone, and Seasons stops (reconciliation, the renderer, the tripwire and every task) before the displays are removed, so neither a pass nor the reset's own chunk loads can draw one again. Then objectives, game modes (from what was read before the stop; the records go with the folder) and files. With `--keep-hall` each gallery file is read back from disk and written without owners, imports or gate states; a file that doesn't load is kept as it is. `reset-pending` is deleted last. If it is there at the next start (a crash or a failed delete), Seasons finishes the deletion before it reads anything in the folder and removes the displays in the recorded boxes once the server runs; the game modes of players who were offline then are not given back. Other admins online are told who reset Seasons. Help texts for arguments are plain text, so they name values in words rather than as `<tags>`, which plain text drops.
284. **A player record ahead of the season.** A record whose `archivedThrough` is beyond the season on record, as after `season.json` alone was reset by hand, would be skipped by every archive. Seasons now reports such records at startup, in `/season status` and to admins joining, naming the players; `/season reset` is the way to start over.
285. **Workstation inputs at archive time (security review H1).** Step 1, "close any open menu and return cursor and crafting-grid items to the inventory", is read as covering every slot the game hands back to the player when a menu closes: the inputs of an anvil, smithing table, grindstone, enchanting table, loom, stonecutter, cartography table and beacon, and a villager's trade slots. They are carried items: returned to the inventory where there is room and otherwise archived as overflow, like the cursor, and emptied before the menu closes. Containers that belong to the world (chests, furnaces, a crafter) are never touched. After the clear Seasons checks that nothing turned up in the inventory; anything that did goes into the record as overflow and is audited, never back to the player.
286. **"Already cleared" after a crash (security review H3).** Crash recovery's "if the inventory is already cleared, the archive is marked done" is read as "cleared by step 4 of this archive". Seasons journals `ARCHIVE_CLEARING` once the player still matches their copy and just before it clears them; recovery takes an empty inventory as cleared only when that entry is there. An empty inventory without it means what was copied went somewhere else, so recovery stops, tells admins (`archive.recovery-uncleared`) and leaves the operation open. Recovery also seals the vault page again whenever the player still matches, which is harmless, and a season page whose archive is still open for its player can't be withdrawn from (`vault.pending`), since the ender chest it copied may still be in the game.
287. **An archive that doesn't go through (security review H2).** The spec archives every online player at season end and everyone else at login, and says admins are told of problems, but not what becomes of the player meanwhile. The safest reading: never let them go with what the archive should have taken. An attempt that stops before the clear while the server runs on is put back at once (its vault page removed, `ARCHIVE_ABORTED` journalled to close the operation, its file moved aside as `aborted-<time>`); one that stops after the clear is left to recovery. Either way, and when the player is busy with another transaction as the archive reaches them, they are held as pending (nothing they carry can move and their commands wait, as during an archive) and their login plan runs again every 10 seconds until it goes through or they leave; admins hear once, again after 6 tries in a row (`archive.stuck`), and the player is told. Launch already waits for online players who aren't archived; a pending player who leaves is held again at their next login while catch-up runs. `/season reprocess <player> --restart` is new: for a recovery that is stuck because the player's inventory neither matches nor is empty, it puts the open archive back the same way and archives the player afresh from what they carry now; it is refused while they carry nothing, since what the archive copied would be lost.
288. **Vault clicks (security review M2).** "One server transaction per click … clicks queued per player" is read as a bounded queue: one withdrawal runs and one more waits per player, and clicks beyond that are dropped with `vault.busy`. A click whose item wouldn't fit in the player's inventory is refused at once with `vault.full`, before anything is journalled or written; the give still checks again and rolls back, as before. Click messages go to the player at most once a second, and a refused click is audited at most once in ten seconds per player. The journal's open operations are worked out once each time the journal changes rather than on every lookup. The review's fix plan also suggested compacting the journal at Homecoming; with full-inventory clicks no longer journalled and lookups no longer scanning the journal, the journal grows only with real withdrawals, so compaction stays at launch.

## M6: public release (branch `m6-release`)

289. **How A43 measures.** "The average tick time Seasons adds … measured with spark" is read as: Seasons' own work on the server thread, tick by tick, timed by the scenario hooks' tick meter (ADR 0003 M6 amendment): every task it schedules, every listener and every display call, in the server thread's CPU time, so the 20 bots on the same machine don't inflate it. Paper 26.3 bundles spark, so no plugin is added: the scenario runs `/spark profiler` over the same stretch and saves its profile in the server's `plugins/spark/` for a person to read; asserting on it would mean parsing spark's file format. Seasons' admin commands themselves aren't timed (they run when an admin types them, not every tick). The average is over every tick from `/season end --now` to just after Homecoming, with a minute of the Frontier between launch and Homecoming: shorter than any real rollover, whose 10-minute countdown and 15-minute decorating window the scenario skips, so stricter. The game's own one-off cost of the first figure and text display a server ever spawns (loading Paper's classes for them, about 20 ms each) is paid by `/scenario perf warm` before measuring. Drawing displays had to change to pass: a rollover drew every cell in the same tick, about 1 ms each, and a cold or busy server could take 5 ms over one cell. Cells now queue and are drawn a display at a time (the clearing and the figure together, then each other display), a cell's steps before the next cell's, each tick starting a step only while the last one's time still fits in 2 ms. Reconciliation looks again at a cell once a draw under way is done, rather than repairing it half drawn. On the MacBook A43 measures about 0.4 ms a tick on average and 2 to 3 ms for the busiest tick of drawing. Confirm the reading.

The generator is a build tool in the core's tests, so nothing of it ships. The bundled `config.yml` is laid out one setting a line, nested sections in block style, so `hof.entry` and `wand.outlines` are no longer one-line maps; values and defaults are unchanged (a test checks the generated file loads to the same defaults). Command-edited files (seasons, galleries, `hall.yml`, `museum.yml`) hold data only and are written by commands, so the reference doesn't list them; `messages.yml` is its own documentation.
292. **Hangar and Modrinth.** Publishing uses the Hangar publish Gradle plugin and Minotaur (ADR 0006). The projects are `gr33nMari0/SeasonsMC` on Hangar, with `Release` and `Beta` channels, and `seasonsmc` on Modrinth (`hangarProject` and `modrinthProject` in `gradle.properties`); the repository has the `HANGAR_API_TOKEN` and `MODRINTH_TOKEN` secrets. Only the Seasons jar is listed; Seasons Web joins the stores with M7, its jar staying on the GitHub Release meanwhile. Both listings give BlueMap as an optional dependency, and Modrinth the `paper` and `purpur` loaders.
293. **CI across supported versions.** v1 supports 26.3 only, so the scenario matrix stays one version (question 5). The newest-API compile the spec asks for is a `newest-api` job compiling the main code with `-PpaperApi` set to `paperApiNewest` in `gradle.properties` (26.3 for now), which the `build` check requires; deprecations are already errors in every build. When 26.4 ships, `paperApiNewest` moves to it and `minecraftVersions` gains it.
294. **The end's own tick.** A43 bounds the average and drawing, not archiving: the tick that starts archiving copies every online player's gear and advancements at once, about 100 ms of CPU for 21 players on the MacBook. That is one long tick at season end, once a season, while everyone is being moved to their cell; spreading it over ticks would change when each player is archived, which the crash and lock scenarios rely on, so it is left as it is. Raise it if a large server finds it a problem.
295. **The server log (1.1.0).** The spec asks only for "SLF4J logging with structured context" and that secrets are never logged. Read as: every line goes through one logger named `Seasons`, so the console labels it `[Seasons]` rather than with a class name (`core/log/SeasonsLog`). INFO is a short startup summary (`logging.startupSummary`, on by default: version, season, Hall, journal and records, Discord, BlueMap, and a count of setup problems from the config load and `/hof hall check` without reading the world) and one line per milestone (init, end or countdown and its cancelling, one archive summary for everyone archived at the end, a player archived at login, launch, zone unlocks and Homecoming, reloads, curation, the dragon kill, Hall repairs grouped per reconcile pass, and shutdown). WARN is for what an admin should act on; notes that need nothing (the spawn loading at launch, a gate waiting for its cell to empty) now go to online admins without a log line. Repeating warnings are throttled: the tripwire once a minute per player, a Discord webhook once every five minutes, each with a count of those left out; every hit is still audited. Per-player and per-event detail (each archive, each login plan, each zone refusal and Hall interaction, each Discord post and retry, each map publish, each command run) is debug only, written at INFO with a `[debug <area>]` prefix for the areas listed in `logging.debug`, since servers hide the DEBUG level. A webhook is named by host and id with its token left out. `/seasons` is an alias of `/season`, as `/halloffame` is of `/hof`, since owners type it; and `/season info` with no season adds that Seasons is idle until `/season init`. Log lines are English in code, not in `messages.yml`: they are for the owner reading the console, not for players. A43 now also holds Seasons to 20 log lines over its whole run, and `log-startup` and `log-milestones` check the summary and the milestone lines.
296. **Who may open the event stream (M7).** The API table gives `GET /api/v1/events` the access "Player", while the access levels, A48 and the example `web.yml` (`event-feed: public`) make the event feed public. Taken: the stream follows the `event-feed` visibility, public by default, so A48's visitor sees the feed; with `public: false` or `event-feed: players` it needs a login. Open streams are capped per visitor, per account and in all (`stream` in `web.yml`: 2, 4 and 200), so a public stream can't be used to hold the server's threads.
297. **Archived gear as text (M7).** The spec says Seasons describes archived items with Paper's data component API. Taken: Seasons API reads the archive's neutral item data (`core/snapshot/ItemText`): id, count, custom name as plain text, enchantments (stored ones on books too) and trim. It runs on any thread and never makes a real item, which deserialising on a worker would; names are never parsed as formatting. An item from before 1.20.5 shows its id and count only.
298. **Who's online (M7).** A player counts as hidden by a vanish plugin, and is left out, when another online player can't see them (`Player#canSee`; the metadata convention is deprecated API). The region is the nearest shared waypoint within 200 blocks across the ground, or zone in force (inside it, or within 200 blocks of a box or circle; other shapes only from inside), and otherwise the biome's id. AFK is idle for `api.afkAfter` (5 minutes), and the snapshot refreshes every `api.refresh` (30 s), both new settings in `config.yml`, and at every join and leave.
299. **Who is an admin on the dashboard (M7).** Permissions can only be checked for online players, so `seasons.web.admin` is checked when a code is linked, when the player joins and every 30 s while they're online, and kept on their sessions. An admin who loses the node while offline keeps admin widgets until they next join; `/web logout all` ends that at once.
300. **Seasons Web's own records (M7).** Logins, failed codes, lockouts and logouts go to Seasons Web's own audit log, `<world>/seasons-web/audit/YYYY-MM.jsonl`, in Seasons' format, since Seasons API is read-only but for one write: the leaderboard privacy flag, which the data model keeps in the player record (`privacy.leaderboardHidden`), set through `SeasonsApi#setLeaderboardHidden`. Seasons Web's lines are in its own `plugins/SeasonsWeb/messages.yml`.
301. **Login limits (M7).** "At most 5 attempts per IP per minute" is read as both: 5 device codes a minute per visitor's address (`rate-limits.device-codes-per-minute-per-ip`), and 5 wrong codes a minute per account at `/web link` (an in-game player has no address the dashboard can use), after which every code is refused for the rest of the minute. A code already used counts as wrong. Only the browser that asked for a code collects its session: it holds a device secret in an HttpOnly cookie, so someone who sees the code on a screen can't. Polls closer than a second apart get 429. Both cookies use the `__Host-` prefix.
302. **Smaller M7 readings.** The default address is `127.0.0.1:8019` (the owner's choice: TheRanch's example uses 8124). `web.yml` is read at startup (and by the scenario hook); there is no `/web reload`, since the spec lists four web commands. Bare `/web logout` ends the only session, or asks which. Leaderboards before any season answer with empty boards. The dashboard page and the connect page are M7 part 2; part 1 serves a placeholder at `/`. A closed event stream frees its place at its next write, at most 30 s later, since the JDK's server can't see a disconnect sooner.

## M7 part 2: the dashboard and the connect page (branch `m7-dashboard`)

303. **Which link is the map.** The spec's example web.yml has the map as a `links:` entry with `embed: frame`. Taken: the map is the first such link. The map widget shows it and the links widget leaves it out; with `map: hidden` it isn't a link either (`/api/v1/links` leaves it out). No new setting.
304. **"A link if framing is blocked".** A browser can't tell a page's script that a frame was refused, so Seasons Web looks at the map's own headers on a thread of its own, at start and every 10 minutes (`MapProbe`, a GET with the JDK's `HttpClient`, 3 s timeout, nothing sent about players): `frame-ancestors` wins when present, else `X-Frame-Options`, read against `public-url`'s origin (`Framing`). `blocked` and `unreachable` show a card linking to the map; `allowed` frames it; `unknown` (too slow to tell, or no public-url to compare) frames it and falls back to the card after 10 s without a load. A link to the map is always under the frame.
305. **Widgets the API had no data for.** The museum browser, season history, a planned Homecoming and the admin's audit log and pending players had nothing in Seasons API 1.2, so Seasons API 1.3 adds them (additive: `SeasonsApi#seasons`, `museum`, `pending`, `audit` as default methods, and `SeasonView#plannedHomecoming` with the 1.2 constructor kept), and Seasons Web needs `>=1.3 <2.0`. Five endpoints beyond the spec's table, each read-only under `/api/v1`: `dashboard` (the page's settings, always answered), `seasons` (`history`), `museum` (`museum`), `admin/pending` (`pending-players`) and `admin/audit` (`audit-log`). New visibility keys with their defaults: `museum`, `history` and `converter` public, `pending-players` and `audit-log` admins.
306. **Season history.** Seasons keeps no dates for a season once the next has begun, so a season's span is when the first and last of its players were seen in it (from the player records), with its players, its firsts and whether a gallery holds it. Its launch and Homecoming dates are shown only for the season now.
307. **Pending players.** The access levels table gives admins "pending players". Read as: players who played a season that has ended and aren't archived into it yet, such as those offline at the end, whom catch-up archives at their next login; each with the first such season.
308. **The audit log on the web.** "Never served: unpublished coordinates" holds for admins too: Seasons' last 50 audit entries are shown by time, actor, action, target and result, without the details, which can hold positions. Seasons Web's own audit log (logins) stays a file on the server.
309. **"Current rules".** The zones in force, each with its mode now in plain words ("Locked: nobody goes in", "No building", "Entering is announced", "Open"), when Homecoming comes (its date, "when the group votes", or that it has come), and any link whose label says rules. Seasons API gives a zone's mode now, not its condition, so a locked zone doesn't say until when. No rules text setting.
310. **Homecoming countdown.** Shown when Homecoming's condition is a date (`date:`) or a time after launch (`after:`), and not after it has come; Homecoming by vote, the dragon or players reaching the End has no countdown.
311. **Second-screen widgets.** `screens:` in web.yml, as the spec's example has it: each screen is `layout: landscape` (the only layout; another is a warning and the screen is left out) and `widgets`, by the example's names (`season-clock`, `leaderboard`) or any widget's own; an unknown name is a load warning and left out. `/screen` shows `second-screen`, `/screen/<name>` any other. Visibility still applies, so a screen that isn't logged in leaves out player widgets. It refreshes from the event stream and every 30 s, and reloads itself once a day at 04:00 local to pick up a new jar.
312. **The page's text is player-facing,** so it lives in Seasons Web's `messages.yml` under `dashboard.*`, plain text with `<name>` placeholders rather than MiniMessage, and reaches the page through `/api/v1/dashboard`. The public site isn't part of a plugin and keeps its text in its HTML.
313. **Items as text.** A name is the custom name or the item's id in words ("Diamond Sword"); enchantments in words with roman levels, one-level ones without ("Mending"); a trim as "Coast trim, Gold". Nothing from Minecraft's language files is bundled. Icons are ours, drawn for Seasons, one per kind of item (weapons, tools, armour by slot, books, food, potions, blocks and others).
314. **The connect page.** The address typed is the dashboard's (such as `seasons.petepeterepeat.com`), always over https: `http://` and other schemes, user info and junk are refused with a reason. It asks `https://<address>/.well-known/seasons.json` without cookies, accepts only `service: seasons`, `api: v1` and a name, and goes to the `dashboard` it names only when that is https on the same origin, else to the address typed, never a third site. Nothing is stored in the browser; `?server=<address>` connects at once, so a server can link players straight in. The public site's other page says what Seasons is and links to the repository's README and config reference, the releases and the stores; no copy of the docs is kept in `site/`.
315. **Wake lock.** Asked for on load, again whenever the page comes back into view (browsers let go of it while hidden), and once more at the next tap after a refusal; a status dot says whether it holds. Without the API (iPadOS before 16.4) the screen says so and carries on.
316. **Smaller readings.** `/hall` shows the newest gallery and `/hall/<season>` any other. The page's files are served at `/app/<name>` from an allow-list, with strong ETags and `Cache-Control: no-cache`, the same for everyone (never marked private), and count towards the per-visitor rate limit like any request; a page load is about 25 requests, well under the default 120 a minute. Spotify's embed is built from an `open.spotify.com` playlist, album, track, artist, show or episode link.


## M8: reliable links (branch `m8-reliable-links`)

Plan in `docs/plans/m8-reliable-links.md`, approved by the owner on 2026-11-24.

317. **Links are a destination with triggers, amending 248, 249 and 279.** A link has an id, an optional name, a destination (`hall`, `season <n>`, a spot, `point <name>`, `link <id>` for that link's landing, `gallery <id>` for its entry, `return` as `/hof leave`), any number of triggers, an access rule, an optional condition, an optional landing and an optional two-way partner. Triggers: a block clicked (`use`), stood in or on (`step`), or either (`both`); an area passed through (as 279); a floating text clicked, left-clicked with `--left`, or walked into within `--walk`. A link with no triggers is taken only by `/hof link go` and `send`. A destination inside the Hall (a gallery, a point or a link there) is a way into the Hall as the Hall spawn is: /hof's checks but the bed, the spot saved for `/hof leave`.
318. **Click-only by default, amending 248.** A block link made with the new grammar or the wand is `use` (clicked only) unless its block is a pressure plate or tripwire (`step`) or `--trigger` says otherwise; standing on a button, a sign or a block above one no longer takes the link. A plate clicked does nothing of the link's, since a click on a plate does nothing in the game either.
319. **links.yml, and hall.yml left as it was.** `<world>/seasons/links.yml` (schema-version 1) holds the links and named points. At the first start without one, every link in `hall.yml` is copied into it, in the background once their chunks load, and `hall.yml` is not written: its links stay in it as they were (`HallLayout#frozen`), carried through untouched whenever Seasons later writes `hall.yml` for the hub, the Hall spawn or exits, so the previous Seasons, which reads only `hall.yml`, still finds them. No file's schema-version changes, since `ConfigLoader` refuses a newer one, so going back is swapping the jar. A copied link keeps its id, dimension, place and destination, is open to everyone, and its block's kind is `use` for a block whose click does something (Paper's block-kind test, as for 248's take-over), `both` for every other block, pressure plates and tripwire included (they fired on a click in 1.1 too, harmlessly): `links.upgrade.keepStepping` (`non-interactive`, `plates-only` or `all`) is read once, at the copy. The copy records a fingerprint of `hall.yml`'s links; `/hof hall check` reports them changed since (the previous jar edited them), `/hof link upgrade import --replace` copies them again, `forget-old` drops them from `hall.yml`, `report` lists each copied link's trigger before and after, and `done` stops the reminder admins get as they join. The 1.1 forms of `add`, `to`, `move`, `list`, `info` and `remove` keep their replies word for word, and a block link made with them gets the kind the copy would give it.
320. **`hof.links.returnToLink` stays where it is.** The plan moved it to `links.returnToLink`; with config.yml merged over the bundled defaults, a moved key's default would hide a server's own setting, so it stays at `hof.links.returnToLink`, which changes nothing for anyone.
321. **The arrival grace is off by default.** `links.arrivalGrace` holds step and area triggers off after one of Seasons' moves, counted in the 500 ms sweeps (real time, not Seasons' clock, which a test holds still). The trigger a player lands in never fires until they leave it, as 260 had it, which already stops anyone being sent straight back; a grace of a second also stopped a player crossing an area just after an unrelated trip, so the default is 0s. The rate limit for links is `/hof`'s, `hof.entry.rateLimit`, rather than a setting of its own.
322. **Access.** A new link to the Hall or a season's spawn is open to everyone, any other `op`, by `links.access`. `op` asks for `seasons.link.op` (ops by default) or being an operator; `permission` asks for the link's own node or `seasons.link.use.<id>`, and for the latter `seasons.link.use.*` too, since Bukkit has no wildcards of its own (LuckPerms does). Conditions: `always`, `after-homecoming`, `stage frontier|open`, `played <season>` (a record of play in that season). A refusal says "You can't use this link." or "This link isn't open yet." and never names the node. The zone lock, the Intermission rule and the rate limit apply on top, as 249 had them. `seasons.admin.links` is a child of `seasons.admin.hof` in `paper-plugin.yml`, so a Hall admin keeps every link command; the static nodes are declared there, per-link nodes are not registered one by one.
323. **`/hof link send`.** Targets are read by the server from where the sender is (`Bukkit#selectEntities`), so `@p` from a command block is the player nearest it; a name works too. Only players are moved (`links.commandBlocks.playersOnly`); other entities picked are counted in the reply, which a command block keeps as its last output. `--checks none` keeps only the zone lock and the Intermission rule (into the Hall it goes as an admin's own teleport does), `entry` (the default) adds the link's access and /hof's checks but the bed, `full` the bed too. A send isn't rate limited per player.
324. **Past seasons' spawns.** `/season spawn record <season> [position] [yaw]` writes `seasons/<n>.yml`'s spawn for a season before the one in progress; the season in progress and later ones are refused (they are `spawn set`'s), and so is a spot inside the Hall. A past spawn inside an old-world zone is allowed and draws no warning, since each season file's spawn is checked against its own zones only. `/season spawn clear <season>` forgets one. Season history on the dashboard counts seasons from records and galleries, so recording a spawn adds none.
325. **The wand anywhere, amending 253.** A plain right-click with the wand by a Hall or link admin, anywhere, opens the link menu: the block as a link to the Hall, a season's spawn, a point or another link, one way or two, or put aside for the admin's next `/hof link add` with no `from`. In a cell the anchor menu gains a link entry and, on an anchor, Move. In the Hall, for a Hall admin, the menu also sets the Hall spawn, a Hall exit, a gallery's entry and exit on the block in front of the face clicked, and the Hall spawn, a Hall exit and a gallery's entry from the selection, through the commands that set them. A wand click on a block that is a trigger already opens that link's editor.
326. **Exits keep their behaviour.** The plan gave new exits trigger kinds; exits live in `hall.yml` as plain positions, and a kind there would be a key the previous Seasons can't read, so exits fire as before (standing in or on them) and a button meant to be clicked to leave is a link to `return` instead.
327. **The link editor.** Sneak-right-clicking a trigger with an empty hand (`links.editor.sneakClick`), or clicking one with the wand, opens a form for a link admin: where the link leads, its name, who may take it, and buttons to save, lead to where the admin stands, test it, remove the trigger clicked, or remove the link. It is Paper's dialog (`links.editor.ui: dialog`), not marked experimental in the 26.3 builds checked, so 215's reason for avoiding dialogs doesn't apply; each button is a server-side callback that checks again that the admin may edit links, then runs the code of the matching command, audit and undo included. Where the client can't show a dialog, or with `ui: menu`, the buttons come as a choice menu and the link's details in chat. Anyone else sneak-clicking a trigger takes it.
328. **Link text.** Sign lines (`/hof link sign <id> line <n> <text>`, `glow on|off`) and floating text (`/hof link text add|edit|scale|line`) are MiniMessage with only `links.styleTags` kept (colours, gradients, rainbows, decorations, reset, shadow colour); click, hover, insertion, selector, score, NBT and every other tag are stripped and a line is at most 120 characters, so typed text can never run a command. Picking a colour for part of a line is done with tags in the text. Styling needs `seasons.link.text.style`. Writing a sign's text is a block's state, holding no item, so it isn't journalled, as outlines aren't (276); a sign nobody styles keeps the text it was built with.
329. **Link signs.** `/hof link item <id> [count] [player]` gives signs (`links.item`) marked with the link's id; placing one, for a holder of `seasons.link.place`, makes it a `use` trigger of the link and writes `links.item.lines` on it, glowing, and the sign editor doesn't open on it. A builder breaking any link block takes that trigger off its link; a link sign broken by a builder in survival comes back as a link sign rather than a plain one.
330. **Floating text.** A floating text trigger is a text display and an interaction entity, never saved with the world (`setPersistent(false)`), drawn from `links.yml` once a second wherever its chunk is loaded and taken away when its trigger goes or changes; so a restart, a reconciliation or an unloaded chunk can't leave two. The hitbox is sized from the longest line and the scale. Sneak-scrolling the wand at a floating text, as at a plaque, was left for later; `/hof link text scale` sets its size.
331. **Nudging boxes.** A left-click with the wand takes the smallest box holding the block clicked (a cell, a link's area, a point's box, a gallery, the hub) to edit, with the face clicked picked; `/hof sel edit` does the same by name. Sneak and scroll move the face by the step, drop (Q) and `/hof sel step` change the step, `expand`, `contract` and `shift` work on the edited box or the selection, and nothing is written until `/hof sel apply` (or swap-hands, `wand.nudge.swapHandsApplies`), which goes through the command that owns the box (its checks, audit and `/hof undo`); refused, the edit stays for `/hof sel cancel`. Zone boxes are drawn with `/season zone add --replace` as before; nudging them was left for later. A gallery's bounds command now refuses a box over the hub, which would have left `hall.yml` out at the next start.
332. **Anchors seen and dragged.** Every anchor gets an outline in its type's colour, a figure as the 1 × 2 box it stands in, and a label within `wand.anchors.labelRange`; the wand cell's line on the action bar says what it has and lacks, and a cell without a figure says so on its label. Move in the wand's anchor menu picks an anchor up: sneak and scroll turn it by 45°, a right-click puts it down by 227's rule inside its own cell (as one edit, undone by `/hof undo`), a left-click puts it back, and a drop outside the cell, another cell included, is refused. Its page, egg, scale and area come with it. Gate corners aren't dragged (their plane has rules of its own; `/hof cell anchor … gate` sets them), the anchor's facing arrow and carrying the block under an anchor were left for later, and the hold waits until a click rather than timing out. `/hof cell anchors <cell>` numbers a cell's anchors, `anchor move <cell> <type> [#n] <position> [yaw]` moves one, and `unanchor <cell> <type> [#n]` takes one of several off.
333. **Smaller readings.** Link and point ids follow 248's rule. A `--two-way` partner is `<id>-back`, leading to the first link's landing, with the same access. A landing defaults to the free floor nearest the link's first trigger that is in none of its triggers. Removing a link that is paired needs `--both` or `unpair`; one another link leads to needs `--force`, which leaves those leading nowhere, as removing a used point does. Audit entries for links and points name the link or point as their target (`link:<id>`, `point:<name>`), with any position in the details, which the dashboard leaves out (308).
334. **`/hof link go` is taken at the link (review of #40).** The spec says players visit the Hall "from a safe spot next to a bed" (`hof.entry.requireBed: true`), and only a link skips the bed. A link is somewhere in the world, so `/hof link go <id>` from anywhere would be `/hof` without the bed, and a way to any season's spawn. The safest reading: a player takes a link with `go` only within 6 blocks of one of its triggers (a block, a floating text, or an area's box), and its access and rules apply as for a click. Holders of `seasons.admin.links` (or `seasons.admin.hof`) take any link from anywhere, to try it. A link with no trigger is taken only by admins' `go` and by `/hof link send`. Link signs placed from `/hof link item`, and link blocks broken by a builder, also go through the Hall's and the zones' rules for placing and breaking blocks, so neither reaches into locked land or another player's cell.

## M9: dashboard and docs design overhaul (plan in `docs/plans/m9-design-overhaul.md`)

335. **The theme rule.** The spec gives the second screen a dark theme and says nothing else about themes; M9 sets one rule for the public site, the docs and the dashboard (`design/theme.js`). A first visit follows the system (`prefers-color-scheme`), and with no system preference it is dark. The toggle switches dark and parchment light and is kept on that device with the system theme it was chosen against. When the system theme changes, while the page is open or between visits, the page follows the system at once and the toggle's choice is dropped. Second-screen mode stays dark (`data-theme-lock`). Without JavaScript the stylesheet's media query follows the system.

336. **Finding a dashboard from the game address.** The spec's connect flow has the player type "the server's address" and fetches `/.well-known/seasons.json` there. Players know the address they join the game with, not the dashboard's, so the connect page (`site/public/connect/`) reads the typed address as a game address first: it looks up `_seasons.<host>` (and `_seasons.<SRV target>` of `_minecraft._tcp.<host>`) for a TXT record `v=seasons1; url=<https origin>` through public DNS-over-HTTPS (Cloudflare, then Google), then the address itself in case it is the dashboard's, then `https://seasons.<registrable domain>`. A dashboard reached by record or convention must list the typed address (or the SRV target) in a new `gameAddresses` field of its well-known reply before the page goes there; a dashboard from before 1.4, which lists none, is trusted from a record and asked about ("Is this your server?") from a convention; one that lists other addresses is offered only with "Open it anyway" from a record and ignored from a convention. Only when nothing is found does the page ask the public status service `api.mcsrvstat.us` whether the game server is online, to tell "online, no Seasons" from "offline". The page names every service it asks in its privacy note; it sends only the typed address, never to anyone else, and keeps "Recent on this device" (address, name, dashboard) in the browser only, asking a remembered dashboard again each time. `localhost` and IP addresses ask no public DNS. `web.yml` gains `game-addresses` (normalised: lower case, no trailing dot, port 25565 dropped; an IP or junk is left out with a warning) and the additive `gameAddresses` field keeps the API at v1. `/web discovery` (console, or `seasons.web.discovery`, ops by default) prints one record per host; `/web discovery check` looks them up through the same resolvers, off the server thread, and asks the dashboard's own well-known address, sending only the record's name.
337. **Rich previews of dashboard pages.** Each page Seasons Web serves (`/`, `/player/<uuid>`, `/hall[/<n>]`, `/museum`, `/history`, `/help`) carries Open Graph and Twitter tags in its HTML, filled in on the server, since crawlers run no script; with no https `public-url`, or `previews.enabled: false`, it carries only a title. What a preview says is what a visitor who isn't logged in may see under web.yml's visibility: the season and stage need `season`, the online count `online`, a gallery `hall`, the museum `museum`; a player's card names them only when `profiles.summary` is public and they haven't hidden themselves with `/web privacy`, and otherwise reads "A player on <server>". The picture, 1200 × 630, is drawn with Java2D from the bundled design (pixel art read from `design/art`'s SVG rectangles, TrueType copies of the three fonts), at `/og/<kind>/<key>-<hash>.png`, the hash taken over what it shows, so a changed page gets a new address; drawn pictures are kept (64 at most) and at most 20 new ones are drawn a minute, beyond which the address answers 503 with Retry-After. A player's face is cut from their skin, fetched once from `textures.minecraft.net` (the address the profile names, and only that host), unless `previews.skins: false`. `/p/<name>` redirects to that player's profile, or home, through Seasons API 1.4's additive `playerId(name)`. The text lives in Seasons Web's `messages.yml` under `previews.*`.
338. **Help, and dashboards of one's own.** The Help page (`/help`, `/help/<guide>`) and widget show the players' guides from the public docs, bundled into the jar at build time (`site/src/content/docs/docs/players/*.md`, served at `/app/help/`), drawn by a small Markdown reader that makes text nodes only, plus web.yml's `help.links` (https only) and `help.rules`, a Markdown file in `plugins/SeasonsWeb/` up to 64 KiB. It shows to everyone when `public: true`, else only to players logged in, as the rest. A viewer can lay out the home page on a 12-column grid (drag, resize, keyboard moves, add, remove), keep several dashboards, mark one as what `/screen` shows on that device, and copy a layout as a share code or, for admins, as web.yml's `screens:` block. Layouts live in the browser (`localStorage`), never on the server, so the API stays read-only; a layout only arranges widgets, and one this viewer may not see shows "not available" and asks the API nothing.
