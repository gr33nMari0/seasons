# Open questions

Ambiguities found while building, the reading taken, and what to confirm. Newest last.

## M0

1. **Java package and Maven group.** The spec names no package. Taken: `com.petepeterepeat.seasons` (from the play.petepeterepeat.com domain in the runbook), with `com.petepeterepeat.seasons.lib` for relocated libraries. Renaming later is a mechanical refactor, but it changes the persistent-data keys (`seasons:` namespaces are unaffected; only class names move).
2. **Mineflayer trails 26.3.** Mineflayer 4.39.0 (the latest) supports up to Minecraft 26.1. Taken: the bots speak 26.1 and the scenario servers install ViaVersion and ViaBackwards so they can join a 26.3 server. Test servers only; recorded in `docs/adr/0001-viaversion-on-scenario-servers.md`. Drop them when Mineflayer supports the newest drop. Confirm this is acceptable, since bots then see the world through a protocol translation.
3. **bStats plugin ids.** Each jar needs its own bStats plugin id, registered on bstats.org by the owner. Taken: bStats is pinned in `libs.versions.toml` but not yet shaded or started; it is wired in once the ids exist (by M6, the public release). `THIRD_PARTY_NOTICES.md` will list it then.
4. **Curation permission nodes.** The spec says `seasons.curate.*` without naming the leaves. Taken: they are declared in M4 with the curation commands, default `op`.
5. **"Every supported version" in CI.** v1 supports only 26.3, so the spec's `build.yml` (one job) covers it. Taken: `minecraftVersions` in `gradle.properties` lists the versions, and `scenarioTest` runs one scenario server per entry, so adding the next drop is a one-line change. The CI compile against the newest Paper API with deprecations as errors comes with M6.
6. **Branch names.** The repository's first commit is on `master`, while the spec and the workflows use `main`. Taken: M0 is on `m0-skeleton`; rename `master` to `main` before creating the GitHub repository.
7. **Default branch protection and the GitHub repository** are not created by M0; they need the owner's account (`gh repo create seasons --public|--private --source . --push`).
8. **Dependabot and paper-api.** `libs.versions.toml` has two `paper-api` entries: `paper` (`26.3.build.+`, the oldest supported drop) and `paper-mockbukkit` (the exact build MockBukkit was made against). Dependabot can't tell them apart and proposed bumping the MockBukkit one past MockBukkit's own build (PR #6). Taken: Dependabot ignores `io.papermc.paper:paper-api`; `paper` changes when the supported drops change, and `paper-mockbukkit` is bumped by hand with each MockBukkit update. The spec's `dependabot.yml` gains that `ignore` entry.

## M1

9. **Where the planned end lives.** The spec lists it both in `seasons/<n>.yml` (command-editable, `schedule.plannedEnd`) and in the season state (`data/season.json`). Taken: `seasons/<n>.yml` is the source of truth, so `/season schedule end` and a hand edit plus `/season reload` both work. `season.json` keeps a copy, the time it was set and the reminders already sent; when a reload brings a different planned end, the reminders start over as if it had just been scheduled.
10. **Reminders already past, and "at least a week later".** Taken: a reminder whose threshold had already passed when the planned end was set is never sent (setting the end 5 minutes away sends no "10 minutes" reminder). If the server was down through several thresholds, only the nearest one is sent. Changing the planned end starts the reminders over. "At least a week later" describes TheRanch's practice, so a closer planned end is accepted with a warning, not refused.
11. **A restart during the end countdown.** Taken: a countdown that hadn't reached archiving is cancelled by a restart. The season stays Active, the server log and online admins are told, and `/season status` shows when it was interrupted until the next `/season end`. Ending is manual by design, so nothing ends by surprise after a crash. With `schedule.autoEnd: true` the countdown starts 5 minutes after startup, as the spec says. If archiving had already started, the end sequence runs again after journal recovery (archiving is idempotent per player and season) and the season reaches Intermission; offline players catch up at login.
12. **The stage `/season init` records.** The season in progress began before Seasons was installed, so there is no old world to lock. Taken: Active, Open stage.
13. **Line numbers for config errors.** Taken: a YAML syntax error is reported with file, line, column and message, which is what A40 checks. A value that parses but fails validation is reported with file, key path and message, because Configurate's nodes don't keep line numbers.
14. **Discord in M1.** A1 (an M1 scenario) needs reminders "in chat and on Discord", while "Discord webhooks" are listed under M4. Taken: M1 sends reminders through a small webhook sender in `integrations/`; M4 adds season end, awards, firsts, the dragon slayer, launch, Homecoming and the admin webhook to the same sender. Every post sets `allowed_mentions` to nothing, so no text can ping `@everyone`.
15. **Webhooks must be https, in tests too.** Taken: the validation rule stands. The scenario servers trust a self-signed certificate made at test time by `keytool`, and the bot runner hosts an https webhook receiver with it.
16. **A JSON library.** Data files are JSON, but the spec's dependency list has none. Taken: `configurate-gson`, recorded in `docs/adr/0002-configurate-gson.md`.
17. **An invalid config at startup.** Reload keeps the previous config, but at startup there is no previous one. Taken: a broken `config.yml` or `messages.yml` falls back to the bundled defaults (which are the conservative settings, such as `autoEnd: false`), and the problem is logged and shown in `/season status`. A broken season file means no planned end until it is fixed and reloaded.
18. **Scenario isolation.** Scenarios change persistent state (a season can be initialised once, an ended season stays ended), so each scenario file now runs on its own freshly wiped server, and a scenario can ask for several sessions with a server restart between them. Each scenario costs one server start.

## M1 part 2

19. **Cursor and crafting items at archive time.** As the spec says, they go back into the inventory first and the menu is closed. Items that don't fit are never dropped: they stay on the cursor or grid, and the menu stays open (closing it would drop them), until step 4 clears them with the rest. They are archived as the overflow, shown on their own page of the archive view, and checked again before the clear. Because nothing leaves the player before step 4, a crash or a failed write never loses them (the game itself doesn't save the cursor, so a hard crash before step 4 loses only what vanilla would). Unarchive puts the overflow into free slots, and any that don't fit go to the displaced-items file (23).
20. **Players from before Seasons was installed.** A player with no record whose player file existed before is taken to have played the season `/season init` recorded, and is archived into it once it ends. Their baseline is zero, so their archive's statistics are lifetime totals. Nobody gets a record before `/season init`.
21. **Advancements without a display.** Only advancements under `recipes/` count as recipe unlocks and are kept (with `recipes: keep`). Every other advancement, including ones without a display such as a datapack's, is archived and revoked. TheRanch runs no datapacks, so revoking those has no side effects there; a server whose datapacks rely on hidden advancements can set `resets.advancements: keep`.
22. **`/season archive` targets.** Online players only, into the season catch-up would choose (the last finished season they played that isn't archived). It never archives into the season in play, so running it mid-season or twice changes nothing.
23. **Unarchive needs the player online and empty-handed.** With `--force`, whatever the player carries is written to `archives/s<n>/<uuid>.displaced-<ms>.dat` in the same NBT archive format, so a curator can recover it later (curation is M4), and the unarchive is audited. Nothing is destroyed.
24. **New journal kinds.** `UNARCHIVE_STARTED` and `UNARCHIVE_DONE` join the data model's list, so a crash part-way through an unarchive is finished at the player's next login like an archive.
25. **Joins during the Archiving phase** are archived at login, as during the Intermission.
26. **The deaths objective has no scoreboard port.** The spec's port table has none, so `Players#deathsObjective` creates it.
27. **A13 and A14 in M1.** The M1 scenario list includes A13 (firsts) and A14 (season card), but the milestone list puts firsts and season cards in M4. Taken: they move to M4, and M1 is done without them. The data A14 needs (statistics minus the baseline, the furthest block, the advancement count) is already captured in each archive. Owner to confirm. **Decided by the owner (PR #10): rejected.** A13 and A14 stay in M1, built as M1 part 4 (see 55 to 60): firsts are a race from launch day, so tracking has to run when Season 3 launches, and the card lists the firsts. The dragon slayer first stays with the egg in M4.
28. **The tripwire in M1.** The milestone list puts the tripwire in M2, but A9 is an M1 scenario and the archive view ships now. Taken: a minimal tripwire in this part (checks on pickup, on items appearing in the world and on menu close, a 30 s sweep of online players, deletion and an audit entry). Reporting hits to the admin webhook waits for M4; until then each hit is logged as a warning.
29. **Launch celebration.** The spec's launch has a title, a sound and fireworks, and they all ship. A firework with effects can damage whoever stands next to it, so each launch firework carries a `seasons:celebration` tag and any damage it would do is cancelled, for players and every other entity. (An earlier draft dropped the fireworks; the PR #9 review restored them.)
30. **Restored advancements' times.** `/season unarchive` re-awards the archived criteria quietly (no chat announcement), but Paper's API can't set the time a criterion was awarded, so restored criteria carry the time of the unarchive; the archive file keeps the originals.
31. **Unarchive and later seasons.** "For mistakes only" is read as: unarchiving gives the items back and never leads to them being archived again by themselves. Login catch-up never archives into a season earlier than the latest one the player has entered, so unarchiving Season 2 during Season 3 doesn't send their Season 3 inventory into a Season 2 archive. Unarchiving an older season while a later one is archived leaves `archivedThrough` alone, so the later archive is never redone. An admin can still `/season archive` a player whose unarchived season is the one that just ended.
32. **Archive files are never overwritten.** If an archive file for that player and season already exists when archiving writes one (after an unarchive, or a crash before `ARCHIVE_STARTED`), the old file is moved aside as `<uuid>.superseded-<ms>.dat` first, like the displaced and unarchived files.
33. **Launch waits for every online player to be archived.** `/season launch` is refused while anyone online played the season that ended and isn't archived into it, or has an archive or unarchive open in the journal. Otherwise a failed archive would carry its items into the new season. The fix is `/season archive` or `/season reprocess`, or the player logging out (they then catch up at their next login).
34. **Held at login.** A player is held, as during archiving, from the moment they join until recovery and login catch-up have run, usually a tick or two, so they can't drop or hand over items before the checks.
35. **Hidden advancements.** The visible total counts advancements with a display that isn't hidden, as the advancement screen does, and so does the completed count. Hidden ones are still archived and revoked like the rest.
36. **Who owns a cell is kept in the gallery file only.** The data model lists cell owners in the gallery files; the player record doesn't copy them, so there is one place to change and nothing to fall out of step. `/hof gallery info` and `/hof cell info` show them.
37. **Game modes in the Hall.** Inside a gallery's bounds, players are in adventure mode except an owner in their own cell while they may decorate it (survival). Leaving the Hall puts back survival only for players Seasons switched. Creative and spectator players, and holders of `seasons.hof.bypass`, are left alone.
38. **`claim` and `ordered` before M5.** `/hof claim` isn't built yet, so `claim` behaves as `manual` (admins assign) until it is. `ordered` hands out cells in gallery order to players sorted by name. **To be amended by 167** on `m3-finish`, which builds `claim`.
39. **No broadcast when the window opens.** Each player is told their own cell ("Your Hall of Fame cell for Season 2 is c1 in season-2."), as the spec says; there is no extra chat broadcast.
40. **The lock.** `decorating.lockAtEnd: true` closes the window at the end of the countdown, before anyone is archived. An owner archived then (or archived later in the Intermission) gets `decorating.afterArchive` once, from their archive; it is kept in `season.json`, so it survives a restart. `/season decorate close` ends every cell's time at once, and launch ends it too (the next season's state starts with no window).
41. **Swap requests live in memory.** A restart within the 60 seconds drops a waiting request; the player asks again.
42. **An imported double chest** is one container and one archive anchor, at the half its slots start in; the other half is a protected Hall block like any other. Its sixth row doesn't fit beside the page buttons, so it continues on a page of its own.
43. **The imported figure's head.** The owner's player head stays in the record (and on the gear page of the archive view), but the mannequin doesn't wear it: the mannequin wears that head's skin instead, as the spec's table says.
44. **Imported records** have an empty inventory, no advancements or statistics, and ender chest policy `keep`; the player record is untouched (`archivedThrough` stays as it was), since Season 1 predates Seasons. Sign text goes into the record for the season card (M4).
45. **The import saves the world.** A crash after a cell is emptied but before the world is saved would bring the items back into the cell while the record also holds them. So the import saves the dimension right after emptying a cell, before writing `IMPORT_DONE`, and the undo saves it after putting items back and before setting the record aside. Recovery empties whatever still matches the record.
46. **An interrupted undo is left to an admin.** Recovery reports it rather than guessing which items went back; running `/hof import undo` again puts back only what is missing.
47. **Dry-run counts.** A cell already imported is listed as "already imported" and counted as neither ready nor flagged; a cell whose owner already has a Season 1 record is flagged. An item frame's item becomes a trophy anchor at the frame's block.
48. **Display copies are tagged.** The items figures wear and trophies show are copies tagged `seasons:archived`, like the archive view's, so the tripwire deletes any that ever turn up anywhere else.

### PR #10 review fixes

49. **A cell that changes during an import.** The import scans the cells first and empties them later, so a chest emptied, or a stand or frame removed, in between would leave its items both in the record and with whoever took them. Taken: a fresh import stops at that cell, sets its record aside, audits it and changes nothing there. Only recovery after a crash treats an empty source as already emptied (as archiving does for a cleared inventory). If emptying a source fails part-way, the journal entry stays open and the next start finishes the cell.
50. **Unarchiving an imported record.** `/season unarchive` would give back nothing (an imported record has no inventory) and set the record aside where `/hof import undo` can't find it. Taken: it is refused and points to `/hof import undo`.
51. **Game modes in the Hall, amending 37.** Seasons remembers in the player record (`hallAdventure`) that it switched a player from survival to adventure, so a restart doesn't strand them in adventure, and leaving the Hall puts back survival only then. A player already in adventure for another reason stays in adventure, and an owner is put in survival to decorate only if Seasons put them in adventure. Players without a record (before `/season init`) are remembered in memory only.
52. **Gallery files Seasons writes.** A double chest's archive anchor is the half its slots start in if that half is in the cell, else the half that is. Before writing anything, the import checks that the gallery it will save keeps every rule, and stops at that cell if not. **Decided by the owner (PR #10):** a broken gallery file at startup is left out and nothing else is; see 61.
53. **A6 and the zone lock.** A6's "locks the old-world zones" needs the zones, which are M3. Taken: M1 does everything else in A6, and the lock is checked again when zones land in M3. **Confirmed by the owner (PR #10).** A6 runs again in full once zones land.
54. **`/season config get|set`.** It is one of the `seasons.admin.config` commands with zones and markers, and no acceptance scenario covers it. Taken: it ships with those commands in M3. **Confirmed by the owner (PR #10).**

## M1 part 4: season firsts and the season card

55. **What counts as a first.** Each advancement that has a display (so no recipe unlocks), the Nether and the End (arriving in the dimension), and carrying a diamond, an elytra or an item on `firsts.rareItems`. "First diamond" is read as the first to carry one, like the rare items, since a diamond can come from a chest as well as ore. Only while the season is Active, and not for a player held by archiving, unarchiving or login catch-up, so `/season unarchive` giving advancements back never makes a first. The dragon slayer comes with M4.
56. **Where firsts are kept.** In `season.json`, as the data model says, for every season (key, label, player, name, time): after launch the next season starts with none of its own, and earlier seasons' cards still read theirs. The archive record doesn't copy them yet; Seasons Web (M7) can read them from the season state.
57. **The inventory sweep for firsts** runs every 10 seconds, its own task beside the tripwire's 30-second one, so a rare item is noticed well within the 30 seconds the spec allows.
58. **The season card is a book, never an item.** Right-clicking a cell's plaque anchor opens it with `Player#openBook`, so nothing is given, placed on a lectern or left behind. The plaque's text display keeps the name, season and advancement count, and says to right-click for the card. A card for an imported Season 1 cell shows "Season 1 · imported" and its signs, with no statistics.
59. **What the highlights add up.** Play time from `minecraft:play_time`; travelled from walking (on land, on and under water), sprinting, swimming, flying, elytra, boats, minecarts and horses; diamonds mined from diamond ore and deepslate diamond ore; blocks placed from every block item used; blocks mined from every block mined. The four block counts aren't General-tab statistics, so Seasons takes them with the baseline and at archive time under `seasons:` ids, and only the General tab is listed on the card's further pages. Each statistic there is named by the client in its own language.
60. **Statistic ids.** Bukkit still names some statistics by their pre-1.13 names (`play_one_minute`, `chest_opened`). The Paper adapter reports the game's own ids (`play_time`, `open_chest`), which the stats files and the client's translations use. Baselines taken before this change used Bukkit's names; no server ran those builds, so nothing migrates them.
61. **A broken gallery file at startup**, amending 17 and 52. Seasons loads every other file and leaves out only the broken gallery, or a gallery that breaks a rule with another. `/season status` shows the problem, and admins are told a few seconds after they join. `/season end` (and `schedule.autoEnd`) and `/season launch` are refused until it is fixed and `/season reload` succeeds, since the end would otherwise archive that gallery's players without cells; `/hof gallery create` refuses its id, so the broken file isn't written over. A reload still swaps every file in or none, as the spec says.


## M2 part 1: visiting the Hall

62. **The Hall entry.** Plain `/hof` lands at the entry of the newest season gallery that has one. With none, `/hof` is refused ("The Hall of Fame has no entry yet."). Before `/season init` it is refused too, since there is no season and nobody has a record to keep a saved spot in.
63. **`/hof <season>` or `/hof <player>`.** A whole number names a season (that season's gallery entry); anything else is a player, online or by the last name in their record, and lands at their newest cell's entry anchor (else in front of its figure). A player whose name is all digits can't be visited by name.
64. **`/hof` from inside the Hall** moves the player within it with no entry checks except the rate limit, and keeps the saved spot they first left from.
65. **Monsters nearby** uses vanilla's sleeping box (8 blocks across, 5 up and down) around the player, counting any hostile mob (`Enemy`) except a zombified piglin that isn't angry. Paper has no "prevents rest" API, so this is the closest public reading.
66. **Hazards and movement.** Being on fire counts as a hazard (the teleport puts fire out, which would make `/hof` an escape button), and being in water at all counts as swimming. "On the ground" is worked out from the blocks under the player's feet, not from what the client says. The order is: rate limit, cooldown, bed, hazards, movement, monsters, recent damage; the first that fails is the one named, so standing in lava says "lava", not "hurt". The new keys `onGround`, `noHazards`, `cooldown` (0s) and `rateLimit` (5s) join `hof.entry`; missing keys take the bundled defaults, so `schema-version` stays 1.
67. **Entering the Hall another way.** Walking in after Homecoming, or another plugin's teleport, saves the spot they came from as their return point, so leaving takes them back there. Pearl and chorus teleports into, within or out of the Hall are refused; one that would have carried them out returns them to their saved spot instead. Walking or riding in on a mount is refused at the edge.
68. **`/hof leave` with no saved spot** is refused outside the Intermission, since it would otherwise be a free teleport to a bed or the spawn. During the Intermission everyone stays in the Hall.
69. **Teleports out of the Hall.** Any teleport that isn't Seasons' own (admin `/tp`, other plugins) counts as leaving and returns the player to their saved spot. Admins who need to move visitors use `seasons.hof.bypass`. Seasons' own moves (launch, archiving to a cell) never count.
70. **The saved spot is dropped** when a player is archived (they go to their cell) and when they enter a new season, so nobody returns into a season that ended. It is written to the player record at once, before the teleport, not coalesced.
71. **Death in the Hall** isn't handled specially: respawning outside the Hall counts as leaving, so the player is sent to their saved spot. Hall damage rules come with M2 part 2.
72. **Scenario stand-ins for movement.** Mineflayer still trails 26.3 (ADR 0001), so A27's walking, pushing and falling are moves the test plugin makes as the client would (`/scenario move` fires `PlayerMoveEvent`, then puts the player there); the pearl is a real one. Sneak-clicking a bed, using items, dropping and sitting also go through the test plugin (ADR 0003).
73. **A spot return safety would turn down is turned down at `/hof`** (review of #11). Return safety checks more than the entry checks do (magma underfoot, monsters within `hof.returnSafety.hostileRadius` rather than vanilla's sleeping box), and an unsafe saved spot sends the player to their bed or the spawn. So `/hof` also runs the return checks on the spot the player leaves from and refuses with the reason ("This spot isn't safe to come back to (magma)."); otherwise a bed and a magma block would make `/hof` then `/hof leave` a teleport home from anywhere. It comes after the other checks, so their messages are unchanged, and it isn't a setting, since turning it off would reopen that teleport. Return safety now finds the floor just under the feet, so a spot on a slab, a bed or farmland counts as safe.
74. **`/hof leave` works only inside the Hall**, amending 68. A saved spot can be left over outside it (an entry teleport another plugin cancelled, a crash between the teleport back and forgetting the spot); from outside, `/hof leave` would be a teleport from anywhere. A failed entry teleport drops the spot it just saved, and the sweep drops the saved spot of a player it first sees outside the Hall after they join, which covers the crash. Walking back in keeps a saved spot they already have, so stepping out and straight back can't swap it for a spot just outside the Hall.
75. **Bypass holders leaving the Hall** drop their saved spot, since nothing sends them back.

## M2 part 2: protecting the Hall

76. **What visitors may use.** Deny by default: in the Hall a visitor can open a container (as a view-only copy), use anchors and plaques, step on exit plates, sit on cushions, and open wooden doors, trapdoors and fence gates, since "walk into any cell" needs a door to open. Everything else is refused: levers, buttons, beds, workstations, lecterns, signs, cauldrons, composters, note blocks, item frames, armour stands and other entities. A refused click on a block that does something (`Material#isInteractable`) says so and is audited; a click on a plain wall is refused quietly.
77. **What an owner may do while decorating their own cell.** Place and break blocks, place, use and break item frames, glow item frames, paintings, armour stands and cushions, use any block, fill and empty water buckets, light candles and campfires, and open their own containers for real. A container with something in it can't be broken ("Take everything out of it first"), so nothing spills. The owner may pick up items in their own cell while they may decorate it, so what they break comes back to them; everyone else still picks up nothing in the Hall.
78. **Liquids and pistons.** Lava can't be poured anywhere in the Hall. Water flows, and pistons move blocks, only within one cell whose owner may still decorate it; nothing flows or is pushed across a cell's edge, the Hall's edge, or inside a locked cell.
79. **Damage in the Hall**, which question 71 left open. Nothing in the Hall takes damage, players included, except from `/kill` and the void. An entity hit by a player (an owner breaking their own armour stand) is decided by the Hall's rules instead.
80. **Access modes `bounds` and `gate`** aren't built yet. Rather than run as `open`, a config naming them is refused on load and reload with a message saying so. **To be lifted on `m3-finish`** (168, 169).
81. **A decorated pot** has no menu to open. Right-clicking one in the Hall, unless you are its decorating owner, puts nothing in and opens a view-only copy of its one slot instead.
82. **Auditing blocked interactions.** Each refused change or use in the Hall is written to the audit log (`hall-blocked`, the player, the cell or `hall`, `denied`, what and where). The same player doing the same thing in the same place within 10 seconds is counted, not repeated: one entry when it starts and one with the count when it stops. Changes by holders of `seasons.hof.bypass` are allowed and audited the same way (`hall-bypass`).
83. **Reconciliation isn't journalled.** The journal covers items moving; displays only show tagged copies, and a repair is idempotent, so a crash mid-repair is put right by the next pass. Each repair is audited. Reconciliation runs when a chunk's entities load (it never loads chunks itself), every 5 minutes for cells whose chunks are loaded, and on `/hof reconcile`, which loads them. The work is queued and done on the server thread within about 1 ms a tick.
84. **Containers not on `cells.containers`** can't be placed in the Hall, even by a decorating owner, and neither can an ender chest; one already there (built by an admin) opens for nobody but bypass holders. Colours count as the same container: `shulker_box` covers every coloured shulker box.
85. **Cushions** are placed through `EntityPlaceEvent` and broken through Paper's `EntityBreakByEntityEvent`, both present in the 26.3 API.
86. **The tripwire on chunk load.** When a chunk's entities load, item frames, armour stands and items on the ground are checked for archived copies; when a chunk in the Hall loads, so are its containers. A hopper moving an archived copy anywhere is stopped and the copy deleted.
87. **After their archive an owner takes nothing out of their cell** (review of #12, amending 77). The spec says cells lock at the end and containers are view-only from then on ("a stash gains nothing"), and also that owners get `decorating.afterArchive` to arrange their cell (A46). Both hold: in that time the owner still places and breaks blocks, places entities and turns item frames, but their containers open as view-only copies, a block they break drops nothing, they pick nothing up, and hitting or using an armour stand or hitting a frame is refused. Before the end, while the decorating window is open, 77 stands: they open their containers for real and pick up what they break. Otherwise a chest filled before the end, or blocks broken after it, would go with them to the new spawn.
88. **A double chest never reaches across a cell's edge or the Hall's** (review of #12). A double chest's inventory is both halves, so a chest placed outside the Hall, or in a neighbouring cell, beside a cell's chest would open the cell's items. A chest that would join another is refused unless both halves are in one cell its owner may decorate (outside the Hall nothing is decided). One already there, however it came, counts as in the Hall if either half is: it opens as a copy unless the opener may take things out of the one cell holding both halves, and no hopper moves items through it.
89. **Reconciliation finds a cell's displays anywhere in its chunks** (review of #12). A figure pushed out of its cell's bounds is removed when its cell is reconciled, as well as drawn again; one found in a chunk none of its cell's bounds touch is removed when that chunk's entities load. A display of a cell that isn't known, as when a gallery file is left out, is kept until it is.

## M3 part 1: zones and Homecoming

90. **Which season file the zone commands edit.** The runbook draws the old-world zones during Season 2, before launch, so they must go in the next season's file, as `/season spawn set` does; but a zone drawn during the Frontier stage must lock at once. Taken: `/season zone` edits the season being played while its old world is locked (Active or counting down, Frontier stage), and the next season's file otherwise (Season 2 under `/season init`, after Homecoming, the Intermission).
91. **When zones are in force.** A season's zones come from its own file and are in force only while that season is played (Active, or the end countdown), so nothing is enforced before launch, and launch locks them (A6). In the Frontier stage each zone is locked, unless unlocked on its own (question 100); Homecoming switches every zone to its `afterUnlock` mode, those unlocked or locked again on their own included (amended in review, question 109), and a zone locked again after Homecoming stays locked. Archiving and the Intermission enforce nothing: players are in the Hall.
92. **Drawing zones before the wand.** `box` takes both corners as coordinates until the wand comes in M5; with none it says so. `cylinder <radius>` is centred on the block the admin stands on, in their dimension, with `--max-y` and also `--min-y`. A box from the console is in the overworld; a cylinder needs a player.
93. **Shapes `outside`, `y-above` and `y-below`** aren't built in part 1. Rather than ignore them, a season file naming one is refused on load and reload with a message saying so, as access modes were (question 80). **Lifted in M3 part 4** (154): all three are built.
94. **Entry is checked on every move as well as by the sweep.** The spec's sweep (every 10 ticks, a tenth of the players each tick) stays the backstop, but a player's own move into a blocked zone, and a vehicle's with a player in it, is refused the moment the block changes: the move is cancelled, and they are dismounted, stopped and shown the title and action bar. Waiting up to half a second would let someone step in, open a chest and step out.
95. **The last valid position** is where the sweep or a move last saw the player outside every blocked zone. A player found inside goes back there, or to the season spawn if there is no such place or it is now inside a blocked zone (as when a zone is drawn around them or locked again with them in it), and is told why in chat.
96. **A spawn inside a zone** is a warning on reload, validate and startup, not a problem: the file loads, so an unrelated reload isn't blocked. `/season zone add` refuses a zone around the spawn and `/season spawn set` refuses a spawn inside a zone; `/season end --dry-run` names the zone (A41); `/season launch` and its dry run are refused, with a reason that doesn't name the zone (refusal messages only carry season numbers) and points at the dry run.
97. **Block mode inside the zone.** Nothing inside burns, is broken by an explosion (blocks, item frames, paintings, armour stands, animals), or is primed (TNT), even when the cause is inside too, as with lightning; endermen take nothing. Growth, liquids, pistons, hoppers and redstone wholly inside keep running, so farms in old bases still work at Homecoming.
98. **No-build mode, the strict reading.** Breaking crops is breaking, so "use a farm" means its machines (buttons, levers, doors) and their chests, and trading. Hitting an item frame, painting, armour stand or cushion is refused, so items in frames aren't taken by hitting them; other entities can be hit and used. Bone meal, stripping, waxing and lighting are building. The edge rule applies to no-build zones too: nothing flows, is pushed or is moved by a hopper across their edge.
99. **Announce mode.** Once per player, per zone, per day in the server's time zone, kept in memory, so a restart may announce someone again the same day. Posting to Discord as well is `zones.announceToDiscord` in config.yml, off by default.
100. **One zone at a time.** `/season unlock <zone>` and `/season lock <zone>` are built in part 1, since the spec says the manual command always works whatever a zone's condition. What they set is kept in `season.json` for the season and cleared at launch. Unlocking broadcasts "The <zone> is open!" and posts it to Discord; locking again isn't announced. No zone may be called `homecoming`.
101. **Unlock conditions** are checked once a second and at startup, so a date that passed while the server was down unlocks then. Homecoming unlocks every zone whatever its own condition ("every old-world zone switches to its afterUnlock mode"); a zone whose own condition comes true before Homecoming unlocks alone. `after` counts from the season's launch.
102. **Milestones.** `dragonKilled` holds once any ender dragon dies while the season is played; `playersReachedEnd` counts the different players who arrived in the End this season. Both are kept in `season.json`.
103. **What zones don't stop.** Redstone signals across an edge, and mobs and items wandering out of a zone by themselves (portals they can't use). Everything else the spec lists is stopped. (Amended in review: picking up an item lying just inside a blocked zone's edge is stopped after all, question 110.)
104. **Auditing.** Refused interactions with a zone are written as `zone-blocked`, and bypass holders' as `zone-bypass`, a repeat within 10 seconds counted as in question 82.
105. **Homecoming and the journal.** Like launch, Homecoming moves no items, so it has no journal kind: `season.json` (Open, `homecomingAt`) is saved first and the titles, fireworks, broadcast and Discord post follow only once it is on disk. A crash after the save leaves the zones unlocked and doesn't repeat the fanfare.
106. **`/season zone list`** shows the zones in force (the season being played) as well as those of the season the commands edit, when the two differ, each with the mode in force now; zones not yet in force show off.
107. **A player who logs in inside a blocked zone** is found by the sweep within half a second of joining, after any archive catch-up (players held by it are skipped), not by the join event; one who respawns inside is found the same way.
108. **Vehicles.** A boat's or minecart's move with a player in it is the player's move: refused, both go back where they came from and the player is dismounted. A ridden animal that isn't a vehicle to the server is caught by the sweep.
109. **Homecoming opens every zone** (review of #13, amending 91). The spec says every old-world zone switches to its afterUnlock mode in the same tick, so Homecoming clears what `/season unlock <zone>`, `/season lock <zone>` and zones' own conditions set before it. The milestones (the dragon's death, players who reached the End) are kept. After Homecoming, `/season lock <zone>` locks one zone again, as the spec's command table allows.
110. **Taking across the edge** (review of #13). A pickup does carry a position: the item's. A player can't pick up an item lying in a blocked zone, as from just outside its edge, unless they hold the bypass; the refusal is quiet, since the game asks every tick, and audited as `zone-blocked` with repeats counted. Reeling in an entity or item with a fishing rod is using it, so it is refused in a blocked zone and allowed in a no-build one. A player's hit on any entity, by hand or by projectile, is decided wherever it is, not only in the Hall: in a blocked zone every hit from outside is refused, and in a no-build zone hits on item frames, paintings, armour stands and cushions are refused, so a frame's item isn't knocked out and a stand's gear isn't dropped. Minecarts and boats are decided through their own damage event, and inside a blocked or no-build zone nothing but a player breaks them.
111. **Auditing zones** (review of #13, extending 104). Besides refused and bypassed interactions: every refused entry (walking or riding in, a teleport, a portal trip and its arrival, a new portal, a player the sweep finds inside) as `zone-blocked`, repeats counted; Homecoming (`homecoming`, by the admin who ran it or by Seasons when its condition came true); one zone unlocked or locked again (`zone-unlock`, `zone-lock`); and every `/season zone add`, `mode`, `after` and `remove` as `config`, with the path in the season file, the old value, the new value and who.
112. **Zone dimensions** (review of #13). The spec's validation rule "every dimension id exists" applies to zones: a season file with a zone in a dimension the server doesn't have is refused on load and reload, since the zone would lock nothing.
113. **Portal trips** (review of #13). On Paper 26.3 a nether portal trip fires `PlayerPortalEvent` before the game looks for a portal at the other end, then teleports the player to the portal it found with the `NETHER_PORTAL` cause, so a trip whose exit is an old portal inside a blocked zone is refused at that teleport (a30-real-portal, a real portal trip). As a backstop, a player who arrives in a dimension inside a blocked zone is put back where they last stood outside, at once rather than at the next sweep.

## Faster scenario suite

114. **Seasons' sweeps and the scenario clock.** Seasons' sweeps (the tripwire every 30 s, season firsts every 10 s, the Hall, visits, zones, reconciliation, the season tick) run on the server's scheduler, not on Seasons' clock, so moving the clock alone would leave them to come round in real time. On scenario servers only, Seasons' scheduler is wrapped so that moving the clock runs every delayed task that came due and every repeating task whose period passed, once each however many periods were skipped, as the next run would have. Real servers use the platform's scheduler unwrapped.
115. **The Paper jar for shards.** The shards boot Paper themselves, several at once, which run-paper's `RunServer` can't (Gradle won't run tasks of one project side by side without the configuration cache), so `scenarioTest` runs each shard in a Gradle worker (`buildSrc`, plain Java on the Gradle API). The spike worked: the Paper jar and the Via jars come from run-paper's own cache through its public download services (`DownloadsAPIService.paper`, `PluginDownloadService`), so the Paper build is not pinned. Paperclip unpacks Paper once into a folder the shards share (`bundlerRepoDir`).
116. **Docs-only changes.** CI skips the scenario shards when every changed path is under `docs/`, a Markdown file at the repository root, or `LICENSE` (`.github/scripts/docs-only.sh`). An empty or unknown change runs them. The final `build` job passes a skipped shard only for that reason.
117. **Branch protection.** At this change `main` had no branch protection (the API answered 404), so no check name was required yet. The final job keeps the name `build`, the check the spec's GitHub step 2 asks for; protecting `main` with it is left to the owner.
118. **Fresh mode is sharded too.** `-PscenarioIsolation=fresh` gives every scenario a freshly wiped server of its own, as before, but runs the shards side by side, so the nightly run takes minutes rather than the old 21.
119. **What a fresh server is.** A scenario server's fresh boot removes the animals the world generated before the first scenario, so every scenario, first or not, starts without them, in fresh mode too (any scenario server can reset, and its leak check compares with that fresh boot). No scenario depends on them.
120. **Gradle's downloads in CI.** setup-gradle's cache is written only on `main`, so on a pull request every job started empty and the six jobs fetched every dependency from Maven Central at once; Central answered 429 and a shard failed. The jars job now saves Gradle's downloads (`~/.gradle/caches/modules-2` and the wrapper) under a key of the build files' hash, and the shard and final jobs restore them.
121. **Every scenario ran in CI** (review of #14). Passing shard jobs alone don't show the suite ran: a shard count that differs from the matrix, or a shard that ran nothing, would leave scenarios out with every check green. The shard jobs take the count from the matrix (`strategy.job-total`), and the final `build` job runs `:testkit:scenarioCoverage`, which fails unless every session of every scenario file has a passing result on every supported version. A full local `scenarioTest` runs it too.

## M3 part 2: the ender vault and pets

122. **When season pages can be withdrawn from.** "Withdraw-only after Homecoming" is read as: while the season being played is in its Open stage (Active, or counting down from Open). In the Frontier stage, and between seasons (archiving and the Intermission), every season page is read-only, older seasons' pages included: they are old-world storage too, and anything taken during the Intermission would be carried into the next season. The Returned page can be withdrawn from at any time, except while the player is held for archiving.
123. **Which clicks withdraw.** A left click or a shift click on an item takes the whole stack. Every other click (right, number keys, the off-hand swap, drops, drags, double-clicks, creative clones) is refused like any click in a view-only menu and moves nothing. Nothing can be put in. After each withdrawal the menu opens again on the same page, built from the vault file.
124. **The withdrawal transaction.** Per click, queued per player and with the player held throughout: save the player's file, journal `VAULT_WITHDRAW` (the vault page as its season, 0 for the Returned page, and the inventory's hash before), take the item out of the vault file with a withdrawal id, give it whole or not at all, save the player's file, then journal the new kind `VAULT_WITHDRAW_DONE`. A failed give (full inventory, or they left) puts the item back in its slot. Recovery after a crash: if the vault file never recorded the withdrawal, nothing moved; if it did and the player's saved inventory still has the hash from before, the give didn't stick and the item goes back; otherwise it was given and saved. The vault file keeps each withdrawal (page, slot, time, item) as its withdrawal history.
125. **Unarchive and the vault** (a dupe found while planning). `/season unarchive` used to restore the ender chest from the archive's copy, which after withdrawals would hand back what had already been taken out. It now restores the vault page as it is now, and removes that page before moving the archive aside, so a crash between the two can't leave a page holding what the player was just given.
126. **An empty vault.** `/vault` with nothing in any page says "Your ender vault is empty." and opens nothing. After the last withdrawal the menu still opens again, empty, so the player sees the item gone.
127. **Removal reasons.** On Paper 26.3 `EntityRemoveFromWorldEvent` with `Entity#getRemovalReason`: only `KILLED` is final, a death ("died") that drops the registration at once. Every other reason, `DISCARDED` included, only updates the last known position and leaves the registration for travel to settle, since an animal discarded can come back: a parrot landing on its owner's shoulder is discarded and returns, same id, when it hops off (review of #15; see 136). Registered pets carry a `seasons:pet` mark (their owner's id), so only they are looked at. At shutdown Seasons records where every loaded registered pet stands, since unloads after it go unheard.
128. **Telling an offline owner.** A death or removal while the owner is offline is kept in their player record (`notices`) and shown at their next login, once.
129. **Names.** A pet keeps its name tag's text, as plain text; an unnamed pet is named from its type ("Wolf", "Skeleton Horse"). A name already used by another of the owner's pets gets the lowest free number: "Wolf 2". `/pet remove` matches names ignoring case.
130. **Who can register what.** The animal the player looks at within 5 blocks (`LivingEntity#getTargetEntity`), tamed by them as the game records it. Refusals, in order: not looking at anything in reach; not a tameable animal ("A villager can't be tamed"); not tamed; tamed by someone else; already registered; carrying a chest; at `pets.maxPerPlayer`. Registration is open while a season is played (Active, or the end countdown) and closed from the end until the next launch; `/pet list` and `/pet remove` always work. With `pets.enabled: false` `/pet add` is refused.
131. **When pets travel.** A pet travels once its owner has entered a later season than the one it was registered in: right after they reach the new spawn at launch, or after their login catch-up (archived, then sent to the spawn). Each login after catch-up also tries again for pets still due, which covers an owner who left part-way or a crash. A pet registered after launch waits for the next season. Pets travel one at a time, to where the owner stands.
132. **What travel does with each pet.** Found at its last known position (the chunk loaded asynchronously with a plugin ticket, waiting up to 5 seconds for its entities) or already loaded anywhere: still the owner's, no chest, then unleashed, taken out of any vehicle and off anything riding it, `PET_TRAVELLED` journalled, and teleported. A pet carrying a chest stays behind ("animals carrying chests can't travel"), one that can't be found is reported, and one now owned by someone else stays behind; all three are dropped, since registrations clear after travel. Only if the owner leaves part-way does a pet stay registered, for their next login. A pet inside a locked zone travels like any other: Seasons moves it, so no zone check applies.
133. **`PET_TRAVELLED` needs no recovery.** Pets aren't items, and travel is safe to run twice: the registration is dropped only after the teleport, so a crash before then means the pet travels at the owner's next login. The journal entry is written before the teleport, as every world change's is.
134. **`/season status` and pets.** After a launch, while the season is played, status shows "Pets: N waiting to travel": pets registered in an earlier season and not yet brought.
135. **Scenario stand-ins** (ADR 0003). A summoned animal is tamed with `/scenario tame` (the game's own taming needs a bot to feed it), given or relieved of a chest with `/scenario chest`, and put on a lead with `/scenario leash`. "Can't be found at travel time" is staged with `/scenario forget-pet`, which takes the `seasons:pet` mark off so a later `/kill` goes unnoticed, as when a pet's chunks are regenerated. Bots are aimed from the eyes with `/execute ... anchored eyes facing entity ... run tp`, since `/tp ... facing` aims from the feet. Player bots' commands in the pet scenarios are paced, since the game kicks a player who isn't an op for chat spam.
136. **Parrots on a shoulder** (review of #15). A registered parrot discarded within 3 blocks of its online owner, in the same world, is taken to have landed on their shoulder: the registration stays, marked `onShoulder` in the player record, and nobody is told anything. If travel then can't find it in the world, it is on the owner's shoulder and already with them, so it counts as come. Its next unload clears the mark. The shoulder itself isn't read, since `HumanEntity#getShoulderEntityLeft` is deprecated and the build treats deprecations as errors.
137. **No registering across a locked edge** (review of #15). `/pet add` asks the zones about the animal as it would about any entity a player uses (`Intent.UseEntity` at the animal's position), so a pet inside a blocked zone can't be registered from outside it before Homecoming, with the zone's edge message; a holder of `seasons.zone.bypass` may, as they may reach in. Otherwise a horse left in an old base would leave the old world early, saddle and armour included. After Homecoming, or in a zone left open, it can.
138. **Unarchive holds the player first** (review of #15). `/season unarchive` takes the player's hold before reading the archive and the vault page, and keeps it to the end, so no vault withdrawal can change the page or the inventory between the read and the restore. A player already held (a withdrawal under way) gets "busy".
139. **A withdrawal that fails part-way** (review of #15). If a withdrawal stops before its item is given while the server runs on (an exception, a failed write), the item goes back in the vault at once and `VAULT_WITHDRAW_DONE` closes it, rather than waiting for recovery at the next login, which would judge it by an inventory the player has changed since. Journal recovery tells withdrawals apart by their id, the start of each entry's payload, as well as by player and page, so a later withdrawal from the same page never hides one still open.

## M3 part 3: BlueMap, spawn candidates and shared waypoints

140. **Where shared waypoints live.** The spec keeps markers "in Seasons' data" but names no file for them. Taken: `<world>/seasons/markers.yml`, a command-editable file like the season and gallery files, in the world folder so a world backup carries it. It is read and validated with every other file (a set or name that doesn't make sense, two names that differ only in case, a position that isn't three numbers, or a dimension the server doesn't have is a problem), written with backups, and a hand edit takes effect on `/season reload`. The map shows only what Seasons' files hold, so BlueMap's own files never matter.
141. **What `<set>` is.** Each set (`megaprojects`, `hubs`) is a marker set of its own on BlueMap, beside Seasons' own `Seasons` set, so players can switch them on and off separately; its label is its id. `/season marker remove` takes the set and the name, as add does. A name is the rest of the line, 1 to 64 characters, plain text (never formatting, and escaped wherever BlueMap would read HTML), and names in a set are told apart ignoring case. There is no `/season marker list`, since the spec lists add and remove only; BlueMap and `markers.yml` show them.
142. **Which spawns are shown.** "Season spawn points" are the spawns of seasons that have launched: the season being played (or just ended) and every earlier one with a spawn in its file. The next season's spawn appears at its launch, not when it is set, so `/season spawn set` at a spot nobody voted on reveals nothing early. "Spawn candidates before launch" are the next season's candidates, shown until it launches; the one chosen stays shown as a candidate until then. Candidates stay in the season's file afterwards, as the spec's example file shows.
143. **Which zones are shown.** The map mirrors what is enforced: each zone in force, styled by its mode now. Locked (`block`) and no-build zones are areas as the spec says; an `announce` zone is shown too, as its own style, since it is locked until it unlocks; a zone that is `off` isn't shown. So nothing is shown before launch or between seasons (no zone is in force; the next season's zones appear at launch), and Homecoming replaces locked areas with no-build ones, or removes them, in the same second the zones change. Areas are extruded between the zone's y limits, or the dimension's build heights where it has none; the Hall's galleries and the zone's own exemptions are cut out of them. Map Link does bring these areas onto Xaero's maps: it reads BlueMap's `shape` and `extrude` markers as areas, flat (it reads no heights), holes included, and drops any area larger than its `maxChunkArea` (164; [thebuildcraft/MapLink at 595f7f4](https://github.com/thebuildcraft/MapLink/tree/595f7f4cc24bfc55f332f47da149c90737216bca), `BlueMapConnection`, `BlueMapMarkerSet`). **Decided.**
144. **The Hall and the museum.** One point for the Hall where plain `/hof` lands (the newest season gallery's entry, else the middle of its floor), and one per museum gallery (its entry, else the middle of its floor).
145. **Candidates stay out of zones, as the spawn does** (96). `/season spawn candidate add` refuses a spot inside one of the next season's zones, and `/season zone add` refuses a zone around a candidate in the file it edits, as it does around the spawn; the remedy is to remove the candidate. A hand edit that puts a candidate inside a zone loads with a warning. A candidate (and a waypoint) in a dimension the server doesn't have is a problem on load, by the validation rule that every dimension id exists; the spawn's dimension is still checked at launch, as before.
146. **The 24,000-block rule.** It applies to overworld spawns, since strongholds are an overworld thing: a spawn whose block's middle is more than 24,000 blocks from 0, 0 across x and z. It is a warning only: on `/season spawn set`, on `/season spawn candidate add` (a candidate may become the spawn), in the candidate list, on startup, reload and validate, and in `/season end --dry-run` (A41). Distances are measured as the furthest block's are, from the block's middle and rounded down.
147. **Publishing.** Once a second, on the server thread, Seasons checks whether the files or the season state are new objects (every reload, command edit and state change makes one), builds the model only then, and hands it to BlueMap only if it differs. A publishing thread of its own takes the latest model, resolves each dimension's BlueMap world from Paper's `World` (looked up on the server thread), and replaces Seasons' sets on every map of that world (a candidate's preview map included), leaving every other plugin's sets alone. A failure is tried again after 1, 2, 4 and 8 seconds. BlueMap drops API markers on reload and then starts its API again, which is when Seasons publishes again; when Seasons stops (or a scenario resets it) it stops listening and takes its sets down. Nothing relies on a set being hidden by default, since Map Link ignores that flag.
148. **Text on the map.** Labels come from a new `map:` section of `messages.yml` as plain text. BlueMap escapes a marker's label itself, but shows its detail as HTML, so Seasons escapes the detail (the label again).
149. **Spawn edits are audited.** `/season spawn set` now goes through the same edit path as the zone commands (`ConfigEdits`), so it is audited as a config change (`seasons/<n>.yml spawn`, old, new, who) like candidates (`spawnCandidates.<name>`) and waypoints (`markers.yml sets.<set>.<name>`).
150. **Without BlueMap, or with the wrong one.** With no BlueMap plugin Seasons never touches BlueMap's classes (they are on its classpath only when BlueMap is installed) and publishes nothing; `/season status` says so, and `/season marker add` says the waypoint shows once BlueMap is installed. A BlueMap whose API doesn't link logs a warning and publishes nothing.
151. **Testing against a real BlueMap** (ADR 0004). One scenario, `m3-bluemap`, runs on a server of its own with BlueMap 5.29, set to download the game's client jar (it starts its API only with it) and to run without its web server. Every other scenario server has no BlueMap.
152. **A command edit that doesn't take is put back** (review of #16). `ConfigEdits` wrote the file, then loaded every file, and left the file changed when the load failed: the admin heard "wasn't saved", nothing was audited, and the change went live at the next successful reload. Worse, a waypoint added by command beside a hand edit not yet reloaded (`tower` by hand, `Tower` by command), or two admins adding the same name at once, could leave a `markers.yml` the load refuses, which stopped every later reload and, at the next start, every other file (153). Taken: on the writer thread, the file is read before the edit and, if the edit or the load fails, put back as it was (or removed, if there was none) before the writer takes the next edit, so a command edit is on disk only while it is in force. The backup the edit kept is of that same content. The reason the admin hears is the first problem worded as `/season reload` words it. This holds for the zone, spawn and marker commands alike.
153. **A broken `markers.yml` at startup is left out** (review of #16), amending 17 and 61. A `markers.yml` with a problem took every file down with it at startup, the season files included, so after a restart no zone was in force and the old world was open before Homecoming. Taken: like a broken gallery file, it is left out at startup and nothing else is. No shared waypoints are shown, `/season status` shows the problem, admins hear about it a few seconds after joining, and `/season marker add|remove` refuse until it is fixed and `/season reload` succeeds. A reload still swaps every file in or none, so it fails until then. Unlike a broken gallery, it doesn't hold `/season end` or `/season launch`: waypoints play no part in a rollover.

## M3 part 4: the outside and height shapes, and /season config get|set

154. **The `outside` shape is a footprint** (lifting 93). "Outside of a circle or box" is read across x and z: an `outside` zone holds every column beyond its circle or box, at every height, and has no y limits of its own (`y-above` and `y-below` are for heights). In a season file it is `shape: { outside: { circle: { center: [x, z], radius: r } } }` or `{ outside: { box: { min: [x, z], max: [x, z] } } }`. A circle counts blocks as the cylinder does (a block is inside when its middle is within the radius), so `outside circle r` holds exactly the blocks `cylinder r` with the same centre leaves out. A box holds both its corners, so its outside starts one block past them. Season files naming `outside`, `y-above` or `y-below` are no longer refused.
155. **`y-above` and `y-below` include their y**, as `minY` and `maxY` do: `y-above: 128` holds y 128 and up, `y-below: 127` holds 127 and down, so the nether roof rule can be written either way. Both cover the whole dimension across x and z. A y beyond the dimension's build heights isn't refused: it holds no block, or every block, and then the spawn check refuses or warns.
156. **Drawing them by command.** `outside circle <radius>` is centred on the block the admin stands on, as `cylinder` is, so only a player can run it; `outside box <x1> <z1> <x2> <z2>` works from the console too (in the overworld) and, with no corners, says to give them until the wand comes in M5; `y-above <y>` and `y-below <y>` are in the admin's dimension, the overworld from the console.
157. **Validation through the zone's own shape.** The spawn and candidate checks of 96 and 145 ask each zone whether it holds the spot, so they hold for every shape with no new rule: for an `outside` zone the spawn must be inside its circle or box, and for a height zone below a `y-above` and above a `y-below`. `/season zone add` refuses a zone of any shape that would hold the spawn or a candidate, `/season spawn set` and `candidate add` refuse a spot inside any zone, and a hand edit loads with a warning.
158. **Outside zones on the map.** An `outside` zone in force is shown as a ring: its circle or box as a hole, out to an outer edge `max(2 × radius, 5000)` blocks beyond it (a circle around a circle, a rectangle around a rectangle; a box's radius is half its longer side), not to the edge of the world. Map Link copies BlueMap's areas onto Xaero's maps (164), and an area reaching the world's edge could never be shown there or drawn sensibly on BlueMap; the ring shows the frontier where players meet it. The marker sits at the circle or box's centre, where its label belongs. Exemptions and Hall galleries wholly beyond the inside and wholly within the outer edge are holes too; one that crosses either edge isn't, since crossing holes break the area's shape, though the zone is enforced there all the same, and the zone beyond the outer edge is enforced but not drawn. Map Link still leaves a ring out when its bounding boxes pass `maxChunkArea` (164): with the defaults only a ring around a circle of radius up to about 600 blocks fits; a larger frontier shows on BlueMap only, and the frontier border (160) is the in-game way to see it. **Decided.**
159. **Height zones aren't on the map.** A `y-above` or `y-below` zone covers every column, so as an area it would cover the whole map: BlueMap's top-down view would show every block of the dimension as locked, and Map Link, which reads no heights and drops an area that large (164), wouldn't show it on Xaero at all. Players meet one at its height, through the title and the action bar, and `/season zone list` shows it. **Decided by Peter** (review of #18): height zones stay off the map.
160. **The frontier border.** `zones.frontierBorder` in config.yml, off by default. Only an `outside` circle whose mode now is `block` gets one: the game treats a border as a wall a player can't walk through, so a border on a zone players may cross (no-build, announce, off) would stop them where the zone doesn't, and for the same reason it is drawn around the circle, never inside it. The border is the smallest square holding the circle and the zone's own exemptions; Hall galleries are left out, since players reach them by `/hof`, not on foot, and in the Hall they are outside the square. With several such zones in a dimension, the smallest square is shown: it holds every spot inside all of them. A player sees it only in that dimension, standing inside the square, without `seasons.zone.bypass`; everyone else is given back the world's border, so nobody sees one from the wrong side. The sweep keeps each player's border right (within half a second, so after `/hof`, a portal or a teleport too); a change of dimension or a respawn, where the game sends the client the world's own border, sends the frontier's again at once (review of #18: before, a player who died and respawned inside the square kept the world's border until the zones changed); everyone's is checked as soon as the zones in force change (reload, launch, Homecoming, one zone unlocked or locked), a packet goes only when a player's border changes, and everyone gets the world's back when Seasons stops. The world's own border is never read or changed.
161. **`/season config` reaches config.yml only.** Its settings by key path, as the bundled config.yml lists them (`hof.entry.cooldown`); a section (`hof.entry`) lists each of its settings with `get` and is refused by `set`; `schema-version` isn't a setting. Season files, galleries and waypoints have their own commands, and messages.yml and secrets.yml are edited by hand. `get` shows the value in force as the file (or the bundled default) writes it.
162. **Set writes in place.** Configurate doesn't read YAML comments, so saving config.yml through it would wipe its documentation and the admin's notes. `set` changes only the value's characters (a value on the lines below its key, such as a block list, is moved onto the key's line), adds a key the file lacks under its section, making missing sections, and keeps every other byte; YAML anchors, aliases, merge keys and several documents are refused with a request to edit by hand (ADR 0005, SnakeYAML). The value is read as one YAML value and written back in flow style, quoted only where needed; one that equals the setting's text now changes nothing. Then it goes through the edit path the other command edits share: every file loaded and swapped in, put back with the reason if anything fails, a backup kept, and audited as `config.yml <path>`, old, new and who. A hand edit not yet reloaded goes live with it; a broken one makes `set` fail, with the reason as `/season reload` words it.
163. **Secrets.** Only config.yml's settings are reachable, so secrets.yml and the environment never are, and neither is anything else pasted into config.yml (a key the bundled file doesn't list is "no setting"). A path naming a secret (`discordWebhook`, `adminWebhook`, `secrets.*`, or any path containing `webhook`, `secret`, `token` or `password`) is refused for `get` and `set` before anything is read, pointing at secrets.yml. Paper logs every command a player types, so a URL typed into `/season config set` is in the server log before Seasons refuses it, and nothing Seasons does can take it out again; so the refusal (`config.secret`) also says "If you typed one here, it is now in the server log; rotate it." **Decided** (review of #18).

### Map Link, identified (after #18)

164. **What Map Link does.** The spec's Map Link is [thebuildcraft/MapLink](https://github.com/thebuildcraft/MapLink), formerly Remote Player Waypoints for Xaero's Map: a client-only mod, nothing on the server. Its own description: "Synchronizes player positions, marker positions and area overlays from Bluemap, Dynmap, Pl3xMap or Squaremap with Xaero's Minimap and Worldmap." Read in its source ([thebuildcraft/MapLink at 595f7f4](https://github.com/thebuildcraft/MapLink/tree/595f7f4cc24bfc55f332f47da149c90737216bca): `connections/BlueMapConnection`, `mapUpdates/BlueMapMarkerSet`, `clientMapHandlers/XaeroClientMapHandler`, `ModConfig`) in the review of #18, which asked whether it only syncs player positions. It doesn't: **it imports marker sets, points and areas both.** **Decided**; what it does, against what Seasons publishes:
    - It reads BlueMap's public web map over HTTP, as each player configures it: `settings.json`, then each map's `maps/<map>/live/players.json` and `live/markers.json`. So BlueMap's web server must be reachable from players (TheRanch: map.petepeterepeat.com), and it shows what BlueMap's web map serves, players hidden there included. Seasons' scenarios read the markers through BlueMap's API on a BlueMap with no web server (ADR 0004), so they show what BlueMap holds, not what its web map serves.
    - Players: shown on Xaero's maps from `players.json`.
    - Points: `poi` and `html` markers become waypoints, by label, with their icon. Seasons' spawns, candidates, Hall, museum and shared waypoints are all points, so all of them appear.
    - Areas: `shape` and `extrude` markers become area overlays: the outline and every hole, with their line and fill colours; heights aren't read, so an extruded area is shown flat (143). Line markers (and any other type) are left out; Seasons publishes none.
    - A marker set's `defaultHidden` isn't read (its model has no such field), so a set hidden by default on BlueMap still shows on Xaero; a player chooses sets and markers in Map Link's own settings (147).
    - Each area is rasterised into Xaero chunk highlights on the player's machine, and an area whose bounding boxes (its outline's plus each hole's, in chunks) add up to more than `maxChunkArea`, 500,000 by default (about 11,300 blocks square), is left out altogether. So a height zone never could show (159), an `outside` zone shows only as a small ring (158), and a large circle doesn't show: TheRanch's `old-world` at a radius of 12,000 is about 2.25 million chunks, so with Map Link's defaults it appears on BlueMap but not on players' Xaero maps. Seasons publishes each zone as one area, as the spec says, and doesn't split it; a player who wants it on Xaero raises `maxChunkArea` in Map Link's settings (about 2,500,000 for a 12,000-block circle, which costs memory and a few seconds of rasterising), and the runbook's check before launch should look at the old world on a Xaero map with Map Link.

## Finishing M0 to M3 (branch `m3-finish`)

165. **What is left of M0 to M3.** An audit before the first beta (`docs/progress.md`, this file, the TODOs in the code, and the spec's command, permission and config tables against what is built) found these unbuilt or only partly built within M0 to M3: access modes `bounds` and `gate` with the gate anchor (80), `/hof claim` and `claim` assignment (38), a gallery's own assignment, access, decorating and renderer, the armour-stand figure and a figure's pose, the launch button, `/season audit`, the archive status in `/season info`, item ids checked in config.yml, `launch.requireManual`, and the last valid position in the player record. They are built on `m3-finish`; the plan is `docs/m3-finish.md`. Everything else unbuilt is placed in M4 to M7 by the spec's milestone list or by this file, and is listed under On hold in `docs/progress.md`. Question 38's heading ("before M5") doesn't put `claim` in M5: M5 is the wand, templates and stamping.
166. **A gallery's own settings.** The spec lists assignment strategy, access mode, decorating window and renderer choice among a gallery's fields, while config.yml has `cells.assignment`, `cells.access` and `decorating`. Taken: a gallery file may set `assignment`, `access`, `renderer` and `decorating: { lockAtEnd, afterArchive }`, and whatever it leaves out comes from config.yml (`renderer` from `mannequin`). `decorating.opensBefore` stays server-wide, since a season has one decorating window, kept in `season.json` (40). They are set by editing the file and `/season reload`; no new command.
167. **`claim` assignment** (amending 38). While the decorating window is open, a player who played the season (`cells.minPlaytime`) and has no cell in it runs `/hof claim <cell>` for a free cell in one of that season's galleries whose assignment is `claim`; `/hof claim` alone takes the free cell they stand in, or else lists the free cells. Refused, each with its reason: outside the window, a gallery that isn't `claim`, a cell that is taken, a player who already has a cell (they swap instead), one who hasn't played the season. A claim is written through the gallery edit path (`ConfigEdits`), one at a time on the writer thread, so two players can't take one cell, and audited as `claim`. When the window opens, the draw deals cells from the season's `random` and `ordered` galleries as before, and players still without a cell are told to claim one. Anyone without a cell when they are archived gets a random free cell, as under `random`, so nobody who played is left without displays while a cell is free. Swaps and `/hof cell assign` work in `claim` galleries.
168. **Access `bounds`.** A cell's bounds become an edge inside the Hall, as a blocked zone's is outside it: anyone but the cell's owner while they may decorate it is refused entry by any route (a move, a vehicle, a teleport) and put back where they last stood outside it, and the Hall sweep moves anyone found inside to the gallery's entry, an owner whose time has run out included. Seasons' own moves count: archiving sends an owner to their cell only while they may decorate it, and to the gallery's entry otherwise. `/hof <player>` for a cell in a `bounds` gallery lands at the gallery's entry, since the cell's entry anchor is inside it. A cell without bounds has no inside to keep anyone out of, so it isn't a problem, as in any gallery. Bypass holders walk in. Refused entries are audited as `hall-blocked`, repeats counted (82).
169. **Access `gate`.** A cell's two gate anchors are opposite corners of a plane one block thick inside its bounds (a problem on load otherwise). The plane is the configured block, the new `cells.gateBlock` (default `iron_bars`), while the cell is locked, and air while its owner may decorate it; a cell with no owner yet is shut. Seasons sets it when the cell's state changes (the window opening, an owner's time running out, `/season decorate close`, launch, a reload) and at startup, writing `GATE_SET` to the journal before each change, as every world change is; the startup pass sets every loaded gate to its state, which is all recovery needs. Gate blocks are Hall blocks: they drop nothing and only bypass holders change them, and reconciliation puts back a gate that was changed. A player inside a cell when its gate shuts is moved to the gallery's entry. A cell without gate anchors in a `gate` gallery stays walk-in, with a warning on load. Otherwise a gate cell is an `open` cell.
170. **The armour-stand figure.** A gallery with `renderer: armour-stand`, or a platform without mannequins (`Capability.MANNEQUINS`), gets the spec's fallback: an armour stand with arms, every equipment slot locked, invulnerable, without gravity, silent, wearing a player head with the archived skin, its display tag and copies tagged `seasons:archived` like a mannequin's. The helmet goes on the cell's first trophy anchor, or is only in the archive view if the cell has none. A changed renderer is drawn again by reconciliation.
171. **A figure's pose.** "Standing pose (configurable per cell)": a cell may set `pose` in its gallery file, one of the poses the Paper API keeps on a mannequin (standing by default). An armour-stand figure stands whatever the pose, with a warning on load.
172. **The launch button.** The spec's "op-only button block registered as a `launch` anchor in the Hall" isn't in a cell, so it is a gallery's, like its entry and exits: `/hof gallery launch <gallery> [at]`, inside the gallery's bounds, with `none` to remove it. During the Intermission, a holder of `seasons.admin.season` who right-clicks it is asked to press again within 10 seconds, and the second press runs `/season launch` as them, with its refusals. Anyone else is refused with a message and audited as `hall-blocked`; outside the Intermission it says why and does nothing.
173. **`/season audit [player]`.** The last 10 entries, oldest first, from this month's and last month's audit files, read off the server thread: time, actor, action, target, result and details, as plain text. With a player, only the entries whose actor or target is that player, by name or UUID.
174. **Archive status in `/season info`.** The spec's "your archive status": the last season the player is archived into, or that they are waiting to be archived (the season has ended and they haven't been), or nothing if they have never been archived.
175. **Item ids in config.yml.** "Item groups name known items": `firsts.rareItems`, `cells.containers` and `cells.gateBlock` must each name an item the server knows or one of Seasons' groups (84). Anything else is a problem with its key path, on load, reload, validate and `/season config set`. The platform answers through a new `Platform#knownItem`.
176. **`launch.requireManual: false`** has no behaviour in the spec: launch is by `/season launch` or the launch button. Rather than ignore it, `false` is refused on load and reload with a message, as access modes were (80). Owner to say what `false` should do, if anything.
177. **The last valid position is kept in the player record**, as the data model lists (amending 95). It is saved with the record's coalesced writes and at logout. A player found inside a blocked zone goes back to it if it is still outside every blocked zone, after a restart or a relog too, and to the season spawn otherwise, as before.
